從 `CLAUDE.md` 按功能區塊切出來的（PM 2026-10-19，企劃者「CLAUDE.md 請按照功能區塊切割開來」）：Ollama 與三段式、繁體、省電與維修頁、伺服器假人、整季機器人。

## 模組

**模型與文字**
- `tianxia/ollama_client.py`：本機 Ollama 的 client（JSON schema 約束、截斷修復、必填欄位缺了才重問——`0` 與 `False` 不算缺）；`quick_client` 是行動鎖內用的短逾時、不重問的複本。
- `scripts/maintenance.py`：維修頁（Joy 2026-10-18「線上不要 502，顯示伺服器維修中」）：停機時在伺服器那個埠（7861）接管，隧道連得到來源，外面看到的是我們自己的「江湖暫歇」頁（**503 ＋ Retry-After**，`/api/` 回 JSON 免得網頁解析 HTML 炸開；頁面每 30 秒自己探一次，伺服器回來就跳回遊戲）。只用標準庫、不碰資料庫與任何遊戲狀態。`allow_reuse_address = False`：Windows 的 SO_REUSEADDR 會讓它綁上一個已經有人在聽的埠、兩邊分著收請求（實機踩到），所以寧可起不來也不從活著的伺服器手上偷流量。睡／醒腳本的順序與行程比對的坑見 `docs/superpowers/feedback/beta-主機端操作.md`。
- `tianxia/power_save.py`：省電模式（Joy 2026-10-18「有時候這台電腦還要同步跑到其他東西」）：旗標檔 `.local/power_save`（或環境變數 `TIANXIA_POWER_SAVE`）在的時候，模型的 `keep_alive` 改成檔裡寫的（預設 `5m`），沒人玩就讓 Ollama 卸掉模型、把 VRAM 還出來（這台 12 GiB 的卡，gemma4:12b 佔約 9.1 GiB）。`OllamaClient.keep_alive` 是 property、每次呼叫都問一次，所以**開關換了不必重開伺服器**（重開就是全服重新登入），`server.py` 與 `run_bots.py` 兩個行程、每個角色那一份 client 與 `capped` 複本都當場跟著換。配套是 `scripts/warm_keeper.py`（有真人在線就每分鐘替模型續命、沒人就請 Ollama 卸掉；`--warm-now` 給開服腳本用，keep_alive 照省電模式，不會把 12h 釘回去）與登入預熱（`server._warm_model`）。量到的：遊戲那一側（server 1.7%、bots 0.7%、monitor 與隧道 0.1% 的「一核」，四個共約 320 MB）根本不是負擔，所以**不要去砍假人或調巡邏頻率**；開關、睡／醒腳本與數字見 `docs/superpowers/feedback/beta-主機端操作.md` 的「這台電腦還要做別的事」。只讀環境變數與那個檔，不讀時鐘、不碰遊戲狀態。
- `tianxia/zh.py`：模型產出的文字轉成繁體（`to_traditional`，見「模型呼叫」）。
- `tianxia/event_llm.py`：事件的隨口應對（評成功率與做法的善惡、擲骰後潤色、潤色跟結果句重複時的判斷）。`tianxia/flavor.py`：世界事件傳聞的全服潤色（重複事件與重遊的點綴句 2026-10-12 拿掉：在鎖裡等模型、寫出來畫面上看不到）。
**假人與機器人**
- `tianxia/server_bots.py`：伺服器假人的名號、個性、作息（純函式，不碰檔案也不 import 引擎）。
- `tianxia/bot_policy.py`：假人照陣營目標做一個動作，只走 `Game` 的公開行動（含配點 `Game.allocate_stat`）；鐵匠鋪先換買修再打造（`_smith_want`；人在城鎮、湊得出一爐又付得起〔`bot.forge_ready`〕時「進鐵匠鋪」多加 `FORGE_SCORE`〔＝`SMITH_SCORE`，合起來 16，高過往軍令走的一步、低過軍令本身 30：帶著糧草的照舊先接糧車〕，FB-144），神器原品過幾輪才沿用譜名（`_name_originals`，`DIVINE_NAME_CHANCE`）。出陣探索與地盤：出陣照大勢分挑（`_train_value` 讀 `Game.sortie_push`，今天次數用完就是 0、不再往戰線拉），守在有守城軍令時多一份 `ORDER_SCORE`，豪強的攪局是 `STIR_SCORE`（線在 50 不按）；探索三選一照 `GATHER_SCORE`／`SEEK_SCORE`／`SENSE_SCORE` 挑，缺一階素材時找素材多 `NEED_MATERIAL_SCORE`（0.3，不跟挑戰本人 `CHALLENGE_SCORE` 打平），打探懸賞三種都加、討伐懸賞加在找素材；探索入口本身不給分。
- `tianxia/bot_runner.py`：假人程式的核心，每一輪補人（先叫醒退隱的、沒有才新建）、叫醒、讓在線的假人做事；`game.client` 設成 None。
- `tianxia/bot.py`：整季測試與量表用的亂數機器人（`play_season`）：隨機挑選項，每隔幾步配點、練成、合成、修練（`allocate_points`、`spend_xinde`、`forge_and_cultivate`），路過城鎮揭懸賞、交求藝求兵（`take_bounties`，照 `bounties.give_choice`）。鐵匠鋪：`smith_want`（兵器、防具兩頁，這一頁的事先做、沒事才回切頁那一顆；`bot_policy._smith_want` 也用它）、`visit_smith`（整季機器人：兵器頁的事〔換、買、修、打造、換上更好的、淬煉〕做完再切防具頁換、買、修、打造、換上更好的、淬煉）；`forge_step`：伺服器假人在鐵匠鋪打造的下一步（照 `forge_plan`／`armor_plan`，打完換上更好的、不淬煉、一爐之後留 `FORGE_SILVER_RESERVE` 10 兩〔FB-144 從 30 降下來〕）；`keep_book_names`：整季機器人打出神器原品馬上沿用譜名。馬市：`market_want`（整季機器人與假人共用：換上更快的、沒馬就買〔留 `MOUNT_SILVER_RESERVE` 30 兩〕、飽足低於 50 就餵）、`visit_market`、`feed_mount`（假人在 `bot_policy.look_after` 餵）。`wear_better`：裝備庫裡有更好的寶物（`treasures.wanted`，固定順序，身上已經是最前面的就不換）、更快的馬（`mounts.better_mount`，路上不換）就換上，走 `Game.wield_weapon`；假人在 `bot_policy.look_after` 叫。整季機器人只 `advance`、不 `sync`，寄放的東西靠 `advance` 也補發。探索三選一開著時 `pick` 不按空的探索入口（按了什麼都不做，同 `act:rest` 的道理）；`explore_choice` 是量表與腳本要探索時按哪一顆（找素材，關著時 `act:explore`）。

## 模型呼叫

- **暖機要讓請求跑完**（2026-10-18）：這一版的 Ollama 跟著「客戶端斷線」一起取消載入，所以 `OllamaClient.warm` 舊寫法（2 秒逾時就斷、把逾時當成送到了）其實一次都沒把模型載起來過（實測斷線後等 25 秒 `ollama ps` 還是空的）。現在 `warm` 在自己的背景執行緒裡跑到載完（`WARM_TIMEOUT` 600 秒、同時只送一件、非 200 會記一行），呼叫端照舊馬上拿到 True。冷啟動實測 11.4 秒（`num_ctx` 8192）。
- 本機 Ollama，模型 **`gemma4:12b`**（`content/config.json` 的 `ollama_model`；`ollama_think: false`、`ollama_keep_alive: 12h`）。**挑模型的第一條是「裝得進顯卡」**（2026-10-13 換掉 `gemma4:26b`，量法與對照表見 `docs/superpowers/feedback/2026-10-13-模型評選-12b.md`）：這台是 RTX 5070、12 GiB，26b 是 17.4 GiB——大了 45%，所以固定有 24% 的層跑在 CPU，一輪對話 13～15 秒、而且顯卡一次只服務一件（1／4／8 件並發是完美線性，吞吐量約 0.5 件/秒），20 個人裡只要 3 個同時對話，第 3 個之後就撞 30 秒逾時被取消。12b 是 7.2 GiB、**100% GPU**：實測（模型已常駐）隨口應對評分 3 秒、人物對話一輪 6～9 秒、單一短請求 740～934 ms，吞吐量 0.78 件/秒；冷啟動載入約 24 秒。代價是「分辨機智與平庸」退了一截（65 比 5 → 45 比 15），靠 `event_llm.SYSTEM_PROMPT` 的分數檔位補回大半（見那裡的註解）。trycloudflare 約 100 秒就切斷一個請求。
- **三段式**（照人物對話 `server.prepare_dialogue` 的做法）：A 鎖內很快地開單（`Game.dialogue_request`、`Game.forge_request`、`Game.fight_request`、`Game.free_text_request`，只讀）→ B 鎖外叫模型（`companion_agent.prepare_turn`、`naming.generate`、`fight_llm.judge`、`event_llm.judge_event_gamble`；不碰狀態、不拿鎖）→ C 鎖內整個重驗再套用（`Game.choose(prepared=…)`、`Game.forge(…, proposed=…)`、`Game.choose(fight=…)`、`Game.answer_event`），對不上就丟掉、照沒有模型的路走。打造從 2026-10-12 起不叫模型（打造隱藏配方設計第八節）。合成開爐取名的 B 段預算是 `naming_budget_seconds`（60）扣掉 A 段等鎖的時間，`naming.propose(…, budget=)` 照給出去的逾時扣、用 client 的複本；伺服器的開爐一律給 `proposed`（不必叫模型時是 `NO_NAME`），所以鎖裡從不取名。C 段的名字再過 `naming.recheck`，重名在登記時原子判斷，過不了走退路字表（種子是配方鍵＋這一季的天機，不看誰先到）。之後的模型佇列只會換掉 B 段。
- **決戰的放手一搏**拆成兩次（Joy 2026-10-13，見「全服決戰」）：送出時只評成功率（`score_gamble`，短提示、`num_predict` 24，三段式），劇情等回合結算後一整回合批給模型寫一次（`server.narrate_battle`，背景執行緒、排在真人後面；`write_tales`）。
- **還留在鎖內的模型呼叫**：大事潤色（`world.check_thresholds`／`fire_by_id`）、沒給分數的放手一搏（腳本、測試）、鎖內才備料的對話與每隔一陣子的記憶整理／性情漂移、沒給 `proposed` 的開爐與沒給分數的隨口應對。**一律拿 `Game._quick_client()`，不要直接用 `self.client`**：逾時 `in_lock_model_timeout`（15 秒，這是每一步的上限）、不重問；一次拿鎖期間第一次失敗之後，後面的鎖內呼叫都不叫（`_model_budget`；`server._locked` 每次拿到鎖先 `reset_model_budget()`）。**全服斷路器**：任何一次拿鎖裡鎖內的模型呼叫失敗或逾時，`server.py` 打開 `MODEL_BREAKER_SECONDS`（180 秒），這段時間每一次拿鎖一開始額度就用完、直接用固定文字；時間到之後的第一次照常叫，又失敗再打開；開、關各印一行（不寫是誰）。鎖外的路徑不歸它管。
- **繁體**：模型產出的文字（對話、敘事、選項、標籤、名字、點綴）一律過 `zh.to_traditional`：純 Python 的 `opencc-python-reimplemented`、`s2tw` 模式（只轉字、不換詞——`s2twp` 會把「的士卒」換成「計程車卒」，FB-014），繁體輸入原樣通過（FB-018，「里、斗、了」不會被改錯），之後再套一張異體字表 `VARIANTS`（OpenCC 放過日式新字體「鉄」）；import 失敗退回手寫對照表。**要「保證繁體」只靠 OpenCC 不夠。**
- **保底值會把「模型壞了」偽裝成「模型給了中庸的答案」**：成功率評不到退回 40，可是模型對爛寫法正常會評 0～5；曾經因為 `ollama_client` 把 `0` 當成缺值，所有灌水的寫法都被抬到 40（2026-10-05 已修，`tests/test_ollama_client.py`）。驗模型的機率評估要先看有沒有保底警告（`scripts/try_event_llm.py` 會印）。LLM 相關的東西定案前要用真模型跑一次。
- **匿名**：首創者、第一個練成絕學的人寫給別人看的名號在登記當下記下（`MartialArt.creator_shown`／`master_shown`、`Insight.creator_shown`；匿名是「某位少俠」），之後照它寫；名號本身照舊存著當身分。
