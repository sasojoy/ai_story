## 模組

**模型與文字**
- `tianxia/ollama_client.py`：本機 Ollama 的 client（JSON schema 約束、截斷修復、必填欄位缺了才重問——`0` 與 `False` 不算缺）；`quick_client` 是行動鎖內用的短逾時、不重問的複本。
- `scripts/maintenance.py`：維修頁（Joy 2026-10-18「線上不要 502，顯示伺服器維修中」）：停機時在伺服器那個埠（7861）接管，隧道連得到來源，外面看到的是我們自己的「江湖暫歇」頁（**503 ＋ Retry-After**，`/api/` 回 JSON 免得網頁解析 HTML 炸開；頁面每 30 秒自己探一次，伺服器回來就跳回遊戲）。只用標準庫、不碰資料庫與任何遊戲狀態。`allow_reuse_address = False`：Windows 的 SO_REUSEADDR 會讓它綁上一個已經有人在聽的埠、兩邊分著收請求（實機踩到），所以寧可起不來也不從活著的伺服器手上偷流量。睡／醒腳本的順序與行程比對的坑見 `docs/superpowers/feedback/beta-主機端操作.md`。
- `tianxia/power_save.py`：省電模式（Joy 2026-10-18「有時候這台電腦還要同步跑到其他東西」）：旗標檔 `.local/power_save`（或環境變數 `TIANXIA_POWER_SAVE`）在的時候，模型的 `keep_alive` 改成檔裡寫的（預設 `5m`），沒人玩就讓 Ollama 卸掉模型、把 VRAM 還出來（這台 12 GiB 的卡，gemma4:12b 佔約 9.1 GiB）。`OllamaClient.keep_alive` 是 property、每次呼叫都問一次，所以**開關換了不必重開伺服器**，`server.py` 與 `run_bots.py` 兩個行程、每個角色那一份 client 與 `capped` 複本都當場跟著換。配套是 `scripts/warm_keeper.py`（有真人在線就每分鐘替模型續命、沒人就請 Ollama 卸掉；`--warm-now` 給開服腳本用，keep_alive 照省電模式，不會把 12h 釘回去）與登入預熱（`server._warm_model`）。量到的：遊戲那一側（server 1.7%、bots 0.7%、monitor 與隧道 0.1% 的「一核」，四個共約 320 MB）根本不是負擔，所以**不要去砍假人或調巡邏頻率**；開關、睡／醒腳本與數字見 `docs/superpowers/feedback/beta-主機端操作.md` 的「這台電腦還要做別的事」。只讀環境變數與那兩個檔，不讀時鐘、不碰遊戲狀態。**2026-10-28 起還會換模型**（企劃者「休眠模式的時候換成比較小的模型。不要占滿十二 GB」）：第二個旗標檔 `.local/power_save_model`（或 `TIANXIA_POWER_SAVE_MODEL`）寫了模型名，省電模式開著時 `power_save.model` 就把它換上去（`OllamaClient.model` 也是 property，同 keep_alive：換了不必重開），有人在玩的時候也不會被 12b 佔滿整張卡（gemma3:4b 約 4.5 GiB）。三條規矩：(1) **不給預設小模型**——沒寫就照 `Config.ollama_model`，偷偷換模型會讓對話與旁白的品質變了而沒人知道；(2) 省電模式一關就立刻回到大模型（模型那個檔留著也沒關係），寫 `off`／`0` 等於不換；(3) **只有 `from_config` 建的 client 會換**（真的在跑遊戲的那些）——實測腳本自己指定 `--model` 不可以被主機此刻的省電模式偷偷改掉，不然量出來的是別的模型。配套：卸模型改成**把 `/api/ps` 載著的全卸**（`warm_keeper.unload`、主機端的睡腳本），不然換過去之後舊的大模型還躺在 VRAM 裡等它自己的 12h，卡一直是滿的；兩站共用一張卡，所以主機端的開關一次把旗標寫進兩份 clone 的 `.local/`。
- `tianxia/zh.py`：模型產出的文字轉成繁體（`to_traditional`，見「模型呼叫」）。
- `tianxia/event_llm.py`：事件的隨口應對（評成功率與做法的善惡、擲骰後潤色、潤色跟結果句重複時的判斷；減法季的分岔另一段提示 `OUTCOME_PROMPT`、`classify_outcome`／`judge_outcome`，見「模型呼叫」）。`tianxia/flavor.py`：世界事件傳聞的全服潤色（重複事件與重遊的點綴句 2026-10-12 拿掉：在鎖裡等模型、寫出來畫面上看不到）。

## 模型呼叫

- **必填欄位要寫進送出去的 schema**（2026-10-19）：pydantic 欄位有預設值時 `model_json_schema()` 不會把它列進 `required`，結構化輸出的語法於是允許模型回一個 `{}`，接著 client 的必填檢查判定「缺欄位、疑似被截斷」再重問一趟——實測**每一封書信都白跑第一趟**（`LetterText.letter` 有預設值；對照組 `NameReply` 本來就有 `required`，取名一直第一趟成功）。`chat_structured` 的 `require_in_schema` 把呼叫端宣告的 `required_fields` 寫進 schema，**預設關、要的人自己開**（opt-in）：隨口應對的評分那一次被 FB-223 的守門測試釘到連 kwargs 都要一字不差，連加一個關掉的參數都不行。現在開著的是 `letters`、`battle_instance.write_tales`（`TaleBatch.lines`）、`companion_agent` 的對話（`narrative`、`options`；NPC 智能 2.0那幾輪另用 `schema_required` 加 `parley.ASK_FIELDS` 等——只進 schema、空字串算答了、型別裡的 null 也拿掉，2026-10-24 gemma `ask` 漏填 14/30、`willing` 寫 null 5/30）。**通則測試** `tests/bots/test_schema_required.py` 掃 `tianxia/` 每一個 `chat_structured`：`required_fields` 沒進 schema 的要開 `require_in_schema`，還沒開的列在 `KNOWN`（附原因，只准減）。另外 **`num_predict` 只加不減**（預設 1024 沒出過截斷的呼叫別碰，調低等於自己製造截斷），`fight_llm` 1320、`letters` 420、對話 2400（2026-10-24 從 1400 拉高：NPC 智能 2.0一輪三段敘事）；省電模式下冷啟動 11.4 秒會吃掉假人取名的預算，所以 `bot_naming_budget_seconds` 是 60。細節見 `docs/superpowers/feedback/2026-10-19-模型呼叫的三個坑-給joy.md`。
- **暖機要讓請求跑完**（2026-10-18）：這一版的 Ollama 跟著「客戶端斷線」一起取消載入，所以 `OllamaClient.warm` 舊寫法（2 秒逾時就斷、把逾時當成送到了）其實一次都沒把模型載起來過（實測斷線後等 25 秒 `ollama ps` 還是空的）。現在 `warm` 在自己的背景執行緒裡跑到載完（`WARM_TIMEOUT` 600 秒、同時只送一件、非 200 會記一行），呼叫端照舊馬上拿到 True。冷啟動實測 11.4 秒（`num_ctx` 8192）。
- 本機 Ollama，模型 **`gemma4:12b`**（`content/config.json` 的 `ollama_model`；`ollama_think: false`、`ollama_keep_alive: 12h`）。**挑模型的第一條是「裝得進顯卡」**（2026-10-13 換掉 `gemma4:26b`，量法與對照表見 `docs/superpowers/feedback/2026-10-13-模型評選-12b.md`）：這台是 RTX 5070、12 GiB，26b 是 17.4 GiB——大了 45%，所以固定有 24% 的層跑在 CPU，一輪對話 13～15 秒、而且顯卡一次只服務一件（1／4／8 件並發是完美線性，吞吐量約 0.5 件/秒），20 個人裡只要 3 個同時對話，第 3 個之後就撞 30 秒逾時被取消。12b 是 7.2 GiB、**100% GPU**：實測（模型已常駐）隨口應對評分 3 秒、人物對話一輪 6～9 秒、單一短請求 740～934 ms，吞吐量 0.78 件/秒；冷啟動載入約 24 秒。代價是「分辨機智與平庸」退了一截（65 比 5 → 45 比 15），靠 `event_llm.SYSTEM_PROMPT` 的分數檔位補回大半（見那裡的註解）。trycloudflare 約 100 秒就切斷一個請求。
- **三段式**（照人物對話 `server.prepare_dialogue` 的做法）：A 鎖內很快地開單（`Game.dialogue_request`、`Game.forge_request`、`Game.fight_request`、`Game.free_text_request`，只讀）→ B 鎖外叫模型（`companion_agent.prepare_turn`、`naming.generate`、`fight_llm.judge`、`event_llm.judge_event_gamble`；不碰狀態、不拿鎖）→ C 鎖內整個重驗再套用（`Game.choose(prepared=…)`、`Game.forge(…, proposed=…)`、`Game.choose(fight=…)`、`Game.answer_event`），對不上就丟掉、照沒有模型的路走。打造從 2026-10-12 起不叫模型（打造隱藏配方設計第八節）。合成開爐取名的 B 段預算是 `naming_budget_seconds`（60）扣掉 A 段等鎖的時間，`naming.propose(…, budget=)` 照給出去的逾時扣、用 client 的複本；伺服器的開爐一律給 `proposed`（不必叫模型時是 `NO_NAME`），所以鎖裡從不取名。C 段的名字再過 `naming.recheck`，重名在登記時原子判斷，過不了走退路字表（種子是配方鍵＋這一季的天機，不看誰先到）。之後的模型佇列只會換掉 B 段。
