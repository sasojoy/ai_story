## 測試怎麼挑（開發規範手冊 4.1～4.3、4.5；`scripts/test_for.py`）

- **什麼時候跑什麼**（手冊 4.2）：開發中只跑自己那一塊（`test_for`）；QA 不重跑測試；合進功能分支、develop 跑那一塊＋核心契約＋煙霧（Joy 回覆手冊十一之 3 以前，合併閘門照技能檔舊的寫法）；整套含 slow 一天一次（下面「每日整套」）與上 main 之前。同一台最多兩份測試同時跑，各自 `-n 4`，不寫 `-n auto`。
- **指令**：`.venv/Scripts/python.exe scripts/test_for.py`——不給 `--base` 跟 **`origin/develop`** 比（PM 10/31：大家從 develop 開；以前是 `origin/main`）；環境變數 `TIANXIA_TEST_BASE` 蓋過預設，`--base` 再蓋過它。**功能分支的工作樹照舊給 `--base origin/feature/<名字>`**（不然功能分支上以前的改動全會算進來）。
  - 第一行一定寫這一次跟哪個 base 比、從哪裡來的（預設／`TIANXIA_TEST_BASE`／`--base`）與分岔點，例「跟 origin/develop 比（預設；分岔點 455664ac）」。這份 clone 的 `git fetch origin` 不更新 `feature/*`、`dev/*`：那條分支沒明確 fetch 過時第一行寫「找不到這條分支」和要下的 `git fetch origin +refs/heads/…:refs/remotes/origin/…`，然後**停下、一條都不跑、結束碼 2**（跟 HEAD 沒有共同祖先的 base 也一樣）：沒有分岔點挑法就不準——不給檔名只剩還沒提交的改動，給了檔名整個檔當成新檔（10/31 審查：`models.py` 挑到 347 個檔）。
  - `--list` 只列要跑的檔與**為什麼**（每一個 hunk 落在哪個方法、算哪一群）；`--count` 再用 `pytest --collect-only` 數一共幾條（不跑）。
  - `--slow` 挑到的連 slow 一起跑（內容批要當場跑真實內容的整季時用）；平常 **slow 不自動跟**。注意 slow 不只第四級：77 個測試檔整個標 slow（`pytestmark`），其中很多是一般的功能測試（`test_explore_one*`、`test_sortie_duel*`、`test_epiphany`、`test_errands`、`test_stances*`、`test_story_*`……），所以 `test_for` 開跑前會列出「整個檔標 slow、這一次不跑」的檔；挑到的全被 slow 濾光、一條都沒跑時印「要跑加 --slow」、結束碼 0（不是 pytest 的 5）。**看到這個提示、而那些檔正是你這一包的，加 `--slow`**（PM 10/31：照這個做法，不自動帶 slow、不改那些檔的標記）。
  - **改到的測試檔本身一律連 slow 一起跑**（改了就是要跑它）；挑到的其他檔照舊不含 slow，所以這時分兩次跑（`--count` 兩行）。
  - `--all` 整套含 slow（上 main 之前）。
  - 挑到三個檔以上自己加 `-n 4`；`--` 之後的參數原樣交給 pytest，`-- -n 2` 換掉預設的 `-n 4`、`-- -x -k fuse` 照給。
  - 也可以直接給檔名：`scripts/test_for.py tianxia/engine.py --list`（照它跟 base 的差異算；沒有差異就照整個檔算）。

## 每日整套（開發規範手冊 4.4，`scripts/nightly.ps1`）

整套含 slow 不再在每次合併時跑，改成一天一次集中跑（企劃者 2026-10-30「整套集中在某個時間點跑」「偶爾晚一點才知道別處壞了，可以接受」）。

- **做什麼**：`scripts/nightly.ps1` 把自己的行程優先權設成 BelowNormal（子行程 python、pytest 的工作行程都繼承，不搶線上伺服器的 16 核），再叫同一個資料夾的 `scripts/nightly.py`：
  1. 明確 fetch `origin/develop`（`+refs/heads/develop:refs/remotes/origin/develop`；這份 clone 的 `git fetch origin` 只照 `remote.origin.fetch` 寫的那幾條抓；git 一律 `GIT_TERMINAL_PROMPT=0`、`GCM_INTERACTIVE=never` 不跳提示，fetch 300 秒〔`FETCH_TIMEOUT`〕沒回來就放棄、照本機上一次抓到的跑、寫進「備註」），把 `<主要 clone>\.local\nightly\checkout`（一份 `git worktree`）重設成它的乾淨一份（`reset --hard`＋`clean -ffdx`）；
  2. 在 checkout 裡跑整套含 slow：`pytest -q -n 4 -m "slow or not slow" -rfE --junitxml=…`，`PYTHONIOENCODING=utf-8`，`TIANXIA_DB` 指到系統暫存資料夾的 `tianxia-nightly\nightly.db`（每次清掉）；
  3. 寫 `.local\nightly\<日期>.log`（pytest 完整輸出）、`<日期>.xml`（junit）、`<日期>.json`（這一次的摘要，下一次拿來比）、`latest.txt`（給人看的摘要）。
  不推任何東西，不碰 `saves\` 與線上。`.local/` 在 `.gitignore` 裡。
- **`latest.txt` 怎麼讀**：第一行是日期與 develop 的 SHA；「結果」是 passed／failed／error／skipped、pytest 結束碼、用了幾分鐘；接著跟前一次（`<日期>.json` 裡日期比今天早、最近的那一份）比：
  - **新紅**：前一次綠（或前一次沒有這一條）、這一次紅——交回最近碰到那一包的那一線修；
  - **舊紅**：前一次就紅；每一條後面寫「從哪一天起紅、第幾天」（`<日期>.json` 的 `red_since` 一路帶下去；這一欄以前沒有的 json 當成從那一天起；轉綠再紅從頭算），PM 照手冊 4.4「新紅三天沒修就 revert」直接看；
  - **轉綠**：前一次紅、這一次不紅；
  - 最後列前一次的 SHA 到這一次之間 develop 新進的提交（`git log <前一次>..<這一次>`），對照紅的測試是哪一包、哪一筆碰到那一包。
  第一次跑沒有前一天：寫「沒有前一天可比」，紅的全部列在新紅。pytest 沒跑完——結束碼不是 0（全綠）、1（有紅），例如 2 中斷（junit 只有一半）、3 內部錯誤、4 用法錯誤（venv 少了 develop 新用的外掛）、5 一條都沒收到，或根本沒有 junit——寫「沒跑完」、不比、不留 `.json`（下一次照樣跟最後一次跑完的比）。開跑前先刪掉同一天的 `<日期>.xml`：同一天重跑（修好紅的再跑一次）時 pytest 沒寫出新的，不會把早上那一份掛在新的 SHA 上。
- **PM 每天早上看 `latest.txt`**（手冊 4.4）：新紅開 FB、寫進交接；綠了把 SHA 記在交接「測過的」；新紅三天沒修，把那一線合進 develop 的那一筆 revert。develop 上的紅不擋別人開工，只擋上 main。
- **手動跑**：`powershell -NoProfile -ExecutionPolicy Bypass -File scripts\nightly.ps1`（哪一份工作樹的都行，它照 `.git` 找回主要的 clone；`-Workers 4`、`-Branch develop` 是預設）。**一次只跑一份**（手冊 4.2）：跑的時候在 `.local\nightly\running.lock` 記 pid 與開始時間，第二份（手動撞上排程、或反過來）看到鎖就印「另一份每日整套正在跑」、結束碼 1，不碰 checkout、暫存資料夾與 log（排程的 `IgnoreNew` 只擋排程自己疊起來）；跑完或失敗都會還鎖，被排程兩小時上限砍掉留下的鎖超過 3 小時（`LOCK_STALE`）就不算數。只重寫摘要：`.venv\Scripts\python.exe scripts\nightly.py --summarize-only [--date 2026-10-31]`。
- 摘要的比較（junit 換回測試 id、新紅／舊紅／轉綠、同一天重跑跟前一天比、沒跑完不留 `.json`、第一次全列新紅、兩個 BOM）由 `tests/core/test_nightly.py` 守（純函式，用 `tmp_path` 造 junit 與 json，一兩秒）；改 `nightly.py` 跑 `scripts/test_for.py scripts/nightly.py`。
- `nightly.ps1` 存成 **UTF-8 含 BOM**：Windows PowerShell 5.1 沒有 BOM 會照 ANSI 讀，中文全變亂碼。改它的時候保住 BOM（Write 工具寫出來沒有 BOM，用 Python 寫 `b"\xef\xbb\xbf" + …`）。`latest.txt` 也帶 BOM，`Get-Content` 才讀得對。
- `<日期>.log`、`<日期>.xml` 留 30 天（一份 xml 約 1.5 MB），`<日期>.json` 全留。checkout 是主要 clone 底下的一份 `git worktree`，`git worktree list` 看得到它（`.local/nightly/checkout`），不要刪；刪了下一次會自己重建。
- 2026-10-31 第一次手動跑（develop `455664ac`，`-n 4`、BelowNormal，同時另有一個代理在跑 `-n 6`）：11,479 passed、0 failed，14.9 分鐘；三層行程（powershell、python、pytest 與四個工作行程）的優先權都是 BelowNormal（6）。

### 怎麼註冊排程（**已註冊**：2026-10-31 PM 照企劃者 10/30「03:30，PM 註冊」註冊了 `TianxiaNightly`，每天 03:30、使用者登入時才跑、漏跑醒來補一次；下面是當時的步驟，重註冊或搬機器時照做）

註冊排程是這台機器的持久設定（手冊 4.4、第十四節）：**由企劃者按一次，或 PM 徵得企劃者同意後註冊**；子代理不註冊。時間還沒定（Fable 提 03:30，避開 Joy 的部署與企劃者的白天），下面先寫 03:30，註冊時換成定的時間。

1. 先讓 checkout 裡有這支腳本：develop 合進了 `scripts/nightly.ps1`、`scripts/nightly.py` 之後，手動跑一次（上面「手動跑」），它會把 `.local\nightly\checkout` 重設成有這兩支的 develop。之後排程指到 checkout 裡的那一份——每次跑都會先把自己更新成最新的 develop。
2. 在 PowerShell 註冊（`StartWhenAvailable`：機器睡著漏跑，醒來補跑一次；`IgnoreNew`：上一次還沒跑完就不疊一份）：
   ```powershell
   $ps1 = "C:\Ray\專案\天下大勢\.local\nightly\checkout\scripts\nightly.ps1"
   $action = New-ScheduledTaskAction -Execute "powershell.exe" -Argument "-NoProfile -ExecutionPolicy Bypass -File `"$ps1`""
   $trigger = New-ScheduledTaskTrigger -Daily -At "03:30"   # 待企劃者定
   $settings = New-ScheduledTaskSettingsSet -StartWhenAvailable -MultipleInstances IgnoreNew `
       -ExecutionTimeLimit (New-TimeSpan -Hours 2) -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries
   Register-ScheduledTask -TaskName "TianxiaNightly" -Action $action -Trigger $trigger -Settings $settings `
       -Description "天下大勢每日整套：origin/develop 整套含 slow（scripts/nightly.ps1）"
   ```
   用 `schtasks` 也可以，但它設不了 StartWhenAvailable，註冊完要補一步：
   ```powershell
   schtasks /Create /TN TianxiaNightly /SC DAILY /ST 03:30 /TR "powershell.exe -NoProfile -ExecutionPolicy Bypass -File \"C:\Ray\專案\天下大勢\.local\nightly\checkout\scripts\nightly.ps1\""
   $t = Get-ScheduledTask TianxiaNightly; $t.Settings.StartWhenAvailable = $true; Set-ScheduledTask -InputObject $t
   ```
3. 預設是「使用者登入時才執行」。要登出也跑，在工作排程器裡那一項的內容勾「不論使用者登入與否均執行」（會問 Windows 密碼，企劃者自己輸入）。
4. 驗：`Start-ScheduledTask TianxiaNightly` 立刻跑一次；`Get-ScheduledTaskInfo TianxiaNightly` 看 `LastRunTime`、`LastTaskResult`（0 是腳本正常結束，紅不紅看 `latest.txt`）；拿掉：`Unregister-ScheduledTask TianxiaNightly -Confirm:$false`。

## 量表與教訓

### 好玩度量表（企劃者 2026-10-03 提的方法，`scripts/fun_run.py`）
企劃者的話：「你要假裝自己是一個新玩家，甚麼都不知道，然後有新東西……你的好玩度會上升，反之如果你的行動看到重複出現過的，那你的好玩度會下降，重複越多次下降越多」。
- **定案的算法**：每條管道（事件、意境、合成出來的功法〔配方首創／查表〕、對手、地點）各自算「每次碰到它，有幾成給了你新東西」（−100～+100）再平均（`FunLog.balanced`）；整季沒出現的管道算 −100。單一總分（`FunLog.score`，每百行動的密度）只留著對照，**不要拿它下結論**——總分會隨「玩了多久」無上限累積，被觸發頻率高的管道支配。
- 實作上刻意處理：新而沒有收穫的首見只拿一半分；**機制動作的重複（移動、遊歷、練功、療傷）不扣**，只扣敘事內容的重複；遞增懲罰夾上限；輸出分項、每日淨值的時間軸、最後一次看到新東西是第幾天。
- **校準先於結論**：`--calibrate` 用行為重現造出已知比較無聊的歷史狀態（`--no-craft --no-train`、`--no-train`、現在），指標排不對就是指標錯了。計畫一拿掉素材煉製之後校準剩這三個狀態；10/3 四個狀態時量到種子落差 36 分 < 狀態差距 93 分，現在的數字沒重量。當時最大的問題是事件管道（茶館說書一季 27～37 次），之後有了防重複輪替（`events.rotation_pool`）。
- **量不到的事**：挫折（連續失敗、不可預期的損失）。新角色連輸三場、氣血見底這種坑，這個指標看不出來，要另外量或實機試玩。

### 量平衡與試玩的教訓（還在用的）
- **量平衡之前先確認機器人會用到那個機制**（舊稱「第三層」的教訓）：`bot.py` 不會煉製的那段時間，所有平衡數字描述的都是「忽略新玩法的玩家」。`bot.forge_and_cultivate`、`allocate_points` 就是為此存在。
- **以後要在「什麼都沒發生」的分支上掛東西，先確認那個分支真的會被走到**：舊版探索 100 次有 100 次撞到事件，掛在「一無所獲」後面的素材與遭遇戰一次都沒執行過。
- **不要憑有限的試玩就斷言某個機制「不存在」**，下結論前先查 content。
- **實機試玩**（用真實 `content/` 跑真正的 `Game`，每步印出所有選項、偵測「全部 disabled」或「選項組合連續多輪不變」）抓得到單元測試看不到的死路：體力歸零全部 disabled、龍頭人物碰不到、裝飾用的按鈕、對玩家隱形的數值變化、新角色照著引導走把自己打死。資訊透明（勝算、成功率、還差多少）是這類坑最常見的解法。
- **重現歷史缺陷要連同期的程式行為一起退回**：缺陷常常是「檢查沒有」加上「當時的策略比較笨」兩件事一起造成的。
- 判準只寫有依據的那一條；判準不通過時先確認是重現不夠真、還是指標看不見，不要急著調參數迎合直覺。
- **任何「用 Game 跑整季」的腳本都要先開季**（`store.open_season(now)`；`bot.play_season` 自己會開），不然停在籌備中、什麼都不會發生。
