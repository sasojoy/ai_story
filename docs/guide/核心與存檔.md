## 模組

**門面與程式**
- `tianxia/`：純 Python 規則引擎，**不得 import 任何網頁框架**（fastapi 等）。`engine.Game` 是唯一對外門面。**例外**（PM 2026-10-31）：功能包的 `tianxia/features/<包>/routes.py` 可以 import fastapi，只在殼掛路由時延後 import（包的 `__init__.py` 在 `routes()`、`admin_tools()` 裡面才 `from . import routes`）；引擎、`run_bots.py`、假人不碰。守門：`tests/core/test_feature_boundaries.py` 的 `test_only_package_routes_import_a_web_framework_and_only_when_the_shell_mounts_them`（照原始碼：`tianxia/` 底下只有包的 `routes.py` import fastapi／starlette／uvicorn、沒有模組在載入時就 import `routes`，幾毫秒）與 `test_the_engine_the_bot_program_and_the_bots_load_no_web_framework`（slow，約 3 秒：乾淨的子行程 import `tianxia.engine`、`tianxia.bot`、`bot_policy`、`bot_runner`、`run_bots` 之後 `sys.modules` 裡沒有這三個）。
- `content/`：遊戲內容（JSON；**各包宣告的內容檔在 `tianxia/features/<包>/content/`**，`Feature.content` 寫的是相對於那裡的路徑，真實內容與測試內容才去包裡找、其他的根照舊攤平，掃整份內容走 `content.real_files()`、`real_event_files()`，全部拆包第 62 批；**測試內容**同一個判準，包宣告了這個 rel 而且有檔的在 `tianxia/features/<包>/tests/content/`，其餘的在 `tests/fixtures/content/`；包的測試用的 `content` fixture 只載核心加那一包〔`load_content(only=)`，不驗；碰 `validate` 報 RuntimeError，要驗內容的測試標 `whole_content` 拿整份〕，第 63 批），載入時由 `tianxia/content.py::validate` 交叉檢查（id、連通、素材拿不拿得到、退路字表組出的每個名字都過得了命名過濾、獎勵不能給或扣博聞、隨口應對的獎勵不能高過檢定選項……）。`tianxia/features/gear/content/gear.json` 是寶物表、名駒、名將贈禮（裝備三；沒有這個檔就沒有寶物的來源）。`content/profiles/<名字>.json` 是設定覆寫檔，由環境變數 `TIANXIA_PROFILE` 選（現役 `season21`、`week7`；`server.py` 當主程式、`run_bots.py` 與主機端工具沒帶時套 `season21`〔`content.serving_profile()`〕，`import server` 與不帶設定的 `load_content` 讀 `config.json` 那一層；週末設定 `weekend` 第 14 批拿掉），只能寫 `Config` 有的欄位。`season21`（正式季第 1 批）：21 天的季（`season21`、第一季規則開、`season_weeks` 3、`season_days` 21、人數上限 20、豪強分屬兩軍），見「第一季濃縮版」的「21 天季」；只有寫了 `season21` 的設定檔可以改 `season_weeks`（`tests/core/test_content.py` 守門：`season21` 的章加季長釘住它）。
- `server.py`：網頁伺服器（FastAPI），只負責登入、行動鎖、鎖外的模型呼叫與把畫面要的東西整理成 JSON；引擎的 Markdown 在這裡轉成 HTML（原始 HTML 一律跳脫）。鎖內模型呼叫的全服斷路器也在這裡（見「模型呼叫」）。
- `web/`：手機優先的單頁網頁（`index.html`／`style.css`、緊接它的 `map.css`、`shop.css`／`app.js`，沒有建置步驟、不靠外部函式庫，見「介面」）。
- `run_bots.py`：伺服器假人程式的入口，每隔 `bot_tick_seconds` 呼叫一次 `BotRunner.tick()`，跟 `server.py` 同時開著、開同一個資料庫與同一份設定。
**存檔與全服狀態**
- `tianxia/database.py`：SQLite（預設 `saves/tianxia.db`，環境變數 `TIANXIA_DB` 可改；線上版與開發版各用各的）：連線、資料表、交易。一個動作＝一筆交易（`BEGIN IMMEDIATE`，出錯整個撤回），同一個執行緒可以巢狀（交易可以巢狀；`WorldStateStore.mutate` 不行，內層寫的會被外層蓋掉，直接丟 `RuntimeError`）。結構版本記在 `PRAGMA user_version`（目前第 9 版：第 4 版加 `gear_recipes`，全服兵器配方；第 5 版加 `biographies`，玩家傳；第 6 版加 `mall_purchases`、`mall_ledger`、`mall_entitlements`，商城，見 [商城](商城.md)；第 7 版加 `action_counts`、`action_firsts`，真人量表，見下面 `playlog`；第 8 版拿掉從來沒人讀寫的見聞紀錄 `rumor_heard`〔審查 S-12〕；第 9 版加 `sessions`，登入狀態，只存 cookie 的 SHA-256，`accounts.SessionStore`〔審查 S-10〕）；改結構時新增一組句子、接進 `SCHEMA`、`MIGRATIONS[舊版]` 指向它、`SCHEMA_VERSION` 加一，舊檔打開時在同一筆交易裡一版一版就地升級（中途出錯整個撤回、檔還是舊版；沒有遷移路徑就丟 `RuntimeError`）。**改結構前先跟 PM 對版本號。**
- `tianxia/world_state.py`：全服狀態的資料模型與存取介面 `WorldStateStore`（Protocol）；實作是 `tianxia/sqlite_world.py::SqliteWorldStore`（`open_world()`）。小的整份覆寫，會長大的（傳聞、江湖史、全服登記的武學、配方、兵器配方、改過的名字、合併出來的意境、第一個練成絕學的人、投靠名冊、決戰回合）一筆一筆加、照季分；換季不刪資料，江湖史跨季保留——**例外是傳聞與決戰回合紀錄**（審查 S-12，企劃者 Joy「上上季的資料存在另一個封存區備用」）：`next_season` 換到第 N 季時，第 N−2 季與更早的 `rumors`、`battle_rounds` 搬進資料庫旁邊的 `<檔名>-archive.sqlite`（`tianxia/log_archive.py`：主檔的寫入交易裡讀出 → 另一條連線寫進封存檔、COMMIT → 主檔一個 savepoint 刪掉；封存檔寫不進去、刪不掉都只是這一次不搬，換季照常，下一次換季再搬；同一個流水號 INSERT OR REPLACE，重搬不重複），搬了就照易名帖那樣作廢傳聞快取（`_forget_logs`）。封存檔遊戲裡沒有畫面讀它；決戰本身（`battles`）、江湖史、戰記（`-tale.sqlite`）不搬。武學、改過的名字、意境、兵器配方共用一個名字空間（`sqlite_world._name_taken`）；登記都是鎖內原子（`claim_recipe`、`claim_insight_recipe`、`claim_weapon_recipe`、`link_recipe`、`link_insight_recipe`、`rename_skill`、`claim_master`，隱藏配方的首位發現者與神器原品主人 `claim_gear_find`、神器定名 `name_divine`、仿品數 `add_copy`）；`fused_arts`／`merged_insights` 是合到舊的找候選用的；`divine_records` 讀神器譜（`gear_recipes` 裡「鑄|」開頭的列，跨季）；名將本命兵器的歸屬（`WorldState.signature_arms`：人物 id → `SignatureClaim`〔拿的人、送或奪〕，小的整份覆寫，隨季存進 `seasons` 表）由 `signature_records()` 跨季讀（唯讀快照，一次 `json_extract`，沒有新資料表、結構版本不動），給神器譜的本命兵器那幾行（`signature_arms.book_rows`）；玉璽碎片的全服登記 `SharedWorldState.seal`（正本，跨季、不分季）與還沒收場的奪璽單挑 `seal_duels`（全服、不在季裡，寫一律 `world.mutate`、只加傳聞與江湖史，`_save_season` 蓋不到），唯讀的 `seal_state()`、`seal_duel_open()`。**存進資料庫的模型要讓上一版程式讀得進來**（FB-695，退回舊程式用）：這些模型沒設 `extra`，pydantic 預設略過不認得的欄位，所以加欄位沒事；可是往舊程式也有的 `Literal` 加一個值（例：碎片登記 `SealEvent.kind` 加 `use`），新程式一寫進去，舊程式讀到整列就 `ValidationError`、伺服器與假人程式都起不來。新的種類另開一欄（`SealRegistry.uses`），空的時候用模型自己的 `model_serializer(mode="wrap")` 把那個鍵拿掉、不寫進 JSON（`SealRegistry._drop_empty_uses`、`BattleInstance._drop_empty_front_note`；關著、沒用過的存檔一個位元組都不變）——**不用 `Field(exclude_if=…)`**：那是 Pydantic 2.11 才有的，`requirements.txt` 寫 `pydantic>=2.6`，舊版當多餘的參數略過、空的照樣寫出來，讀檔時用 before 驗證器把舊資料搬過去。
- `tianxia/characters.py`：角色存檔（`CharacterStore`、`open_characters()`），一個角色一列，**不含賽季**（`GameState.world` 只在記憶體）；名號比對不分大小寫。`PlayerState.seen_real`（自己上線的現實秒）只在那個人自己的請求裡寫（伺服器的 `act`／`act_look` 叫 `Game.mark_seen`、假人程式自己那一輪），`Game.sync` 不寫——管理者的 `_admin_target`、`_kin`、`_load_kin` 都碰不到；奪璽單挑的 `last_seen` 也只有 `own_request` 的 Game 記，假人永遠不在場。
- `tianxia/accounts.py`：帳號與密碼（`accounts`、`logins` 表），見「原則」的登入那條。**帳號鍵終身不變**（J 波第 201 批）：有 `password` 列的是小寫帳號，沒有的是 `id:<accounts.id>`；`id:<n>` 只認沒有 `password` 列的帳號（`AccountStore._key()` 照原樣比、不轉小寫）。帳號層的新資料一律認 `accounts.id`（`AccountStore.account_id`）；第三方身分查帳號鍵用 `AccountStore.login_key(provider, subject)`（K 波第 202 批；`provider` 是 `password` 回 None）。管理者重設沒有密碼的帳號回「這個帳號沒有密碼，請他用綁定的方式登入。」（`NO_PASSWORD`，不清 sessions）。帳號綁定開著時，名號不准是客服、官方、管理員、GM（`name_base.STAFF_NAMES`），也不准以 `id:` 開頭（`identity_base.blocked_name`，建角色與易名帖都擋，回撞名同一句）；關著照舊。**名單上的帳號**（第 207 批，M 波；`identity_base.listed`：管理者名號、帳號名照 `accounts.normalize` 比管理者名號、客服名單）在 identity 開著時，要這次 session 是密碼登入、6 小時內登入或重驗過才有管理者權限（`identity_base.admin_session_ok`）；identity 開著時**所有帳號**的密碼至少 12 字（第 207 批先只對名單上的，第 209 批改成全體，企劃者 2026-11-09「2 選 A」；`STRICT_PASSWORD_MIN`，拒絕句 `STRICT_SHORT_PASSWORD`「密碼至少 12 字。」，名單上、名單外一字不差；`check_password(strict=…)` 的 `strict` 只看 `identity_base.on`、不再查 `listed`：註冊、改密碼、補設密碼、忘記密碼、管理者重設、`scripts/set_password.py` 六條路，`register`、`change_password`、`set_password`、`add_password`、`reset_password` 收 `strict`；舊名 `STAFF_*`、`staff` 不留別名；登入不擋，現有的短密碼照登入、下次改才要求；`/api/identity/gate` 多回 `pw_min`，登入頁的提示與 placeholder 由 `web/identity.js` 換）；關著一個字不變。
- `tianxia/playlog.py`：真人量表（減法季批 0，設計稿第十章；資料庫第 7 版）：每個帳號（`characters.name_key`）每一天（回體丹換日的那一天）上線了沒、按了哪幾顆（`action_counts.buttons`，`button_of` 歸類：`act:`、`explore:` 留兩段，其他留第一段），第一次寫隨口應對（`/api/answer`）、第一次跟人物說話（交友、求見、對話選項、自己說）、第一次看輿圖的「全區」（`whole_area`，表先留好，輿圖四層那一批接上）是哪一天（`action_firsts`，一季只記第一次）。表名照整合設計 11.4 的 `action_counts`。**只有伺服器記**：`server.act`／`act_look` 進鎖同步之後記上線（`_play_seen`），`/api/choose`（被擋下來、不在選單上的不算）、`/api/travel`、`/api/answer`、`/api/say` 做成之後另開一筆小交易記一次（`_play_did`）；假人不記。**不露給玩家**（沒有 API、不進 `main_view`）；主機端 `scripts/play_metrics.py`（唯讀）印一季的總數：第 3、7 天留存（判準【預設】五成、四成）、第幾天不再上線、每顆鈕的佔比、三種第一次的中位數、第 2 天以前寫過隨口應對的幾成（判準五成）；設計寫的「管理者頁一張表」還沒做（批 0 先給主機端腳本）；**只印總數不印名號**（表上只有真人，列名號等於從缺席看出誰是假人）。
