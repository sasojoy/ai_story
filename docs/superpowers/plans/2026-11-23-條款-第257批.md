# 條款第 257 批：identity 開著時，同意紀錄的鍵對不對得上伺服器擋的鍵（計畫）

分支 `dev/terms-reask-255`（接第 255 批，起點 2b2921fb）。第一段只量與寫計畫；第二段寫測試，對不上才照③處理。
起因：AG 波紀錄（`docs/superpowers/plans/2026-11-23-波次AG紀錄.md` 第 32、35、248 行）留的一句。

## 一、讀到的（第一段在 2b2921fb 上讀的，第二段不必重讀）

- 帳號鍵（`tianxia/accounts.py`）：`_key()`（77–80）照 normalize，`id:` 開頭照原樣；`_get()`（133–158）：
  有 `password` 列、沒記號列 → 小寫帳號名；沒有 `password` 列，或有記號列（`provider='id'`，第 204 批補設密碼）→ `id:<n>`。
  有密碼的帳號拿 `id:<n>` 查不到（139 行的條件），兩種鍵不會指到同一個帳號。綁定（`add_login`）、解綁（`remove_login`）都拿 `account.key`，不改鍵。
- 殼（`server.py`）：`register()`（1607–1619）記同意在 `normalize(login_name)`；`login()`（1598–1604）回 `normalize(login_name)`；
  `_start_session()`（1796–1811）identity 開著時把鍵換成 `account_store().get(key).key`，關著照傳進來的；`_account()`（1711）回 session 的鍵；
  `_game()`（1718–1729）把 session 的鍵原樣傳給 `terms_base.gate_problem`（不是 GET、不是管理者才問）。
- 核心 `tianxia/core/terms_base.py`：`record(content, key, version)`、`gate_problem(content, key)` 都不轉鍵，只轉給 hook。
- 條款包 `routes.py`：`_Hook.record` → `record_consent` → `ConsentStore.record(key)`；`_Hook.must(key)`（72–86）查 `ConsentStore.latest(key)`，
  快取 `(旁檔路徑, 版號, 鍵)` 只記「同意過現行版」；`/api/terms`、`/api/terms/agree`（125–142）都用 `shell._account(request)`（session 的鍵）。
  `rules.need`（41–48）：沒同意過一律 MUST——鍵對不上的後果是**同意過的人被擋**，不是放行。
- `audit.account_rows`（30–42）照 `_get` 同一套算鍵（password 列的 subject，或記號、沒 password 列 → `id:<n>`）；`must_rows` 經 `rules.need`。
- identity 包 `routes.py`：建角色 `character()`（359–399）`create_without_password` 回 `id:<n>`，`terms_base.record(key)`（388）記在 `id:<n>`，
  `_start_session(key)`（398）；第三方登入（333–339）、驗證碼登入（505）的鍵來自 `login_key`（有密碼回小寫帳號名、否則 `id:<n>`，accounts 251–265）；
  綁定 `code_bound`（512–541）、`bound_back`（224–）、解綁 `unbind`（618–645）、補設密碼 `password_set`（654–676，鍵不變 `id:<n>`）、
  管理者解綁 `admin.unbind`（admin.py 75）都不改鍵。

## 二、記同意與查同意的鍵（第二段每條測試的說明寫它守哪一列）

| 列 | 路 | 記在 / 查用的鍵 | 對得上？ |
|---|---|---|---|
| R1 | 殼 `/api/register`（identity 關或開） | 記 `normalize(login)` | — |
| R2 | identity `/api/identity/character`（第三方、驗證碼新帳號） | 記 `id:<n>` | — |
| R3 | `/api/terms/agree`（同意層、改版頁） | 記 session 的鍵 | 自己記自己查，一定對得上 |
| Q1 | `/api/login` 密碼登入、identity 關 | session＝`normalize(login)` | 對 R1 |
| Q2 | `/api/login` 密碼登入、identity 開 | session＝`get(normalize(login)).key`：老帳號＝小寫名、補設過密碼＝`id:<n>` | 對 R1、R2 |
| Q3 | 第三方、驗證碼登入（identity 開） | session＝`login_key`：有密碼＝小寫名、沒有＝`id:<n>` | 對 R1、R2 |
| Q4 | 建角色那一步直接開 session | session＝`id:<n>` | 對 R2 |
| K1 | 綁定、解綁（本人、管理者）、補設密碼 | 鍵不變 | 不影響 |
| A1 | `audit.must_rows`（`scripts/list_terms_must.py`） | 照 `_get` 同一套算鍵 | 應與伺服器擋的同一批 |

**讀程式的結論：identity 開著時對得上**（第二段用測試證明）。AG 波擔心的「session 是 `id:<n>`、註冊記登入名」只會發生在
同一個帳號兩邊算法不同；有 password 列的帳號 identity 開著時 session 也是小寫名（`_get` 第 157 行），沒有 password 列的帳號只能從 R2 開、記的就是 `id:<n>`。

**讀到的一個對不上（不在這一批「identity 開著」的範圍）**：補設過密碼的帳號（R2 開、有記號列）在 identity **打開過又關掉**之後用密碼登入，
Q1 的 session 是小寫名、同意記在 `id:<n>` → 被當成沒同意過、會改東西的請求 403。會自己好：同意層照 session 的鍵問、按同意記在小寫名，之後放行；
只是那一批人要再按一次。要根治得在殼 `_start_session` 不看開關都轉鍵，或條款包查的時候用 `AccountStore.get(key).key` 轉一次（後者在條款包裡、
但會動 identity 關著的路，雖然關著沒有記號列的帳號結果一樣）。**保守：這一批不修**，第二段寫一條測試釘住現況（403 → 按同意 → 放行），寫進 leftovers 交 PM 問要不要修。
