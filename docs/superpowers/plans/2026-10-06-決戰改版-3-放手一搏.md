# 決戰改版 3：放手一搏 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 放手一搏改成平均跟固定招打平、差別只在起伏大。模型一次給兩樣：成功率，以及這句話算強攻、固守還是奇襲。系統照那一招的份量與剋制擲骰：成了，份量乘上倍數（2 − p）÷ p（最高 ×10）；敗了，從自己這邊倒扣一份。每回合都能寫。成功的寫進戰報頭條，每回合最多 3 則。評分移到行動鎖外。

**Architecture:**
- 放手一搏在 `resolve_round` 裡跟固定招一起合成。它的招（模型分的）算進自己這邊的出招比例。份量 ＝ 那一招的份量 × 氣血狀態 × 剋制係數。成了，乘倍數加進力量；敗了，從力量扣掉一份，一邊的力量最低 0。
- 舊的 `FreeTextGamble`（直接推戰局的公式）拿掉，數字併進 `Config.battle`。
- 評分照專案的三段做法（同 `server.answer_event`）：
  - A：鎖內開單（`Game.battle_text_request`）。
  - B：鎖外問模型（`battle_instance.assess_gamble`，走 `server.model_call`）。
  - C：鎖內確認還是同一回合，才送出（`Game.submit_battle_custom_action(..., judged=, request=)`）。

**Tech Stack:** Python 3、pydantic（`tianxia/`）、FastAPI（`server.py`）、pytest。網頁不用改，輸入框照舊打 `/api/do/battle_text`。

**Spec:** `docs/superpowers/specs/2026-10-03-戰鬥系統-design.md` 3.5。數字都是【預設】（企劃者 2026-10-06：照預設做、測完再調）。

## Global Constraints

- **次數**：每回合都能寫（3.5「次數不限」）。機器人、作戰方針、AI 代挑都不替人放手一搏（照舊）。
- **模型給什麼**：一次給兩樣，成功率（0～100）與招式分類（強攻、固守、奇襲之一）。模型只給機率與分類；擲骰、倍數、推力、扣血全由系統算。
- **評不出來**：叫不動、太慢、格式不對時，成功率 40（`DEFAULT_FREE_TEXT_SUCCESS_RATE`，跟隨口應對同一個），分類空著。分類空著或不是三招之一，結算時當作這個人最拿手的招（份量最高的那招）。
- **份量**：這個人那一招的份量（計畫一的 `scores`）× 氣血狀態 × 剋制係數。跟固定招同一套；它的招也算進自己這邊的出招比例。
- **成了**：份量 × 倍數，加進自己這邊的力量。倍數 ＝（2 − p）÷ p，p ＝ 成功率 ÷ 100，**最高 ×10**（`gamble_cap`）。成功率 0 也是 ×10。
- **敗了**：從自己這邊的力量倒扣一份（−份量）。一邊的力量最低算 0。
- **人數**：放手一搏的人算進這一邊的人數（√人數 那一項）。
- **氣血**：
  - 成了 −10（`gamble_win_damage`）。
  - 敗了 −（20 ＋ 3 ×（100 − 成功率））（`gamble_fail_base`、`gamble_fail_per`）。例：50% 敗了 −170。
  - 放手一搏不吃強攻的威力抵銷，也不乘（2 − 係數）。
- **戰報頭條**：
  - 只寫這一回合成了的放手一搏。倍數高的優先，最多 3 則（`headlines`）。
  - 頭條放在這一回合訊息的最前面：「某某「……」得手！（×9.0）」。
  - 沒進頭條的人，只在自己的「你上一回合」看到結果。
- **評分在鎖外（三段）**：C 段確認還是同一場、同一回合、這個人這回合還沒出手，才送出。
- 數字全由規則引擎決定，全部【預設】，放在 `Config.battle`。
- 測試：`.venv/Scripts/python.exe -m pytest -q`。commit 照專案慣例（明列路徑）；push 照 PM 的規矩。

## Review Focus

1. **平均跟固定招打平**：成功率 p 的放手一搏，成了乘（2 − p）÷ p、敗了倒扣一份，期望值剛好等於一份。成功率低於約 18% 會被封頂，平均就比固定招差。→ Task 1 `test_the_expected_share_matches_a_fixed_move`。
2. **一邊全敗**：力量扣到負的要夾 0，推力不能超過 10，正負號不能算反。→ Task 1 `test_a_side_cannot_go_below_zero`。
3. **成功率 0 或 100**：0 不能除以零（給 ×10），100 是 ×1 而且一定成。→ Task 1 `test_extreme_rates`。
4. **評完回來，已經換回合，或自己已經按了別的招**：不送出、不扣任何東西，說一句話。→ Task 2 `test_a_judged_gamble_for_a_past_round_is_not_sent`、`test_no_request_when_the_round_is_already_played`。
5. **模型回了怪分類或怪數字**：分類不認得就當最拿手的招；成功率夾在 0～100。→ Task 2 `test_a_strange_category_falls_back_to_the_best_move`。

```python
def gamble_multiplier(tuning: BattleTuning, rate: int) -> float:
    """放手一搏成了的倍數（戰鬥系統 3.5）：（2 − p）÷ p，p ＝ 成功率 ÷ 100，封頂 gamble_cap；成功率 0 也是封頂。
    敗了倒扣一份，所以平均剛好是一份，跟出固定招打平，差在起伏。"""
    p = max(0, min(100, rate)) / 100
    return tuning.gamble_cap if p <= 0 else min(tuning.gamble_cap, (2 - p) / p)
```

```python
class GambleJudgment(BaseModel):
    success_rate: int = DEFAULT_FREE_TEXT_SUCCESS_RATE
    move: str = ""  # 強攻、固守、奇襲之一
    reasoning: str = ""


GAMBLE_PROMPT = (
    "你是漢末兩軍交戰的戰場判定系統，評估玩家描述的行動合理的成功機率，並判斷它算哪一招；不是故事寫手，"
    "也不決定最後成不成功。三招：強攻（正面硬打、衝陣）、固守（守住陣腳、穩住）、奇襲（繞後、夜襲、火攻、偷襲、計謀）。"
    "請給出 0~100 的整數 success_rate、move（強攻、固守、奇襲三者之一）與一句話 reasoning。"
)


def assess_gamble(
    client: OllamaClient | None, act_title: str, act_text: str, faction_name: str, text: str,
) -> tuple[int, str | None]:
    """放手一搏的評分（戰鬥系統 3.5）：模型一次給成功率與招式分類，一個是擲骰的機率、一個是合成用的招，數字都由系統算。
    叫不動、格式不對：(DEFAULT_FREE_TEXT_SUCCESS_RATE, None)；分類不是三招之一：None（結算時當最拿手的招）。
    伺服器在行動鎖外呼叫（server.battle_text）；腳本與測試沒在鎖外評過時，由 Game.submit_battle_custom_action 在鎖內用短逾時的複本呼叫。"""
    if client is None:
        return DEFAULT_FREE_TEXT_SUCCESS_RATE, None
    messages = [
        {"role": "system", "content": GAMBLE_PROMPT},
        {"role": "user", "content": (
            f"戰場情境：【{act_title}】{act_text}\n玩家所屬：{faction_name}\n"
            f"玩家的行動：「{text}」\n請給出 success_rate、move、reasoning。"
        )},
    ]
    try:
        result = client.chat_structured(messages, GambleJudgment, temperature=0.7, required_fields=["success_rate"])
    except Exception:  # noqa: BLE001 —— 評不到就照保底，不讓這一步卡住出手
        return DEFAULT_FREE_TEXT_SUCCESS_RATE, None
    if result is None:
        return DEFAULT_FREE_TEXT_SUCCESS_RATE, None
    move = (result.move or "").strip()
    return max(0, min(100, result.success_rate)), (move if move in MOVES else None)
```

```python
    """決戰的放手一搏（戰鬥系統 3.5），跟 answer_event 一樣分三段：
      A（鎖內、很快）同步時間，問引擎這句話現在能不能送；能就拿到單子，同步的結果照樣存起來；
```

## 計畫裡的決定（設計沒寫死、這份替實作選的）

| 題目 | 這份的做法 | 理由 |
|---|---|---|
| 放手一搏算不算進出招比例 | 算，照模型分的招 | 設計 3.5「一樣吃 3.4 的剋制與適性」。它也是一招，對面該看得到 |
| 分類評不出來 | 當這個人最拿手的招 | 評不出來不該再罰一次：成功率已經是偏低的 40 |
| 敗了的訊息 | 不進戰報，只在「你上一回合」 | 千人的戰場只留頭條（3.5），不然每回合上百句 |
| 評不到的成功率 | 沿用 `DEFAULT_FREE_TEXT_SUCCESS_RATE`（40），不另外放進 `BattleTuning` | 跟隨口應對同一個保底，少一個要調的數字 |
| 評分放哪 | 移到行動鎖外（三段），B 段走 `model_call` | 次數不限之後，鎖內評分會讓全服跟著等。Infra 佇列計畫原本把它列為鎖內小呼叫，請 PM 轉告 |

## 不在這份

- 連環（放手一搏擲兩次取好的）：決戰改版四（功效進決戰）。
- 放手一搏的個人貢獻照倍數記：決戰改版六（參戰誘因）。
