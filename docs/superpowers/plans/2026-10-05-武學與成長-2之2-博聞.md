# 武學與成長 2 之 2：博聞 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 加第五項屬性「博聞」：跟另外四項一樣開局 5、升級給點自己分、最高 15；它管武學與意境的持有上限，比基準每多一點 +2 格。升級給的格子同時從每 5 級 +5 格改成 +3 格。

**Architecture:** 博聞的鍵是 `"lore"`，加進 `team.COMBAT_STATS`（屬性清單）、`models.STATS`、`Config.start_stats`、`Config.stat_names`。加點（`allocate`）、狀態列（`status_data` 的 `attrs`）、加點按鈕下面那行說明（`stat_uses`／`stat_uses_note`）、機器人分點、事件加屬性的上限都照 `COMBAT_STATS` 走，所以會自動多一項。顯示名只寫在 `Config.stat_names` 一處。舊存檔沒有這一項時，在 `Game._drop_stale_references` 照開局的數字補上，不升資料庫版本。持有上限改成 `library.holding_cap(content, level, lore)`，另加 `library.cap_of(state, content)` 給呼叫端用。

**Tech Stack:** Python 3／pydantic（`tianxia/` 規則引擎）、FastAPI（`server.py`）、原生 JavaScript（`web/app.js`，這份不用改）、pytest。

**Spec:** `docs/superpowers/specs/2026-10-05-武學與成長-design.md` 6.3（第五項屬性「博聞」）、4.5（持有上限）。

**開工條件：** 照 main `7eaa7fe`（計畫二已併入）寫。專職開發接著計畫二做這份，跟計畫三平行；PM 的目標是趕上週末測試。

**執行方式：** 子代理逐步做（superpowers:subagent-driven-development：每個 Task 一個新的子代理實作、另一個子代理審過才做下一個，最後整條分支再審一次）。

## Global Constraints

- 鍵 `"lore"`，暫名「博聞」。**顯示名只寫在 `Config.stat_names`**；程式其他地方一律用鍵，用途說明寫在 `skillview.STAT_USES`（照鍵），之後改名只動 `stat_names` 一處。
- 屬性清單沿用計畫二的名字 `team.COMBAT_STATS`：五項，順序 `("str", "agi", "con", "wis", "lore")`，狀態列、＋鈕、說明那一行都照這個順序。
- 博聞開局 5、上限 `Config.stat_cap`（15），跟另外四項一樣；點數照舊每級 `stat_points_per_level`（1）。
- 持有上限 ＝ `holding_cap_base`（50）＋（等級 // `holding_cap_levels`（5））×`holding_cap_step`（**3**）＋ max(0, 博聞 − 5)×`holding_per_lore_point`（**2**）。一季最多 88 格。
- 博聞**不進戰力**：不吃 `stat_bonus` 的任何加成，臂力、根骨、身法、悟性的效果都不動。
- 事件檢定（`Check.stat`）、隨口應對（`FreeTextChoice.stat`）、伏筆最後一步（`FsCheck.stat`）都能指定 `"lore"`；`check_voice.json` 有 `"default"` 那一句，不用補內容。
- 舊存檔沒有 `"lore"` 時當開局的數字（5）；**不升 `SCHEMA_VERSION`**。
- 同伴的屬性內容（`characters.json` 的 `stats`）不用補博聞，讀不到就當 5。
- `tianxia/` 不 import 網頁框架；數字全由規則引擎決定。
- 測試：`.venv/Scripts/python.exe -m pytest -q`。commit 照專案慣例（明列路徑）；push 照 PM 的規矩。

## Review Focus

1. **舊存檔沒有博聞**：讀進來、看狀態列、按＋博聞、走考博聞的檢定都不能當機，博聞是 5。→ Task 1 `test_an_old_save_without_lore_gets_the_starting_value`。
2. **博聞被事件扣到 5 以下**：持有上限不能比「50＋等級給的格子」還少。→ Task 2 `test_lore_below_the_base_takes_no_slots_away`。
3. **博聞已經 15**：＋鈕灰掉（照 `stat_cap`）、機器人不再挑它、事件再給博聞也不超過 15。→ Task 1 `test_lore_is_capped_like_the_other_stats`、`test_the_bot_puts_points_into_lore_when_the_rest_are_full`。
4. **博聞掉下來、持有已經超過上限**：照 4.5，悟得到的意境照收，但在熔回上限以內之前不能合成、合併。→ Task 2 `test_losing_lore_can_leave_you_over_the_cap`。
5. **同伴**：事件檢定只看本人，但 `team.member_stats` 對同伴也照 `COMBAT_STATS` 列五項，同伴的內容沒有博聞時不能 KeyError。→ Task 1 `test_a_companion_without_lore_reads_as_the_base`。

```python
def holding_cap(content: Content, level: int, lore: float) -> int:
    """武學與意境合計最多幾個（設計 4.5、6.3）：基本 50，每升 5 級多 3 格，博聞比基準（5）每多一點多 2 格；
    博聞少於基準不扣格（被事件扣了也不會比基本加等級的少）。"""
    cfg = content.config
    from_lore = max(0, int(lore) - team.BASE_STAT) * cfg.holding_per_lore_point
    return cfg.holding_cap_base + (level // cfg.holding_cap_levels) * cfg.holding_cap_step + from_lore


def cap_of(state: GameState, content: Content) -> int:
    """這個人現在的持有上限：照自己的等級與博聞。"""
    p = state.player
    return holding_cap(content, p.member.level, p.stats.get(team.LORE, team.BASE_STAT))
```

## 計畫裡的決定（設計沒寫死、這份替實作選的）

| 題目 | 這份的做法 | 理由 |
|---|---|---|
| 鍵 | `"lore"` | 跟 `str`／`agi`／`con`／`wis` 一樣短；顯示名是暫名，鍵不跟著改 |
| 博聞進不進 `COMBAT_STATS` | 進（五項） | PM 要求沿用計畫二的名字；加點、狀態列、說明、機器人、事件加屬性的上限、檢定都照這份走，一處加就全部跟上。戰力加成是各自讀 `str`／`con`／`agi`／`wis`，不會吃到博聞 |
| 舊存檔 | `Game._drop_stale_references` 照 `start_stats` 補 | 遊戲建構時與伺服器每次進鎖都會跑；存檔是 JSON，多一個鍵不用升資料庫版本 |
| 同伴 | 內容不用補，讀不到當 5 | 檢定只看本人（joy #11～#17），同伴的博聞沒有用處 |
| 持有上限的介面 | `holding_cap(content, level, lore)` 三個參數都要給，另加 `cap_of(state, content)` | 不給預設值，免得哪個呼叫端忘了傳博聞還照樣跑 |
| 博聞低於 5 | 不扣格 | 事件扣屬性不該讓持有上限低於基本加等級 |

## 不在這份

- 考博聞的事件檢定：程式這份就認得 `"lore"`；內容由 Joy 寫，PM 等這份做好再通知。
- 改名：只動 `Config.stat_names["lore"]`。
