# 第一季濃縮版 實作計畫

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 讓企劃者和 joy 用一個週末（約 60 小時）從開季玩到季末結局，完整體驗第一季「黃巾之亂」的陣營玩法。

**Architecture:**
- **戰況**：三條戰線做成三條大勢線（`yingru`、`nanyang`、`jizhou`），黃巾聲勢改成三條的加權值，再加一條豪強割據（`geju`）。既有的大勢線機制（`change_trend`、`Effect.trend`、`Condition.trend_min/max`、地圖的大區標示）整套沿用。
- **時間**：引擎的時鐘照舊跑現實時間。另外加一個「季曆」（第幾週、週幾、幾點），時刻表、軍令、伏筆的時間窗都看季曆。
- **新狀態放哪**：全部當作有預設值的欄位，放進 `WorldState`（共用賽季）與 `PlayerState`（角色存檔），不加資料表、不升資料庫版本。
- **新內容放哪**：全部放進 `content/` 的新 JSON，載入時由 `content.validate` 交叉檢查。

**Tech Stack:** Python 3.14、pydantic、FastAPI（`server.py`）、SQLite（`tianxia/database.py`）、原生 JavaScript（`web/app.js`，沒有建置步驟）、pytest。

## Global Constraints

- `tianxia/` 是純規則引擎，不得 import 任何網頁框架；`engine.Game` 是唯一對外門面（CLAUDE.md「架構」）。
- 引擎不讀電腦時鐘：時間一律由 `Game.sync(now)` 或明確的 `now` 參數傳入（CLAUDE.md「原則」）。
- 數值全部由規則引擎決定，執行時不靠 LLM 算數字；軍令的發布文字可以交給 LLM 潤色，失敗就用模板原文（軍令文件第二節）。
- 資料庫是唯一的真實來源。每次「補算時間＋動作＋存檔」包在 `WorldStateStore.action_lock()` 裡；`WorldStateStore.mutate` 不能巢狀（CLAUDE.md「原則」、`world_state.py`）。
- 伺服器假人跟真人完全一樣、看不出來：任何畫面、榜單、戰報、軍令排名、公告都不能透露誰是假人（CLAUDE.md「原則」）。
- 新欄位一律有預設值，舊存檔直接讀得進來；不改資料表、不升 `SCHEMA_VERSION`（`database.py`）。真的要加表，先回報 Infra。
- 內容（`content/*.json`）由 `tianxia/content.py::validate` 交叉檢查；新的內容檔都要加檢查（第一季設計第十八節）。
- **鎖定不能露出來**：關鍵伏筆鎖定時不發任何傳聞，畫面、江湖紀錄、決戰的起點、推力與選項都不能因為有沒有鎖定而不同；只有大事當天的公告揭曉（伏筆文件 2.4、戰鬥系統 4.3）。
- **豪強是第三方**：豪強的伏筆不跟官軍、黃巾互斥，大事當天不論誰贏都拿到自己的效果（伏筆文件 2.6）。
- **散人**：可以推大勢，但不記貢獻、不能接軍令、不能做伏筆、決戰只能觀戰（第一季設計 5.1、第九節，軍令文件第二節）。
- 畫面文字用繁體中文；用語照企劃者 2026-10-04 的改名：「遊歷」（id 仍是 `act:train`）、「交友」（id 仍是 `act:socialize`）。
- 每個任務做完都要通過全套測試：`C:/Ray/專案/天下大勢/.venv/Scripts/python.exe -m pytest -q -p no:cacheprovider`。整季模擬的 `TIANXIA_DB` 要指到 repo 外的暫存檔。
- 不碰 `saves/`、`.local/`；不在預設資料庫或 7861 埠上開 `server.py`、`run_bots.py`。

## Review Focus

計畫裡每一個任務的測試都沒直接打到、但最可能害到人的五件事。下面每一條的測試已經加進負責那段程式的任務：

1. **一次跨過好幾件大事**：管理者「跳到下一件大事」或快轉，或者伺服器停了一陣子再補算時間，都可能一次跨過好幾件大事（其中可能有決戰）。這時要照週次逐件結算，每件只結算一次，決戰不能被跳過、也不能開兩場（T2、T8、T10 各有一條）。
2. **排定的決戰時間到了，卻開不成或沒人打**：例如上一場還沒打完、或那個大區沒人。時刻表照樣要拿到一個結果，季不能卡住：沒人打就照鎖定或擲骰收場（T8）。
3. **鎖定外洩**：鎖定之後，另一個玩家的 `main_view`、傳聞、江湖紀錄、決戰的起點與選項都要跟沒鎖定時一模一樣（T7、T8）。
4. **大勢人物接位接到底**：例如彭脫也退場、戰線上沒有黃巾的大勢人物了。軍令的 {主將}、晉升召見、伏筆的出面人物都要有退路，不能丟例外（T4、T5、T6）。
5. **季在別的事進行到一半時結束**：決定性勝利或季末時間到了的那一刻，可能還有決戰在打、或有大事還沒結算。結局只算一次，決戰清掉，參戰者照 W13 的補送收到戰報，季的階段確實變成休季（T9）。

**資料**
- `PlayerState`：

  - `contrib_weeks: dict[int, int] = {}`：每週的貢獻；

**介面（Produces）**
- `push.buffered(delta: float, n: int) -> float` ＝ `delta / sqrt(max(1, n))`。
- `push.active_count(state, faction: str, now_time: float, window_seconds: float) -> int`：最少 1。

## 五、兩個真人、不開假人時，戰況靠什麼動（預設值與理由）

**要達成的感覺**：
- 兩個人都不在線時，三條戰線緩慢、看得出在起伏，不會靜止，也不會自己跑到一邊；
- 有人在線、專心推一條戰線時，一節課（一個真實小時）看得到十來點的變化；
- 大事與決戰帶來大跳。

**時間單位**（第六節）：1 週＝真實 5 小時，1 曆日≈真實 43 分鐘，1 曆時≈真實 1.8 分鐘。

| 項目 | 預設 | 理由 |
|---|---|---|
| 玩家一次遊歷打贏 | 推所在戰線 1～2 點（沿用各地點的 `train_trend`） | 已經調過、有測試保護；兩人時人數緩衝是 1，等於全額 |
| 第 1 階守勢行動 | 1 點 | 跟遊歷同級，給不想打的人一條路 |
| 每人每曆日每條線的上限 | **10 點** | 體力 150、每 3 分鐘回 1，滿體力一口氣做 15 次也只推得到十來點；上限只卡住滿體力的爆發，平常碰不到。一週最多 70 點，實際會被體力卡在 30～40 點 |
| 大勢人物每曆日行動 | 主將 1 次、副將 0.5 次，每次 1 點；戰線偏向對方 ≥15 時加倍 | 每條戰線兩方各一兩位，平常互相抵銷、走走停停，大約每 15～20 分鐘看得到某條線跳一點。偏太多時拉回來，人不在時戰線會慢慢回到中段，保持「還有得打」（攻城軍令 30～70、伏筆最後一步 40～60 都要中段） |
| 豪強割據 | 每條亂局戰線每曆日 +1；三條都穩時每曆日 −1 | 起始 10，三條都在中段時一週 +21，季末大約 50～70，三方態勢都有機會；決定性的 85 要豪強真的在推 |
| 時刻表大事 | 結算文件定的：擲骰成了往成的一方偏 8、沒成往另一方偏 5；長社、宛城大勝 15、險勝 8；廣宗 20、10 | 一件大事大約是一個人專心推半週到一週的量，大事比日常重要 |

| **軍令陣營總額度** | `max(4, ceil(模板量 × server_max_players / 3000))`；週末試玩設 `server_max_players = 2`，所以**每道都是 4 次** | 一個人一週全力大約做 25 次動作，三道軍令 12 次大約是一半，有餘裕做別的。軍令文件寫最少 5，兩人時 15 次太滿，所以這一版降到 4（待決 3）。QA 的假人模擬照 30 人上限算，攻城是 12 |
| **伏筆需求量** | 伏筆文件 2.8 多一檔：**未滿 10 人，係數 0.2**。囤糧 24→5、情誼 30→6、葦束 3→1；片段機率 5%÷0.2＝25% | 0.3 那一檔還是照「30 人互相轉告」算的；兩個人沒有別人轉告，片段要自己聽到，在大區做 15 次左右就聽得齊四片 |
| 人數緩衝的活躍時窗 | 一曆日 | 兩人時不影響（各陣營 1 人）；假人模擬裡讓「剛推過的人」才算數 |

## 六、原型的 `season_days` 14 跟 12 週壓成約 60 小時怎麼對應

**問題**：現在 `time_scale` 會連體力回復、走路、打坐、閉關一起壓縮（調查：`sqlite_world.py:329`、`engine.py:236`，`Journey.arrive_at` 也在季的時鐘上）。

如果直接把 `time_scale` 調到 33.6，讓 84 個遊戲日塞進 60 小時，會連帶出問題：
- 體力每 5 秒回 1 點；
- 走 6 分鐘的路變成 11 秒；
- 決戰的回合（真實秒）反而變得相對很慢。

**做法：兩個時鐘，各管各的。**

1. **世界時鐘照舊**：`time_scale` 維持 1，`WorldState.time` 就是開季以來的真實秒（快轉另計）。
   - 體力、走路、打坐、決戰的集結與回合、對話每日 3 輪、新手福利、福緣的日數這些既有規則，一個字都不動，照真實時間跑。
2. **新增季曆**（T2）：
   - `季曆秒 ＝ 世界秒 × cal_scale`，`cal_scale ＝ season_weeks × 7 ÷ season_days`。
   - `season_days` 的意思不變，就是「這一季在世界時鐘上有幾天」：
     - 濃縮版設 **2.5**（60 小時）、`season_weeks` 12，`cal_scale` 是 33.6；
     - 原型的 14 天就是 `cal_scale` 6，兩種只差設定檔，同一套程式。
3. **第一季的規則一律看季曆**：時刻表的週次、每週一發軍令與期限、伏筆最後一步的「大事前 7 天」（＝前一週＝真實 5 小時）、長社「夜裡（子時到寅時）」、每曆日的推動上限、人物的每曆日推動、割據的每曆日漲落。
   - 「夜裡」因此每 43 分鐘有約 11 分鐘，兩個人不用熬夜；
   - 「一週」是 5 小時，一個晚上大約玩一兩週。
4. **畫面**：狀態列改寫「第 3 週・週二 21:40」，旁邊是下一件大事的倒數（真實時間）。三場大戲與季末照管理者排的真實時間，畫面上換算成倒數。
5. **管理者快轉與跳到下一件大事**：推進的是世界時鐘，季曆跟著走；排好的決戰時間存成世界秒，所以快轉後在畫面上看起來提早了。這是「整個世界往前推」的直覺結果。

**排程的預設**：
- 一般大事在那一週的第 0 曆日，也就是週一凌晨（`TimetableEvent.day` 可以改）；
- 三場大戲預設在第 6、9、11 週的週四 20:00（季曆）；
- 季末在第 12 週結束（真實 60 小時整）。
- 管理者開季時改成兩個人約好的真實時間。
