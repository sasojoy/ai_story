## 零、一句話

傳國玉璽裂成七片。一季最多現世一片：第 9 週宛城之戰集結時擲 35%（綁哪一場與機率見 19.1 甲），中了就在勝方戰功前幾名裡抽一人得到。拿到的人帶著它一季一季玩下去，身上多一種小而獨特、不加威力的效果。

每場時刻表決戰開集結時，每一片有主的碎片各擲一次 7%，中了叫「璽動」。決戰照常打。打完之後，持有者那一方大勝就沒事；沒有大勝，就從對面戰功前幾名挑一人，跟持有者當著全服打一場照頭目戰規則的單挑。單挑之後引擎再擲一次，整場被奪最多 25%（這是上限，不是常態）。輸了只失去碎片，名望 +5（【預設】）。

**實際的數字**（9.2、9.4）：人多的伺服器一季只打得到兩場璽動的決戰，一片碎片一季被捲進璽動 13.5%；一季真的易手約 0.3%～2.3%（挑戰者每回合放手一搏時約 1.2%～1.9%）。一輪（七片湊齊，約 20 季）全服大約璽動 7 次、單挑約 5 場（持有者多半旁觀時約 7 場）、易手 0.15～0.9 次（持有者旁觀而且照新角色打時約 1.2 次）：照預設，多數的輪一次易手都看不到。鬆緊要企劃者選（19.1 乙）。

【玉璽一量表 2026-10-13，`scripts/measure_seal.py` 跑真的程式；上面那一段是設計時的估計】單挑係數的期望 E[g]（`--duel-mc`，PM 乙的 1.0／1.0／0.6）兩邊同強時只有 0.11～0.34（都在場不搏 0.12、都代打 0.25、一邊在場最多搏兩次 0.05～0.50），1.5 倍 0.44～0.82、3 倍 0.51～1.0：比設計 9.4 估的 0.64～0.72 低，強弱差一截才到；週末 5/5/5 五季宛城擲中現世 1 季（得主戰功第 2）；`--force-stir` 十一季（週末 5/5/5 三季、14 天兩季、1/1/0 六季）璽動 19 次，四檔 大勝 4、險勝 1、旁觀 4、大敗 7、保底 3（1/1/0 兩軍都沒人還站著），開單挑 11 場（58%），單挑 大勝 5、險勝 2、落敗 4，易手 0 次（照係數的期望約 1.1～1.6 次）；週末那一季第 10 週就決定性收季、廣宗沒開，實際只有兩場標了 seal 的決戰。換成 7%：一片一季被捲進 13.5%～19.6%、易手約 0.8%～1.6%；一輪約 20 季全服單挑約 5～8 場、易手約 0.6～1.1 次。1/1/0 只有一片有主時三次璽動開了兩場單挑（另一次保底）；兩個假人都有碎片時挑戰者只剩在大區旁觀的散人（一次補上）。量表給每個種子一份密鹽（沒有密鹽時每個種子擲得一樣）。強制璽動之外，週末 5/5/5 五季一次都沒有自然璽動（第一季拿到碎片的人有新主保護）。數字樣本小（十一季、十一場單挑），易手的比例照係數的期望寫，量到的 0 次跟期望不衝突（期望約 1.1～1.6 次時一次都沒中的機會約兩成到三成）。


七片都現世過之後（「湊齊」怎麼讀見 19.1 己），下一季是「天命之季」：三場決戰必定璽動，第 12 週開「天命之爭」大決戰，勝方得天命、改寫結局。再下一季七片散去，從頭再來。

## 二、全貌與名詞

```
未現世 ──（第 9 週宛城集結擲 35%；收場時勝方戰功前三名抽一人）──▶ 有主
有主 ──（第 6、9、11 週決戰開集結，每片 7%）──▶ 璽動：決戰照常打
     ├─ 持有者那一方大勝 ──▶ 懷璽不失
     └─ 其他結果 ──▶ 下戰書 180 秒 ──▶ 單挑 5 回合（全服觀戰）──▶ 再擲：25%×局勢×護璽×單挑
                                                             ├─ 中了 ──▶ 易主（碎片給挑戰者）
                                                             └─ 沒中 ──▶ 懷璽不失
有主 ──（換季時整季沒上線而且滿 14 天）──▶ 隱沒
七片都現世過 ──▶ 下一季是天命之季 ──▶ 第 12 週天命之爭 ──▶ 再下一季七片散去，第二輪從「未現世」開始
```

- **碎片**：七片，固定的 id 與名字（7.1），內容在新檔 `content/seal.json`。
- **持有者**：全服登記上寫的那個名號。一人最多一片。
- **現世**：一片「未現世」的碎片第一次有主。
- **璽動**：決戰開集結時，引擎擲中某一片有主的碎片。這一場打完要不要單挑，看持有者那一方打得怎樣。
- **奪璽單挑**：挑戰者對持有者，全服看得到。
- **易主**：單挑之後再擲中，碎片換到挑戰者手上。
- **隱沒**：持有者太久沒上線，碎片「不知所蹤」，不屬於任何人。
- **輪**：七片從散落到湊齊、天命之爭、再散去，叫一輪。
- **全服登記**：`SharedWorldState.seal`，是碎片歸屬的正本，跨季保存（第十三節）。
- **抄本**：角色身上 `PlayerState.heirloom` 那一件，同步時照登記重抄（7.4）。

## 三、碎片怎麼現世

### 3.1 為什麼不綁廣宗

整合版把現世綁在第 11 週廣宗決戰。量表（PM 2026-10-11，`seal_sim.py`）照實報：

- 週末設定 5/5/5，種子 1～30：30 季全部在「第 10 週・週一 00:00」以「群雄並起」（`s1_warlords`，scenario.json:119，割據 ≥85）收季，廣宗一次都沒開過。割據在第 3～8 週頂到 85（第 3 週 2 季、第 4 週 16 季、第 5 週 4 季、第 6 週 5 季、第 7 週 1 季、第 8 週 2 季；九成在第 6 週以前），第 10 週一到，`world.decisive_ending`（world.py:238-250，`decisive_from_week` 預設 10，models.py:1576）當下收季。
- 其他設定也一樣：14 天的季 3/3、10/10/10 3/3 都在同一刻收季；5/5/0 有 4/5 在第 10 週收季；1/1/0 有 3/5 打到廣宗。
- 對照組把 `decisive_from_week` 改成 13（不提前收季），廣宗 5/5 都打成。

所以綁廣宗等於人多的伺服器永遠不現世。要嘛改綁別場，要嘛把 `decisive_from_week` 往後挪；後者會改整個第一季的收季節奏，要企劃者決定（19.1 甲）。這份的【預設】是改綁宛城。

### 3.2 規則【預設】

- **時機**：第 9 週宛城之戰（時刻表 `wancheng`，甲、乙兩版都算；程式認的是時刻表上的標記 `seal: "emerge"`，不寫死 id，8.5）開集結的那一刻擲一次。地方在 `world._open_claimed`（world.py:471-490）的 `_open_battle` 之後：這裡拿得到 store，而且已經不在任何 mutate 裡（3.6、5.12 的寫入順序）。
- **條件**（全部成立才擲）：
  - 這一輪還有沒現世過的碎片；
  - 這一季還沒有碎片現世；
  - 這一季不是天命之季（天命之季改成喚回，8.2）；
  - 碎片開關開著（`Config.seal.enabled`），而且內容有 `content/seal.json`。測試內容沒有這個檔，等於關著。
- **機率**：`Config.seal.emerge_chance` 0.35。亂數另開一份 `random.Random(f"{密鹽}|{天機}|seal-emerge|{季別}")`，不碰季的 rng；天機在 `SharedWorldState.tianji`（world_state.py:81），密鹽見 5.13。
- **中了**：從這一輪還沒現世過的碎片裡，用同一份亂數挑一片，記在 `BattleInstance.seal_emerge`。集結公告多一句，另寫一則天下大事（3.4）。

### 3.3 誰拿到【預設】

- 收場時在 `Game._settle_showdown`（engine.py:2988）的 `_relabel` 之後決定。勝方讀 `result["side"]`，那是已經算進伏筆鎖定的結果。不能讀傳進來的 `battle`：它的 `outcome_side` 是改判之前的。
- **資格**：
  - 勝方的參戰者；
  - 自己出手（逾時被代選的不算，`BattleParticipant.acted_rounds`，battle_instance.py:66）滿 min(3, 這一場實際打了幾回合)。壓倒性收場可能 1～3 回合就打完，只寫「滿 3 回合」的話這種場次一個人都不合格（量表：長社 1/30 場打 2 回合、4/30 場打 3 回合）；
  - 不在序章；
  - 手上沒有碎片（一人一片）；
  - 不是這一場剛被挑去奪璽單挑的挑戰者。
  - 不看是不是假人，也不看新手期。
- **同一場收場要挑好幾個人時的順序**（宛城可能同時有璽動與現世；天命之季的長社、宛城還有喚回）：先挑挑戰者（4.6），再挑現世的得主，最後挑喚回的得主；後挑的排除前面已經挑中的人。理由：挑戰者的資格要「手上沒有碎片」，先把碎片發出去，同一個人就可能兩邊都被挑中、單挑開打時已經有一片。
- **怎麼挑**：合格的人照戰功（4.4）取前三名，再照戰功加權抽一位；戰功都是 0 就平均抽。亂數 `random.Random(f"{密鹽}|{天機}|seal-emerge|{戰報流水號}")`：不管是誰的請求觸發收場，結果都一樣。
- **落空**：沒有合格的人、保底收場（`end_without_fighters`，場上沒人）、季終收兵（unfinished），碎片就「又沉入地底」：這一季不算現世，那一片照舊未現世。
- **拿到的人**：
  - 收場當下只寫登記：登記成持有者，`since_season` 記這一季，所以這一季有新主保護（第六節）；`history` 記一筆 `emerge`。
  - 其餘都等他自己同步時由 `_deliver_seal_results` 補（5.9），不在收場時改他的存檔：抄本（7.4）、戰報與江湖紀錄一律補；**混元一氣只在補送當下還是同一季（`SealEvent.season` 等於目前的季）才給**，「還沒學過、持有也沒滿」也在那時才判（11.2）。跨季才回來的人，武學與名望都是新一季重來的，加在新角色身上不對，所以只補戰報與紀錄。

### 3.4 公告

字都交 joy 潤，下面是暫用的：

- 集結時：集結公告多一句，另寫一則天下大事（world 層）：「宛城地底異光隱現，傳言太平道藏下的一片玉璽碎片，將在此役現世。」
- 收場有人得到：天下大事與江湖史各一句，具名：「某某在宛城陣前拾得傳國玉璽的一角——『雲篆』。」
- 落空：「宛城的異光又沉入了地底。」只寫天下大事，不寫江湖史。

### 3.5 哪一片先出

這一輪還沒現世過的碎片裡照亂數挑。隱沒的碎片在一般季不回來，等天命之季喚回（8.2）。舊的跨季紀錄 `jade_seal_fragments` 不算在七片裡（11.5）。

### 3.6 頻率

- 量表裡宛城每季都打成（週末 5/5/5 30/30），勝方每季都有合格的人（照 min(3, 實打回合) 30/30；只看「滿 3 回合」也是 30/30）。所以人多的伺服器一季現世 35%，**65% 的季看不到碎片**，對上企劃者說的「也可能看不到一片」。
- 七片平均約 7÷0.35＝20 季湊齊，對上二十季大綱。換成現實時間：週末設定一個週末開一季的話約 5 個月；14 天的季中間有休季，約 9～11 個月（整合版估的）。
- 小伺服器比較少：1/1/0 的宛城勝方 5 季裡只有 3 季有合格的人，一季約 21%。週末試玩人數上限 2、不開假人，幾乎湊不到人（15.3），驗收要靠管理者工具（第十二節）。
- 第一季規則關著的季（`rules.season_one` 是假）沒有時刻表決戰，所以不現世、也不璽動，碎片只有效果、照樣可能隱沒（19.2 第 9 條）。

## 四、璽動

### 4.1 什麼時候擲【預設】

- 第 6 週長社火攻（`changshe_fire`）、第 9 週宛城（`wancheng`）、第 11 週廣宗（`guangzong`）開集結的那一刻，在 `world._open_claimed` 的 `_open_battle` 之後擲，宛城排在現世那一擲後面。哪幾場算，看時刻表那一件的標記（`seal: "stir"` 或 `"emerge"`，8.5），不寫死 id。
- 每一片「有主、沒被保護」（4.2）的碎片各擲一次 `Config.seal.stir_chance` 0.07（每場、每片各擲，見總表）。亂數 `random.Random(f"{密鹽}|{天機}|seal-stir|{event_id}|{碎片 id}")`。
- 一場決戰最多牽動一片。擲中好幾片時，用 `random.Random(f"{密鹽}|{天機}|seal-stir|{event_id}")` 從擲中的裡面挑一片，其餘這一場不算動過。
- 從沒開成、照起點判的決戰（`world.settle_waiting_showdowns`，world.py:367）沒有集結，不擲。

### 4.2 不擲的情況

- 碎片是這一季才到手的（新主保護：`since_season` 等於這一季。現世的、這一季剛奪來的都算）；
- 這一片這一季已經動過（`stirred_season` 等於這一季）；
- 全服這一季已經動了 `Config.seal.season_stir_cap` 2 次；
- 天命之季這三條換成第八節的規則。

**持有者躲不掉**：

1. 不必他同意，也不必他在線（第五節的代打）。
2. 換不下、藏不了：歸屬看全服登記，不看身上（7.3）。
3. 叛投、投靠、臨時投效都改不了「對面是誰」：持有者站哪一方、拿來比「不同陣營」的陣營，都在璽動那一刻快照進決戰（4.3），之後不再讀投靠名冊。叛投只擋名字在決戰陣上的人（`defection.enlisted`，defection.py:21-25），持有者不一定參戰；集結 1800 秒加最多 9×300 秒（content/battles.json:11-12），他有時間叛投。不快照的話，他叛到挑戰者那一方的陣營，`choose()` 收尾的 `_record_faction`（engine.py:1402、2743-2748）當下就改了名冊，對面每個人都變成「同陣營」被濾掉，結果是「對面無人能上前」；散人持有者更簡單，臨時投效到快贏的那一方就不必單挑。所以：快照是散人，或璽動之後陣營變了（投靠、叛投），一律照旁觀那一列處理（4.5），而且不套同陣營過濾。叛投本身照舊准（不另加擋），因為快照之後叛投已經躲不掉，只會讓自己算旁觀。
4. 晚點上線躲不掉：這一季還沒上線過也照打，照新角色的威力（5.3，企劃者 10/11 第 3 件）。換季會清掉陣營（engine.py:486 的註解），投靠名冊也照季分（sqlite_world.py:568-574 的 `faction_of` 只查這一季的 `faction_rolls`），所以他在璽動那一刻一定是散人，算旁觀：每次璽動都打、局勢係數 0.7。
5. 新手期不保護持有者：換季後還沒同步過的人 `joined_at` 是 None，`roster.newbie`（roster.py:111）一律當他剛加入。拿新手期擋璽動的話，「晚點上線」的漏洞又打開了。

### 4.3 公告與快照

- 擲中時用一次 `world.mutate` 一起寫兩件事：登記上那一片記 `stirred_season`；季的天下大事記一則「此役牽動某某懷中的『雲篆』」（具名、world 層，字待 joy 潤）。另外用 `mutate_battle` 在 `BattleInstance` 快照：
  - `seal_shard`：哪一片；
  - `seal_holder`：持有者的名號；
  - `seal_holder_faction`：持有者這一刻在投靠名冊上的陣營（`WorldStateStore.faction_of`，sqlite_world.py:568），不讀他存檔裡的 `p.faction`（這一季沒上線的人，存檔裡還是上一季的舊陣營）。散人、這一季還沒上線過的人都是 None；
  - `seal_holder_side`：`seal_holder_faction` 是交戰兩方之一就記那一方，否則記 None（旁觀）。
  - 之後挑挑戰者、判持有者算哪一方，一律只讀這兩欄快照，不再讀投靠名冊（4.5、4.6）。
- 持有者的江湖頁卡片（第十節）寫「此役牽動你懷中的『雲篆』」與開打時刻（`Game.stamp`），不寫機率。
- 決戰畫面、集結公告都多一句同樣的話，讓參戰的人知道打完可能有單挑。
- **讓一般玩家有目標**（企劃者要「讓大部分人集合參與，最後才是跟持有者比拚」）：被璽動的那一場，決戰畫面每回合結算後，對「此刻在自己這一邊合格的人裡戰功排前三」的參戰者多一句「你此役戰功居前；懷璽之人那一方若沒能大勝，你可能被推上陣前」（不露數字、不露名次；持有者本人與快照陣營跟持有者相同的人不顯示）。哪一邊會是「對面」要到收場才知道，所以兩邊合格的前三名都提示。收場挑出挑戰者時，下戰書的公告寫他的名號與「此役戰功居前」。

### 4.4 決戰照常打，另外記個人戰功【預設】

- 決戰本身一個字都不改：照常集結、照常打、照常發軍餉。
- 現在沒有能直接排名的量：
  - `acted_rounds` 打滿的人都是 9；
  - `led_rounds` 一回合只記帶頭的那一個人（battle_instance.py:858-876）；
  - 放手一搏的推進只按陣營加總（688 行的 `gambles[p.faction]`）；
  - `hurt_dealt` 只有點名過別人的人有。
- 所以 `BattleParticipant`（battle_instance.py:46-77）加 `merit: float = 0.0`，存在 battles.data 的 JSON 裡，不動資料表（同 `third_gain` 的寫法）。`resolve_round`（570-777）算完推力（741 行）之後累加三項：
  - (a) 固定招：這一回合的推力往 p 那一邊時，`merit += |round(push)| × p 的力量 ÷ 這一邊力量合計`。`shares`（695-696 行）已經有每個人的力量。
  - (b) 放手一搏：688 行旁邊另記每個人自己的推進 delta（往自己那一邊為正），`merit += max(0, delta) × 比例`。比例：這一邊這一回合「正的 delta」合計超過 `side_trend_cap` 時是 cap ÷ 正的合計，否則是 1。不拿「夾過的淨推進 ÷ 夾之前的淨推進」：同一邊有人搏成、有人搏輸時，夾之前的合計可能是 0（+1、−1）或負的，比例會除以 0 或變號。
  - (c) 點名打傷：`_land_hit`（811-826）時 `merit += 10 × 這一下打掉的 ÷ 對方氣血池上限`，一下最多 2.5。
  - 量級參考：正式的 `push_max` 是 20，放手一搏一次最多推約 16。
- 戰功只拿來挑現世的得主與挑戰者，畫面上不列排名、不露數字；只有被璽動的那一場，對兩邊合格的前三名各提示一句（4.3 最後一條）。公告寫到被挑中的人時，補一句「（此役戰功居前）」。
- 這是 Joy 寫的程式（決戰改版 PR #47），企劃者同意由我們改（17.4）。

【玉璽一】個人戰功用 Joy 的 PR #49（`battle_instance.merit`），不另加 `merit` 欄位；戰功在畫面上本來就公開，「戰功居前」的提示照寫。

### 4.5 持有者那一方打得怎樣：四檔與局勢係數【預設】

- 時刻表決戰的結果由 `battle_instance.decide_result`／`result_at`（1039-1060）給：（贏家, 大勝或險勝），戰局偏離 50 達 15 以上是大勝。換到持有者的角度就是四檔：自己這方贏，是大勝或險勝；對方贏，對方險勝是「險敗」、對方大勝是「大敗」。
- **量表確認四檔分得出來**（週末 5/5/5，30 季、60 場；每場從官軍、黃巾兩個角度各算一次，共 120 個視角）：大勝 35.8%、險勝 14.2%、險敗 14.2%、大敗 35.8%。其他設定差不多：5/5/0 是 36/14/14/36（5 季、22 個視角），10/10/10 與 14 天的季都是 33/17/17/33（各 3 季、12 個視角，樣本很小）。
- 整合版用「挑戰者 0／1／2／3 人」分檔。企劃者 10/11 把最後的比拚改成單挑，一次璽動只打一場，所以換成這一場的上限係數：

  | 持有者那一方 | 打不打單挑 | 局勢係數 | 這一場的上限（25%×係數） | 整合版 |
  |---|---|---|---|---|
  | 大勝 | 不打，懷璽不失 | 0 | 0 | 0 人 |
  | 險勝 | 打 | 0.4 | 10% | 1 人（等強時 10%） |
  | 險敗 | 打 | 0.7 | 17.5% | 2 人（等強時 19%） |
  | 大敗 | 打 | 1.0 | 25% | 3 人（等強時頂到 25%） |
  | 旁觀（璽動那一刻的快照不在交戰兩方：散人〔含這一季還沒上線過的持有者〕、豪強、陣營不在這一仗；或璽動之後陣營變了） | 打，挑戰者從勝方挑 | 0.7 | 17.5% | 散人 2 人 |

  係數照整合版等強時的被奪比例（10%、19%、25%，約 0.4：0.76：1）取低（0.76 取成 0.7，不是四捨五入）。替自己陣營把仗打好，本身就是護璽。
- **持有者親自出陣**（護璽）：在這場決戰自己出手滿 min(3, 實打回合)，上限再 ×`Config.seal.guard` 0.7。
- **持有者算哪一方**：一律照璽動那一刻的快照（`seal_holder_side`，4.3），之後不再讀投靠名冊：
  - 快照是 None（散人、這一季還沒上線過、豪強、陣營不在這一仗）：一律旁觀。散人臨時投效（`battle:enlist`，開打了也能晚到），只要出手滿 min(3, 實打回合)，算護璽（×0.7），**不改局勢那一檔**。不然他可以看完前六回合的戰局，再投到明顯要大勝的那一方、出手最後三回合，就不必單挑，還多拿護璽；這等於讓持有者自己選擇躲不躲，散人也比陣營持有者多一條退路。
  - 快照是交戰兩方之一，但收場時他在投靠名冊上的陣營跟快照不同（璽動之後叛投）：也算旁觀，而且挑挑戰者時不套同陣營過濾（4.6）。
  - 快照時是散人、之後才投靠陣營又替新陣營出戰的：照第一條算旁觀；出手滿 min(3, 實打回合) 一樣算護璽。
- **邊界**：
  1. 伏筆鎖定：鎖定方一定贏，戰場上打輸的記成險勝（`result_at`），所以持有者在戰場上大勝也可能被改判成險敗。一律照官方結果（`result`）算。量表裡假人從不鎖定，這一塊沒量到。
  2. 戰局剛好 50：判守方險勝，沒有平手。
  3. 保底收場（`end_without_fighters`）：場上沒人，挑不出挑戰者，不打單挑，算動過。
  4. 季終收兵（unfinished）：沒有結果，不打單挑，算動過、不失碎片。
  5. 從沒開成的決戰：沒有集結就沒擲，沒有這個問題（4.1）。
  6. 豪強或散人持有、這一季還沒上線過的持有者：照旁觀那一列。

### 4.6 挑戰者怎麼挑【預設】

- **從哪一邊挑**：持有者那一方的對面；持有者旁觀時從勝方挑。站在豪強那一邊（`definition.third.faction`）的人不是交戰兩軍，不能當挑戰者。
- **資格**：
  - 這場決戰的參戰者，自己出手滿 min(3, 實打回合)（序章裡被代選固守的人 `acted_rounds` 是 0，自然擋掉）；
  - 不是持有者本人；
  - 手上沒有碎片（一人一片）；
  - 跟持有者**璽動那一刻的陣營**（`seal_holder_faction`，4.3）不同，擋住「自己人合演轉手」。挑戰者自己的陣營讀收場時的投靠名冊（`faction_of`）；持有者那一邊一律讀快照，**不讀名冊**：不然持有者在集結期間叛到挑戰者那一方的陣營，對面每個人都會變成「同陣營」被濾掉。快照是 None（持有者是散人、這一季還沒上線過），或持有者的陣營在璽動之後變了（4.5），都不套這一條；臨時投效的散人照名冊是散人；
  - 這一季沒叛投過：參戰者加入決戰時快照 `BattleParticipant.turncoat`（他的 `PlayerState.defected`），收緊「朋友季中叛到持有者的對面陣營來接手」；
  - 不在新手期。
  - 不看是不是假人。也不能用 `BattleParticipant.is_bot` 判斷假人：那是決戰補位機器人的旗標，伺服器假人一律是 False。
- **怎麼挑**：
  - 合格的人照戰功取前 `Config.seal.challenger_pool` 3 名；上一次從這一片被奪走的人（`SealShard.former`）在這三名裡的話，直接挑他（追璽）。只要合格就優先的話，持有者跟前主串通就能每次都轉回他手上，所以要在前三名之內；
  - 否則照戰功加權從三名裡抽一位，亂數 `random.Random(f"{密鹽}|{天機}|seal-duel|{戰報流水號}")`。
  - 同一場收場還要挑現世或喚回的得主時，先挑挑戰者（3.3）。
- **人夠不夠**：量表從持有者對面看合格的人數（照「滿 3 回合、不在新手期」，120 個視角）：0 人 4 次、1 人 13 次、2 人 35 次、3 人 41 次、4 人 23 次、5 人 4 次。單挑只要一人，所以 96.7% 挑得出來；從勝方挑時，宛城、長社的勝方 60 場都有合格的人。挑不出來就寫「對面無人能上前」，懷璽不失、算動過。
- 1/1/0（最接近週末試玩）的 26 個視角裡有 19 個一個合格的人都沒有，見 15.3。

### 5.2 一回合怎麼算（對稱版）

記號：C＝挑戰者、H＝持有者，S＝那一邊這一招的份量（`scores[招]`，沒有就用 `strength(power)×foe_fit`），剋＝counter(C 的招, H 的招)。C 剋 H 是 +1，被剋是 −1。

- **兩邊都出招**：
  - 推力（往挑戰者算）＝round(`push_base`×(2×S_C÷(S_C＋S_H)−1)＋`counter_push`×w±`luck`)。w＝剋，但被剋的一方是參謀時那一截減半（`role_counter_relief` 0.5）：剋＝−1 而 C 是參謀，w＝−0.5；剋＝+1 而 H 是參謀，w＝+0.5。
  - 兩邊各扣自己的池子＝自己的上限×`hit`(0.08)×剋制倍數×clamp(√(對方 S÷自己 S), 0.5, `hit_scale_max` 1.5)。剋制倍數：被剋 1.6、剋人 0.5、沒剋 1。
- **只有一邊放手一搏**：搏的那一邊照 `gamble_roll` 擲。成了，往自己那一邊推 max(1, round((10＋0.15×風險)×實力倍數))，扣自己上限的 3%；沒成，往回退 min(4, round(風險×0.05))，扣自己上限的 (10%＋風險×0.25%)。另一邊這一招不算，也不扣血（同頭目戰「你搶了先手，或自己栽了」）。
- **兩邊都搏**：各擲各的，推力相加。
- **擲骰用哪一份亂數**：運氣（±`luck`）與放手一搏的成敗，都用這一回合自己的亂數（5.13），不用 `Game.rng`。
- **勝負**（挑戰者的角度）：
  - 挑戰者池子見底，或氣勢 ≤10：挑戰者落敗；
  - 持有者池子見底：挑戰者大勝（不算提前大勝）；
  - 氣勢 ≥90：挑戰者提前大勝；
  - 同一回合兩邊池子都見底：算挑戰者落敗（偏持有者）；
  - 打滿 5 回合：≥70 大勝、≥55 險勝、>45 僵持，其餘落敗。
- 數字一律讀 `Config.duel`（DuelTuning，models.py:1277-1321，正式值就是預設）與 `Config.battle`。只有節奏、上限與係數放在新的 `Config.seal`（13.4）。

### 5.3 雙方的身手（都用快照）

單挑不叫模型算身手、不扣角色的氣血，也不磨兵器（同決戰）。

| 情況 | 用什麼 |
|---|---|
| 挑戰者 | 他在這場決戰的 `BattleParticipant` 快照：`power`、`scores`、`role`、氣血上限 |
| 持有者有參戰 | 同上，用他自己的快照 |
| 持有者沒參戰，這一季上線過 | `Game._load_kin(持有者)`（engine.py:6426）建一份不叫模型的 Game，取 `_battle_power`（2752）、`_battle_scores`（2762）、`_battle_role`（2773）、`_battle_neili_cap`（2808）。這一份 Game 不 sync、不存回、不記 `last_seen`（5.5） |
| 持有者這一季還沒上線過 | 用 `new_game_state(content, 名號)` 包一個 `_kin` 來算：等級 1、兩門基礎武學第一成（企劃者 10/11 第 3 件）。威力約 8.6、份量約 24，對面戰功前三名對它的份量比中位數是 3（週末）或 5（14 天的季） |
| 觸發結算的人就是持有者 | 用 `self`，不讀資料庫裡比較舊的那一份 |

- 雙方的池子都從自己上限的滿血開始。決戰裡的池子本來就是另一份快照，打完不帶進來。
- **「這一季上線過」怎麼判斷**：持有者存檔的新欄位 `PlayerState.seen_real`（現實秒）不早於這一季開季的現實時間（新欄位 `SealRegistry.opened_real`，在 `open_season`〔sqlite_world.py:458〕與 `next_season`〔473〕寫，同 `season_last_real` 那兩行）。
  - `opened_real` 是 None 時一律當成上線過，照他的存檔算身手。會是 None 的情況：功能上線那一刻正在跑的那一季；測試內容用 `auto_open_first_season`，`seed_first_season`（sqlite_world.py:449-456）直接把季設成開了、不經過 `open_season`，第一季也一直是 None。
  - `seen_real` **只在「這個人自己的請求」裡寫**：伺服器的 `_locked`（server.py:231，登入的那個人自己的 Game；含 `/api/main` 輪詢與每個動作），以及假人程式的 `_take_turn`（bot_runner.py:131）與 `_add_bot` 叫醒（假人自己上線）。`Game.sync` 不寫它，所以管理者工具的 `_admin_target(sync=True)`（engine.py:6620，例如替他發召見、補發東西）、`_kin`、`_load_kin`、`peer_act` 建出來的 Game 都碰不到它。舊存檔沒有這一欄（None）時退回看 `last_real`，只會發生在功能上線後的第一季。
  - 為什麼不能看別的欄位：
    - `player.season_number` 不可靠：別人替他建 Game 再存回去（`peer_act` 6412、`_save_kin` 6436、`_save_target` 6644）就會被改寫；
    - `joined_at` 也不行：換季後沒同步過的人是 None；
    - `last_real` 由 `Game.sync` 寫（engine.py:627-631），管理者的 `_admin_target(sync=True)` 也會 sync 他，替不在線的持有者用了任何管理者工具，就會被判成「這一季上線過」。
- **不要直接讀舊存檔算威力**：`Game.__init__` 最後的 `_drop_stale_references`（engine.py:265→487）會跑 `_reconcile_season`，把舊季的存檔在記憶體裡換成新一季的新角色。只用來算威力沒關係，但絕不能存回去：存回去會改掉他的 `season_number`，看起來像「這一季上線過」。`_load_kin` 在沒有 db 的儲存（測試）裡回 None，要有退路，退到 `new_game_state`。
- **兵器**：兵器第二批（weapons-2）把兵器加成乘進 `Boost.factor`，`_battle_power` 與決戰快照會跟著變。合進來之後照合併後的 `_battle_power` 算，單挑不磨兵器。

### 5.4 下戰書、回合與節奏【預設】

- 決戰收場、決定要打之後，先「下戰書」`Config.seal.muster_seconds` 180 秒：寫一則天下大事，持有者有時間上線，全服也圍過來看。
- 接著打 `rounds` 5 回合。每回合開始時：
  - 判斷雙方誰「親自在場」（5.5）；
  - 不在場的那一邊照 5.6 預擲一招和一句架勢。
- 每回合什麼時候結算（一律「最早在回合開始 `pace_seconds` 20 秒之後」）：
  - 雙方都在場：兩手都送出就結算；有人過了 `round_seconds` 120 秒還沒送，那一手照 5.6 代出（他在場，所以沒給過架勢），然後結算。
  - 一邊在場：等在場的那一邊送出，最多 120 秒。
  - 雙方都不在場：20 秒結算，讓圍觀的人一回合一回合看。
  - 為什麼一律等滿 20 秒：一邊不在場時，在場那一邊一送出就結算的話，圍觀的人從節奏就看得出誰不在場（5.6）。
- 一場最長 180＋5×120＝780 秒（13 分鐘），雙方都不在場時約 280 秒。
- **誰來推進**：沒有背景程式，照決戰的做法。誰送出最後一手，就由他那一次呼叫結算。另外在 `Game.options()`（engine.py:765 附近，跟 `_battle_for_me` 同一處）與 `world_tick`（601）加 `_seal_tick()`，任何人輪詢都會把單挑推到現在，一次最多結算一回合。`world_tick_seconds` 正式是 0，所以沒人在線時單挑會停著等，不傷任何人；測試不要假設有排程在推。
  - `_seal_tick` 只在 `options(tick=True)` 時跑。`tick=False` 的呼叫（`_spar_problem` 的 `who.options(odds=False, tick=False)`〔engine.py:4968〕、`dialogue_request` 等）不推進、也不記 `last_seen`，同一個請求裡不會推進兩次。
- **賽季暫停**（`paused_at`）：暫停中 `_seal_tick` 不推進、送出的一手照收但不結算。`resume_clock`（sqlite_world.py:536-556）現在只用 `shift_deadlines` 挪 `active_battle` 的期限，要一起把 `seal_duels` 的 `starts_real`、`opened_real` 與雙方的 `last_seen` 往後挪同樣的秒數；不挪的話一繼續，兩邊都過了在場窗口，每一回合都會以 20 秒的節奏全由代打打完。

### 5.5 雙方都在線時：怎麼出招與同步

- **「親自在場」**：每回合開始時，看那個人最近一次推這場單挑的時間 `last_seen`，在 `presence_window` 45 秒以內才算在場。
  - **誰記 `last_seen`**：只在 `options(tick=True)`、而且 `self.state.player` 就是單挑的一方、而且是他自己的請求（伺服器的 `_locked`）時才記。`_kin`、`_load_kin`、`_admin_target`、`Game.for_world` 建出來的 Game 一律不記；**伺服器假人一律不記**（14.1）。
  - **低頻寫入**：`last_seen` 存在全服狀態的 `seal_duels` 裡（5.12），每記一次就是一次 `world.mutate`。所以只有存著的那個值已經比現在早 15 秒以上才寫，一個人一場單挑每 15 秒最多寫一次；不必重讀整季（`seal_duels` 不在季裡）。
  - 網頁開在前景時每 10 秒打一次 `/api/main`。
  - 不能用 `presence_seconds` 的 600 秒（「此地還有」用的）：那樣下線九分鐘的人也算在場，每回合會空等 120 秒。
  - **「在線」與「在場」不一樣**（企劃者寫的是「在線自己應戰」）：網頁在 `document.hidden` 時不輪詢（web/app.js:3531），分頁切到背景的在線持有者，照上面的規則會被判成不在場。所以：
    - 持有者從他的碎片被璽動起、單挑雙方從單挑開始（下戰書那一刻）到收場，`status_data["seal_watch"]` 是真；網頁看到它就在背景也照 10 秒輪詢（只在這段時間，最長約決戰加 13 分鐘），輪到他出招時把分頁標題改成「【奪璽】輪到你出招」。挑戰者在收場那一刻才確定，分頁要是在收場之前就切到背景、已經停止輪詢，就收不到；所以被璽動那一場的參戰者，從加入那一場到挑戰者確定也都算 `seal_watch`，挑出來之後只剩單挑雙方。背景輪詢的量：一場決戰十幾個人、最長約一個多小時，每人每 10 秒一次 `/api/main`，跟他們開著前景時一樣。
    - 從璽動起就沒打開過網頁的人，伺服器沒辦法叫他（這個網頁沒有系統通知），那就是不在線。
- **出招**：
  - 選單最前面多三招 `seal:<招>`（寫剋哪一招，照 `duel.move_label`），加上放手一搏的輸入框（`free_op` 是 `seal_text`）。
  - 選項 id 用 `seal:`，不跟頭目戰的 `duel:<招>`、`duel:flee` 撞名；`choose`（engine.py:1340）的分派加 `kind == "seal"`。
  - 同一個人可能同時在打頭目戰（`PlayerState.duel`），兩組選單都會出現，奪璽的排前面。
- **同步**：照 `BattleRound`（battle_instance.py:99-110）的形狀，`SealDuel` 記 `pending`（這一回合誰出了什麼）、`rates`、`stories`、`opened_real`。兩手湊齊才結算；送出之後按鈕變灰，寫「已出招，等對方（最遲 M 分 S 秒）」。
- **兩個在場的人同時出招，互相看不到對方這一回合要出什麼**，只看得到對方上一回合出了什麼。
- **回合開始時判成不在場的那一邊，這一回合中途上線**：這一回合的三招與輸入框一律灰掉，寫中性的字「這一回合來不及了，下一回合再出手」，不寫「代打」；下一回合開始時就算在場，自己應戰。不讓他蓋掉預擲的那一招：架勢已經照預擲的招給對手看了，蓋掉的話照架勢出招的對手會被誤導，等於讓晚到的人改掉已經露給對手的資訊，晚到反而佔便宜。
- **不鎖人**：單挑不進 `_idle`（engine.py:4646），也不擋 `atlas.travel_block`，雙方照常移動、遊玩。身手用的是快照，人在哪裡都一樣。
- **下一場決戰剛好同時開打**：參戰的人的選單會被戰鬥選單取代（engine.py:771-783），看不到奪璽的三招，只能被代打。這種情況很少（兩場時刻表決戰隔三週，只有 `showdowns_waiting` 排隊時才可能接著開），這份接受，列在 19.2 第 11 條。

### 5.6 不在線時代打（像頭目一樣出招）

- 回合一開，就照 `duel.roll_next` 的做法替不在場的那一邊預擲一招和一句架勢，架勢 `tell_truth` 六成是真的。亂數用這一回合的代打種子（5.13），不用 `Game.rng`。
- 招的權重是 (這一招的份量 ÷ 三招裡最高的份量)^`proxy_power`(4)。例：份量 75／60／90 的人，最常出的那一招約佔 59%，落在 `content/duels.json` 頭目偏好的範圍裡（各頭目最常出的那一招佔 42%～65%：赫連豹 42%、韓稜 50%、段鐵頭 62.5%、獨眼何三與褚安 65%）。
- 只有他的對手看得到代打那一邊的架勢（奪璽卡上只在對手的畫面畫，圍觀的人看不到）；親自在場的那一邊不給架勢。代打的人比較吃虧，所以在線應戰是有好處的。這一條要企劃者知道（19.2 第 3 條）【預設】。
- 代打只看存檔，不叫模型、不寫放手一搏。
- 畫面與傳聞都不寫「代打」，也不寫誰在線。**圍觀的人看不出來，但對手看得出你不在場**（有架勢就是被代打）：
  - 代打那一手到結算時才算進奪璽卡的「已出招 X／2」，不在回合一開就算；
  - 每回合一律最早 20 秒後才結算（5.4），節奏上也看不出來；
  - 伺服器假人一律被代打（14.1）：在對手眼裡，假人跟一個不在線的真人一模一樣（有架勢、從不放手一搏），所以「沒架勢、五回合一次都沒搏」這種認得出假人的樣子不會出現（伺服器假人設計）。

### 5.7 放手一搏的三段式（照頭目戰的 `duel_text`）

- **A 段** `Game.seal_text_request(text)`：鎖內、只讀。驗證他是這場單挑的一方、這一回合開始時判他在場（5.5；判成不在場的這一回合不開單子）、這一回合還沒送出、文字 20 字以內，開單子（單挑 id、回合、哪一邊、文字、名號、場景）。
- **B 段**（`server.seal_text`，照 server.py:835-854 的 `duel_text`）：在鎖外呼叫 `battle_instance.assess_gamble`（1124-1157）。參數：
  - `setting` 寫「兩人陣前單挑、爭奪玉璽碎片的」，`place` 寫「單挑」；
  - `target` 帶一行對手的身手。決戰的 `battle_instance.target_line`（battle_instance.py:411）要傳 `BattleInstance` 與 `BattleDef`，單挑沒有這兩樣，所以 `seal_duel.py` 另寫一個小函式 `foe_line(me: SealSide, foe: SealSide, tuning)`，照雙方快照的實力寫一句比較（只寫比較、不寫數字，字照 `target_line` 的寫法）；
  - 預算是 `free_text_budget_seconds`（60），評不到一律 40（`DEFAULT_FREE_TEXT_SUCCESS_RATE`）。
  - 模型同時寫成敗兩版劇情（以名號開頭、40 字內、不寫數字，`clean_story`）。
- **C 段** `Game.seal_gamble(text, rate, stories, request=)`：鎖內重驗，同一場、同一回合、同一邊、還沒送出、同一句才採用，記進 `pending`。送出不等於結算，跟 `submit_battle_custom_action` 一樣，兩手湊齊才結算。
  - **回合對不上就直接回「這一回合已經結算」**，不重評、不套用。不照抄 `duel_gamble`（engine.py:5559-5566）的「對不上就在鎖內重評」：那樣會把第 r 回合寫的那一句套到第 r＋1 回合，可是他第 r 回合已經被代打過了。
  - 同一回合、只是文字或邊對不上（例如同時開了兩個分頁），一樣丟掉、回一句叫他重送。
- 一場單挑每回合都可以搏【預設】，跟頭目戰一樣，不學決戰的「一幕一次」：一場只有 5 回合，而且搏輸了扣的是自己的池子。**但搏在單挑裡是壓倒性的好招**（9.2 的「挑戰者每回合搏」那幾列）：只有一邊搏時對方這一招不算，搏成了推 (10＋0.15×風險)×實力倍數，搏輸最多只退 4。五回合的單挑會變成比誰寫得好，三招退居次要；真正壓住易手機率的是 25% 底下的那幾個係數。要不要照決戰的做法限次數（例如一場最多搏兩次），列在 19.1 乙。
- 網頁只有一個放手一搏的輸入框。`server.main_view` 的 `free_op`（server.py:885）與 web/app.js:3441 現在只在決戰與頭目戰兩者之間選，要改成三選一，順序是「正在打的決戰 > 奪璽單挑 > 頭目戰」；api 的 op 分派（server.py:1423-1426）加 `seal_text`。
- 假人不寫放手一搏（14.1）。

### 5.8 整場被奪最多 25%：怎麼落實【預設】

- **單挑打完照結果再擲一次**：

  易手機率＝`cap`(25%)×局勢係數（4.5）×護璽係數（0.7 或 1）×單挑係數

  | 單挑結果（挑戰者的角度） | 單挑係數 |
  |---|---|
  | 氣勢到 90（提前大勝） | 1.0 |
  | 大勝（打滿 ≥70，或持有者池子見底） | 0.7 |
  | 險勝（打滿 ≥55） | 0.3 |
  | 僵持、落敗 | 0 |

- 四個係數都不超過 1，所以不管怎麼打、模型給多高的成功率、持有者故意放水，一場被奪都不會超過 25%。擲骰用 `random.Random(f"{密鹽}|{天機}|seal-take|{單挑 id}")`：不動 `Game.rng`，不管誰觸發結算，結果都一樣；有密鹽，挑戰者也沒辦法事先算出打贏了奪不奪得到（5.13）。
- **單挑結果 × 持有者那一方 → 這一場易手的機率**（持有者沒出陣；出陣再 ×0.7）：

  | 持有者那一方 | 挑戰者提前大勝（氣勢到 90） | 挑戰者大勝 | 挑戰者險勝 | 僵持、落敗 |
  |---|---|---|---|---|
  | 險勝 | 10% | 7% | 3% | 0 |
  | 險敗、旁觀 | 17.5% | 12.25% | 5.25% | 0 |
  | 大敗 | 25% | 17.5% | 7.5% | 0 |

  **挑戰者打贏單挑，碎片也多半不易手**：最好的情況（持有者那一方大敗、挑戰者提前大勝）也只有四分之一。觀戰的人會看到贏家多半拿不到東西，靠的只是「璽有靈」那一句。這是企劃者給的上限 25% 直接推出來的後果，要企劃者確認這種觀感可以接受（19.1 乙）。
- **串通轉手的上限**：持有者跟別陣營的朋友串通（自己當散人旁觀、不參戰、不上線讓對方看架勢、故意輸），每次璽動最多 25%×0.7×單挑係數（≤1），而且要先被璽動；一季最多被璽動一次，所以一季串通轉手最多約 13.5%×17.5%＝2.4%。追璽要在戰功前三名之內、挑戰者這一季不能叛投過（4.6），朋友沒辦法只靠叛投或「前主」的身分插隊。
- **「照雙方實力把勝面夾住」給不了硬上限**，原因有三：
  1. 放手一搏成了推 (10＋0.15×風險)×實力倍數：成功率 50、倍數 2 時一次推 35；模型評 100 時一回合也推 20。
  2. 真人怎麼出招，事前算不出機率。
  3. 持有者可能跟別陣營的朋友串通、故意輸掉，就是企劃者否決的「自己選擇轉讓」。
  
  量表也證實了：照頭目戰的公式跑蒙地卡羅（`seal_duel_mc.py`，5 回合），份量相當時挑戰者打到險勝以上的機率，兩邊亂出是 39%，挑戰者看架勢是 63%，本來就超過 25%。所以一定要在單挑之後再擲。
- **畫面不寫機率**。單挑開打時只寫一句：「最後氣勢越偏向挑戰者，碎片越可能易主；璽有靈，未必跟著贏家走。」挑戰者打贏卻沒奪到時寫「碎片在兩人之間一閃，終究落回某某懷中」（字待 joy 潤）。
- **持有者親自出陣的折扣怎麼對應到單挑**：整合版的「出陣再打七折」照舊乘在這一場的上限上（護璽係數 0.7）。他自己在單挑裡在線應戰，好處另外算：沒有架勢可以被讀，自己也看得到對方代打的架勢。
- 可以寫一個性質測試：對任意出招、任意成功率、兩邊在不在場的組合，易手機率 ≤ 25%×局勢係數×護璽係數（16.1）。

### 5.9 收場：結果、名望、戰報、江湖史

| 結果 | 碎片 | 名望 | 江湖史（具名，字待 joy 潤） |
|---|---|---|---|
| 易主 | 換到挑戰者手上，`since_season` 記這一季（新主保護）；前主記成 `former`（追璽） | 失主 +5 | 「某某在長社陣前奪得某某懷中的『雲篆』，失主力戰失璽。」 |
| 挑戰者打贏單挑（險勝以上），再擲沒中 | 留在原主 | 持有者 +3；挑戰者 +1【待定】 | 「某某力挫某某，碎片卻落回某某懷中，懷璽不失。」 |
| 挑戰者沒打贏 | 留在原主 | 持有者 +3 | 「某某懷璽不失。」 |
| 沒打成（無人上前、季終收兵、管理者取消） | 留在原主 | 都沒有 | 只寫天下大事 |

- **易手只失去碎片**：不扣銀兩、不扣氣血、不留內傷。
- **寫入**：結算當下用一次 `world.mutate` 一起寫，一起成功：
  - 登記比對再寫：持有者還是原來那人、**挑戰者此刻手上沒有碎片**才換。挑戰者在排隊的時候（天命之季）可能已經奪到或被喚回選中一片；這一條不成立就記成「沒打成」（算動過、懷璽不失、只寫天下大事）；
  - 季的天下大事與江湖史；
  - `SharedWorldState.seal_duels` 裡那一場標成收場。
  
  `world.mutate` 會連季一起讀出寫回（sqlite_world.py:55-80 的 `_load`／`_save`），季和全服登記寫得進同一次 mutate。這一次 mutate 只加傳聞與江湖史（各自是獨立的列），不改季的其他欄位，`seal_duels` 也不在季裡，所以 `choose()` 收尾的 `_save_season`（只換掉 `state.season`）蓋不到它，不必重讀整季。**通則**：之後哪一步要改季本身的欄位，寫完一律 `self.state.world = self.world.get_season()`。
- **交到兩人手上**：不在收場時改兩人的存檔。這一季沒上線過的持有者一同步，`_reset_player_for_new_season` 會把整個 GameState 換成新的，寫進去的戰報和紀錄就不見了（FB-027 的教訓）。改成：
  - 登記的 `history` 記一筆，帶全服流水號 `seq`、單挑每回合一句（挑戰者的角度）、結果；
  - 兩人各自同步時，由新的 `Game._deliver_seal_results()` 照 `seq` 補：戰報（`BattleRecord.kind` 加 `"seal"`，state.py:580；`battlelog.KIND_WORDS` 加「奪璽」）、江湖紀錄；**名望只在補送當下還是同一季（`SealEvent.season` 等於目前的季）才給**，跨季才回來的只補戰報與紀錄（名望每季重來，加在新一季的角色身上不對）。抄本照登記重抄，不靠這一步（7.4）；
  - `PlayerState.seal_seen` 記補到第幾號，加進換季保留清單（engine.py:474 `battle_results_seen` 那一行旁邊）。持有者下線時被奪、下一季才回來，也補得到。
  - 掛在 `sync` 裡 `_deliver_battle_results`（engine.py:643、3146）旁邊。
- **持有者的戰報**照挑戰者那份翻過來寫（照 `_spar_mirror` 的做法，engine.py:5272）：氣勢字倒過來，「你」換成持有者。被代打的那一方戰報寫「你未及趕到，由你平日的路數應對」；照新角色算的另寫「你這一季還沒現身江湖，身手生疏」，這一句只寫進他自己的戰報。
- 決戰的戰報（`_file_showdown`，engine.py:3168）多一行「璽動：某某將與懷璽的某某陣前單挑」。

### 5.10 全服觀戰

- **天下大事**（world 層、具名）：
  - 下戰書一則：「某某向懷璽的某某下了戰書，一炷香後陣前單挑，爭『雲篆』。」
  - 每回合一則，寫雙方出了什麼與氣勢的字，不寫數字。例：「奪璽第二回合：某某強攻，某某以固守相迎，某某略佔上風。」放手一搏的回合放模型寫的那一版劇情。
  - 收場一則（5.9）。
  - 一場多 6、7 則傳聞，每一則都會讓推送指紋裡的天下大事流水號變動、叫醒全服分頁，這正是觀戰要的效果。所以每一則都要短。氣勢只寫字，跟戰線變化不露數字（FB-064）的寫法一致。
- **江湖頁的「奪璽」卡**（`status_data["seal_duel"]`，全服都看得到，可以摺疊，放在軍令卡下面，不擠 375×812 的第一屏）：雙方名號、哪一片、第幾回合、氣勢的字（持有者看的是倒過來的）、最近兩三行、「已出招 X／2，最遲 M 分 S 秒後結算」（X 只算親自送出的，代打的那一手到結算才算，5.6）。下戰書那段寫「M 分 S 秒後開打」。代打那一邊的架勢只在他對手的卡上畫。
- **推送**：`server_push.world_fingerprint`（server_push.py:77）加一組（單挑 id、階段、回合、氣勢、親自送出了幾手），有人出手，開著的分頁就更新。`last_seen` 不放進指紋：它每 15 秒就可能動一次，放進去會一直叫醒全服。
- 決戰畫面收場後就消失了，所以觀戰不放在決戰畫面。

### 5.11 打到一半遇到收季、換季、提前收季

- **提前收季**：第 10 週起每個曆時都會看一次 `decisive_ending`（world.py:562，在 `advance_season` 的迴圈裡）。週末設定一個曆時約 1.8 分鐘，宛城、廣宗收場後的單挑可能被腰斬。所以全服還有沒打完的奪璽單挑時，那一個曆時先不收季，最多約 13 分鐘。做法：`advance_season` 跟讀投靠名冊一樣（world.py 那一段的註解：交易裡的快照用同一條連線讀，不是 mutate），一次推進先用新的唯讀方法 `WorldStateStore.seal_duel_open()` 查一次，有就把 `decisive` 當 None。沒給 store 的純函式呼叫（測試）照舊。
- **自然收季、管理者立刻收季**：打到一半的單挑記成「未分勝負」，碎片留在原主。收季在 `mutate_season` 裡跑，寫不了登記，所以由收季後第一次 `_seal_tick`，或換季那一筆交易（`next_season`），補記 `history` 一筆 `unsettled`，讓兩人補得到。
- **換季**：`next_season` 在同一筆交易裡清空 `SharedWorldState.seal_duels`（還沒收場的先補記 `unsettled`）。

### 5.12 狀態放哪、寫入順序

- **狀態**：`SharedWorldState.seal_duels: list[SealDuel]`，存在 world 表 id=1 那一列的 JSON 裡（同 `active_battle` 是全服的、不在季裡），不必升資料庫版本。用 list 是預留給天命之季：一次只打一場，其餘排隊；排隊的那一場開打前再驗一次資格（持有者還是原來那人、挑戰者手上還是沒有碎片），不成立就記成沒打成。
- **為什麼不放季（`WorldState`）**：`choose()` 一開頭就呼叫 `self.options(odds=False)`（engine.py:1331，tick 預設 True），收尾的 `_save_season`（engine.py:1403 → 1128-1132 → `save_season`）會把記憶體裡的 `self.state.world` 整份蓋回去。`_seal_tick` 推進回合、記 `last_seen`、記 `pending` 要是寫在季裡、又沒重讀，那一回合就被蓋回去；可是那一回合寫的天下大事是 rumors 表的獨立列，不會跟著退，下一次 tick 又結算同一回合，就出現重複或互相矛盾的「奪璽第 N 回合」。要每次寫完都重讀，又是每 10 秒一次在行動鎖裡 `get_season()`（`logs=True` 把整季的傳聞和江湖史讀回來）。放全服狀態：`save_season` 只換掉 `state.season`（sqlite_world.py:443-444），蓋不到它，也不必重讀整季。
- **不能放的地方**：
  - `PlayerState.duel`：兩人各自存檔會互相蓋掉。
  - 收場的那場 `BattleInstance`：`start_battle`（sqlite_world.py:601-612）在舊的那場收場後直接換成新的一場，`_open_waiting_showdown`（engine.py:3039）可能當下就開下一場；`_battle_status`（2814）對已收場的戰鬥也回 None。
- **開單挑**：`_settle_showdown`（2988）在 3035 行重讀 `self.state.world` 之後，才呼叫新的 `_open_seal_duel`，用一次 `world.mutate` 寫 `seal_duels`、登記與下戰書的天下大事。不能寫在 `mutate_battle` 的 callback 裡：`database.rewriting`（database.py:308-323）會丟 RuntimeError。
- **寫入的通則**：寫 `seal_duels` 的地方（開單挑、`_seal_tick`、`last_seen`、送出一手、收場）都用 `world.mutate`，只加傳聞與江湖史、不改季的欄位，所以不必重讀整季；哪一步要改季本身的欄位，寫完一律 `self.state.world = self.world.get_season()`（5.9）。測試補一支：單挑回合中有人 `choose()` 別的動作，回合不會被倒回、天下大事不會重複。
- **結算可能跑在沒有玩家的 Game 裡**：`world_tick`（601-612）用 `Game.for_world`，玩家是空白的。所以 `_open_seal_duel` 與 `_seal_tick` 只讀寫 WorldState、登記與別人的存檔（讀，不存），不碰 `self.state.player`。
- 名字：絕學的契機已經用掉了 `Game._seize`（engine.py:4207），新的函式叫 `_seal_emerge`、`_seal_stir`、`_open_seal_duel`、`_seal_tick`、`_seal_finish`、`_deliver_seal_results`。

### 5.13 亂數與密鹽【預設】

- **每一次擲骰都用自己的 `random.Random`，不用 `Game.rng`**：結果看是誰的 Game 觸發的（玩家的 Game、`Game.for_world`、`bot_runner` 共用的 rng 都可能），「誰送出最後一手誰結算，不管誰觸發結果都一樣」（16.1）這條測試就寫不出來；而且會消耗 `Game.rng`，讓之後的擲骰位移（`rounds.py`、懸賞、秘方都刻意避開這件事）。
- 種子一覽（`{密鹽}` 見下一條；都寫成 `random.Random(f"…")`）：
  - 現世擲不擲、哪一片：`{密鹽}|{天機}|seal-emerge|{季別}`
  - 現世給誰：`{密鹽}|{天機}|seal-emerge|{戰報流水號}`
  - 璽動每一片：`{密鹽}|{天機}|seal-stir|{event_id}|{碎片 id}`；同場擲中好幾片時挑哪片：`{密鹽}|{天機}|seal-stir|{event_id}`
  - 天命之季必定璽動挑哪片：`{密鹽}|{天機}|seal-mandate|{event_id}`；喚回：`{密鹽}|{天機}|seal-recall|{event_id}`
  - 挑戰者：`{密鹽}|{天機}|seal-duel|{戰報流水號}`
  - 單挑每一回合（運氣、放手一搏的成敗，兩邊各一份）：`{密鹽}|{天機}|seal-round|{單挑 id}|{回合}|{challenger 或 holder}`
  - 代打的招與架勢（回合開始時擲）：`{密鹽}|{天機}|seal-proxy|{單挑 id}|{回合}|{challenger 或 holder}`
  - 再擲（易不易手）：`{密鹽}|{天機}|seal-take|{單挑 id}`
  
  每一份亂數依固定的順序取數（例：回合那一份先取運氣、再取放手一搏的成敗），寫進 `seal_duel.py` 的說明。
- **密鹽**：天機（world_state.py:81）從 0 起、跟 `season_number` 一起在 `next_season` 加一，永遠等於季號 −1；`event_id` 是固定的、戰報流水號是遞增的，都猜得到。看得到原始碼的人就能事先算出這一季哪一片會被璽動、會不會現世、挑戰者打贏了奪不奪得到。所以 `SealRegistry` 加一欄 `salt`：第一次建登記時用 `secrets.token_hex(16)` 產生（不是時鐘，不違反「引擎不讀電腦時鐘」），之後不變；不進 `status_data`、不進推送指紋、不寫進任何畫面或紀錄。測試直接給一個固定的 salt。

【玉璽一】密鹽改在伺服器與假人程式啟動時產生（`server.main`、`run_bots.main`），引擎只讀；測試與量表腳本沒有密鹽，同樣的種子跑出同樣的結果（不然用正式內容跑整季的測試與量表每次都不一樣）。

### 7.3 寶物欄：碎片佔不佔一般寶物那一格、能不能換下來【預設：不佔、不能換下】

四欄設計第七節【定】了「寶物欄容得下一件傳承的寶物」，佔不佔那一格、能不能換下來留給這份。【預設】：

- 寶物欄分兩格：**一般**（裝備四欄 6.x 的那一件）與**傳承**（碎片）。
- 傳承那一格：
  - 不佔一般那一格，兩格的效果都算；
  - 不能換下，效果常駐；
  - 不進裝備庫，不佔 100 格；
  - 不能贈送、不能拆解、不能交懸賞；
  - 不受「寶物一天只能換上一次」（四欄 2.3）的限制，因為它根本不換。

理由：

1. **傳承那一格根本不需要換**：歸屬看全服登記（7.4），身上那件只是抄本，換季時也只帶那一件（7.5）。佔一般那一格的話，就得讓持有者在碎片與一般寶物之間二選一、還要能換下來，而換下來的碎片要有地方放（下一條）、也會讓人以為收起來就安全（第 3 條）。另開一格、不換，抄本永遠照登記，規則最單純。這一條跟碎片的效果強弱無關。
2. **碎片是被迫轉手的**：要是走裝備庫，裝備庫滿了就收不進來；四欄 6.5 的寄放規則（`held_gear`）是為懸賞與名將贈禮寫的，用在易主上，會變成「被奪走的碎片卡在寄放裡」。
3. **換下來沒有意義**：誰持有看全服登記（7.4），換下來不會改變被璽動、被奪的風險，只會讓人誤以為藏起來就安全。
4. 企劃者否決過「藏璽」，換下來等於藏璽。

另一種做法（佔一般那一格、可以換下），企劃者要的話列在 19.2 第 2 條。缺點就是上面的 1、2、3。

### 7.4 全服登記是正本，身上那件是抄本

- **正本**：`SharedWorldState.seal`（world 表 id=1 那一列的 JSON，不分季），每一片記持有者、到手季、動過的季、狀態（未現世、有主、隱沒）、前主（第十三節）。現世、易手、隱沒、喚回、散去，都是一次 `world.mutate`，在行動鎖那筆 `BEGIN IMMEDIATE` 交易裡原子完成。
- **抄本**：`PlayerState.heirloom: Equipment | None`，`slot="treasure"`、`heirloom=True`、`template=碎片 id`、`id="璽:<碎片 id>"`。
  - id 固定，不吃 `weapon_serial` 流水號，所以重抄幾次都一樣，也不會跟「寶:N」撞號。
  - 所有照前綴或照 `rack` 找東西的函式（換上、拆解、修練頁的列、機器人的 `wanted`）都碰不到它。以後加「贈送裝備」也要排除它。
- **重抄**：`Game.sync` 裡照登記重抄，排在 `_reconcile_season` 與 `catch_up_season` 之後、`_advance_player_local`（engine.py:631）之前：承露照整段離線時間算體力回復就在 `_advance_player_local` 裡，抄本要先對。讀登記用一個只讀 world 那一列的新方法 `WorldStateStore.seal_registry()`，不讀季。登記說是你的，就寫上抄本；不是你的，就清掉。重抄幾次結果都一樣。戰報、紀錄、名望的補送（`_deliver_seal_results`）照舊排在 `_deliver_battle_results`（engine.py:643）旁邊。
  - `_kin(state)`（engine.py:6418，切磋的 `_spar_problem`〔4968〕、截殺 `raid`〔5372〕算對方時用）建出來的 Game 不 sync，也要重抄一次（只是讀一次登記，不貴），不然舊主過期的金角、螭首還在起作用。
- **易手那一下只寫登記**。動作者自己剛好是一方的話，直接改 `self.state`；別人的抄本等他同步時重抄。
  - 不能從資料庫讀動作者自己那一列來改：伺服器的 `act` 最後會把 `self.state` 整份存回去（server.py:260、bot_runner.py:149），剛寫的會被蓋掉。
  - 也不讀、不存下線持有者那一列（5.3 的理由）。
- **抄本過期的影響**：碎片被奪之後，舊主身上那件到他下次同步才清掉。他做任何動作之前都會先 sync（server.act、假人的 `_take_turn` 都是），重抄又排在 `_advance_player_local` 與出關結算之前，別人算他的時候（`_kin`）也重抄，所以碰不到過期的效果。
- 裝備一計畫的 `Equipment` 裡 `tier`、`quality` 是必填（`plans/2026-10-10-裝備-1-四欄化與防具.md:161`），寶物不分階品，要等裝備三給這兩欄預設值。這是要等裝備三的理由之一。

### 7.5 換季、叛投、贈物

- **換季帶走**：`_reset_player_for_new_season`（engine.py:426-481）的保留清單加兩行：`heirloom` 與 `seal_seen`。同步時本來就會照登記重抄，這一行只是保險。這就是四欄設計第七節第 2 條說的那個接點；碎片不在裝備庫，所以只帶那一欄。
- **叛投跟著走**【預設】：`defection.clear_progress`（defection.py:92-111）只清陣營進度，不碰裝備與登記。投靠名冊在下次 `_record_faction`（engine.py:2743-2748）時改成新陣營；之後**新開集結**的璽動照新陣營快照。已經璽動、還沒收場的那一場照璽動那一刻的快照，叛投只會讓他算旁觀（4.2 第 3 條、4.5）。
- **贈物、拆解、交懸賞**：都不行（7.3）。

### 7.6 隱沒【預設；要不要有、門檻多少是【待定】，19.1 庚】

- **判斷**：在換季那一筆交易（`sqlite_world.next_season`，sqlite_world.py:473-492）裡，對每一片有主的碎片讀持有者那一列的 `$.seen_real`（5.3；舊存檔沒有就退回 `$.last_real`）。寫法同 `characters.present`（characters.py:56-72）的 `json_extract`，next_season 握著 conn，可以直接 SELECT characters 表。兩條都成立才隱沒：
  - `seen_real` 早於剛結束那一季的 `opened_real`，也就是整季沒上線；
  - `now − seen_real` ≥ `Config.seal.sink_days` 14 天，用現實秒算，`now` 是 next_season 收到的參數，不讀電腦時鐘。
  - `opened_real` 是 None（功能上線前開的季、測試內容的第一季）就判斷不了，這一次不隱沒。
  - **查不到持有者那一列**：當成整季沒上線、而且已滿 14 天，直接隱沒。這只會在主機端手動刪列時發生：讀不懂的存檔由 `CharacterStore.backup`（characters.py:100-107）搬到備份表，但 `server.open_game`（server.py:118）搬完當下就 `Game.new` 一個同名的新角色存回去，列還在。
  - **同名重建的角色繼承碎片**是本意：名號是身分，帳號綁名號（CLAUDE.md「登入」），backup 只發生在他自己登入、存檔讀不懂的時候。新角色第一次同步就照登記重抄到碎片。
- **算一下**：週末設定一季 2.5 天、一個週末開一季，缺一季時換季那一刻距上次上線約 8 天，還不到 14 天；連缺兩季（兩個週末）就沉。14 天的季缺一整季就沉。這是企劃者「持有的人帶進下一季」之外多出來的失去途徑，而且不經過大事件，要企劃者確認（19.1 庚）。
- **寫法**：碎片改成 `sunk`、持有者清掉，`history` 記一筆。江湖史只寫「某某懷中的『玄紐』不知所蹤」，不寫原因；真人假人走同一條路。
- **next_season 要注意**：它是手動 `_load`、`_save`，沒有 rewriting 保護。隱沒、蓋天命之季的章、七片散去，都要直接改那份 `state.seal`；在裡面再呼叫 `self.mutate` 的話，寫進去的會被最後的 `_save(conn, state)` 整份蓋掉，而且不會報錯。
- **假人**：換季時假人全部算退隱（bot_runner.py:7-9），叫醒是隨機挑（`self.rng.choice(retired)`，252 行），而且 `_add_bot`（248-268）只在 `_fill`（225-246）發現某陣營不到 `bots_min_per_faction` 時才會被呼叫。真人與假人夠多的伺服器上，退隱的持碎片假人永遠不會被叫醒，必然整季沒上線、滿 14 天就隱沒，看得出是假人。只改 `_add_bot` 先叫醒持碎片的假人不夠（缺額不出現就不會呼叫它）。做法【預設】：
  - 每季開季後第一次 `_fill`（暫停中不做），對每一位持碎片、退隱的假人另外擲一次回不回來，**不看缺額**：機率 `Config.seal.bot_return_chance` 0.7（沒有真人回鍋率的數據；上線後照主機端真人持有者「整季沒上線」的比例校準）。亂數用 `bot_runner` 自己的 rng。
  - 回來的走 `_add_bot` 同一條叫醒的路，派到投靠名冊人數最少的陣營；沒回來的照真人的規則可能隱沒。
  - 剩下的差異：真人回不回來看興致，假人是固定機率；回來的假人可能換了陣營（真人換季後也是重新投靠，看不出來）。15.2 的量表印「季末碎片在真人、假人手上各幾片」，看會不會往假人手上集中（19.2 第 16 條）。

【玉璽一】照 PM 庚：`SealShard.absent` 記連續幾季沒上線，`absent ≥ 3` 而且滿 28 天才沉。持碎片的退隱假人每季回不回來的種子照密鹽、季別、名號（重開假人程式結果一樣）。

## 八、七片湊齊：天命之季與天命之爭

### 8.1 觸發【預設】

- 換季時（`next_season` 那一筆交易，在 `fresh_season` 之後），這一輪七片都現世過，就在新的一季蓋上天命之季的章（`WorldState.mandate = True`、`SealRegistry.mandate_season`）。現在有主的、已經隱沒的都算現世過。
- 企劃者的原話是「當整個伺服器湊齊 7 片」。讀成「七片都現世過」是 PM 的解讀，另一種讀法是「七片同時有主」，兩種讀法差很多（19.1 己）：
  - 七片都現世過：跟隱沒無關，平均約 20 季（7÷0.35）。
  - 七片同時有主：隱沒的碎片要能在一般季重新現世（不然一沉就永遠湊不齊、天命之季也永遠不來），而且要看隱沒得多兇。`seal_rev3/together.py`：一片一季隱沒 0% 時平均 20 季、2% 時 24 季、5% 時 37 季（九成在 63 季內）、10% 時 118 季。
- 正在跑的那一季不受影響（同 `stamp_season` 的熱更新規則）。
- 新的一季沒蓋第一季規則的章（沒有時刻表決戰）的話，天命之季延到下一個有蓋章的季（`SealRegistry.mandate_pending`）。
- 天命之爭要的時刻在 `fresh_season` 的 `default_schedule`（world_state.py:113）排過之後另外補進 `schedule`（8.3），因為 `stamp_season` 不知道登記。

【玉璽二】蓋章寫在 `sqlite_world.next_season` 的 `_stamp_mandate`（換好新的一季之後）；`mandate_pending` 兼管理者「下一季」。

### 8.2 天命之季的規則（加壓）

- **三場決戰必定璽動**【定】：長社、宛城、廣宗開集結時不擲 7%，每場直接牽動一片（「每場一片」是【預設】，見下面第三條）。
  - 從有主、這一季還沒動過的碎片裡挑一片，亂數 `{密鹽}|{天機}|seal-mandate|{event_id}`（5.13）。
  - 這一季沒有新主保護【定】（企劃者 10/11 第 4 件）。
  - 這一季也沒有全服每季兩次的上限【預設】：這是 PM 從「三場決戰必定璽動」推出來的（留著兩次的上限，第三場就動不了）。「每片每季最多動一次」照舊【預設】，所以三場牽動三片不同的碎片。
  - 「必定璽動」到底牽動幾片要企劃者選（19.1 丙）：每場一片（【預設】）、每場兩片，或每片每場都動。最後一種要拿掉「每片每季最多動一次」，一季 21 場單挑、每場決戰後要連打約 90 分鐘，不建議。
- **每場仍然最多被奪 25%**【定】：5.8 的算法不變，大勝照樣不打單挑。
- **喚回**【預設】：第 6、9 週兩場決戰收場時，各從隱沒的碎片裡喚回一片。抽法同現世（3.3：勝方戰功前三名抽一人，排在挑戰者之後、排除已經挑去單挑的人），擲骰換成 `{密鹽}|{天機}|seal-recall|{event_id}`。沒有合格的人就留著隱沒。喚回的碎片這一季也會被牽動（沒有新主保護）。
  - **喚回不算現世**：它是舊碎片回來，不是新的一片出土；天命之季也不擲現世（3.2）。可是一季會冒出兩片，企劃者說的「一季最多也只會看到一片」算不算被打破，要企劃者確認；另一種做法是一季只喚回一片（19.1 辛）。
  - **隱沒超過兩片**：喚回不了的那幾片留著隱沒，天命之爭時不屬於任何人、不推起點，再下一季照樣跟著七片一起散去（8.4）。
- **不提前收季**：這一季的提前收季從第 13 週起算（等於不提前收）。不然第 10 週就收季，廣宗與天命之爭都打不到（第三節的量表）。所以天命之季三場決戰都打得到。
  - 做法：`decisive_ending` 讀 `season.mandate`，蓋了章就用 `Config.seal.mandate.decisive_from_week` 13。不改 `Config.decisive_from_week`，一般季的節奏不變。

【玉璽二】喚回只拿碎片、不學混元一氣；天命之季的璽動亂數 `seal-mandate|event_id`。

### 8.3 天命之爭【預設】

- **時刻**：第 12 週週一 20:00（季曆）。週末設定是開季後約 55.6 小時（季末 60 小時），14 天的季是第 13.0 天。決戰最長約 75 分鐘，打得完。
- **地點與陣營**：冀州下曲陽。官軍對黃巾，豪強是第三方。內容新加一筆 `content/battles.json` 的 `tianming`：3 幕 × 3 回合，集結、回合的秒數同其他時刻表決戰。用現成的決戰引擎，不另寫一種戰場。
- **時刻表**：`content/timetable.json` 加一件 `tianming`（kind showdown、week 12），標 `mandate_only`。時刻由蓋章時寫進 `schedule["tianming"]`，`timetable.when` 照它讀，所以不受決戰預設在週四 20:00（timetable.py:36-37）的限制。
  - **沒蓋天命之季章的季要完全看不到它**。直接讀 `content.timetable` 的地方很多，只改 `_pending`、`due_showdowns`、`next_event` 不夠。所以加一個過濾函式 `timetable.events(season, content)`（沒蓋章就拿掉 `mandate_only` 的那幾件），**列舉整張時刻表的**每一處都改走它：
    - timetable.py：`default_schedule`（52 行，不改的話每一季的 `schedule` 都會多一筆第 12 週週四 20:00 的 tianming）、`_pending`（69）、`schedulable`（336）、`status_rows`（374）；

    - server.py:1101、1106；opportunities.py:340；howto.py:292、294、310、325（大事的件數與種類）。
    - **照 id 查一件的**（timetable.py `_event` 139、engine.py 2999 與 6109、foreshadow.py:102）可以照舊讀整張：只有那一件真的開出來、被結算時才會查到它。`content.py` 的 `validate` 也照舊讀整張。
    - 加一支守門的測試：`tianxia/` 與 server.py 裡，除了 `timetable.events` 本身與上一條那幾處白名單，不准再直接讀 `content.timetable`（跟其他「不要另寫一份判斷」的守門測試同一種寫法）。

### 8.5 換劇本：不寫死黃巾之亂的 id【預設】

- **問題**：七片湊齊要約 20 季，`2026-10-02-世界觀推進-註記.md` 第三節的二十季大綱每一季的史事、陣營、決戰都不一樣（第 2 季洛陽之變是外戚、宦官、涼州軍，第 20 季是晉對吳）。照舊寫法，現世寫死 `wancheng`、璽動寫死 `changshe_fire`／`wancheng`／`guangzong`、天命之爭寫死冀州下曲陽「官軍對黃巾」與 `s1_tianming_guan`／`huang`，換了劇本這些 id 都不存在：現世、璽動、天命之爭整個停擺，或內容一載入就驗不過。
- **做法**：
  - 時刻表的決戰加一個欄位 `TimetableEvent.seal: Literal["emerge", "stir"] | None`：`emerge` 是現世那一場（也算璽動），`stir` 只璽動。黃巾之亂標宛城 `emerge`、長社與廣宗 `stir`。`Config.seal` 不再寫 `emerge_event`、`stir_events`。
  - 天命之爭是時刻表上標 `mandate_only` 的那一件決戰，同一件寫 `mandate_endings: {陣營 id: 結局 id}` 與它自己的 `battle`（地點、交戰兩方在 `battles.json` 那一筆）。喚回的兩場照時刻表順序取「天命之爭以前、標了 `seal` 的前兩場」，不寫死。
  - 每個劇本自己標。`validate`：有 `content/seal.json` 而且時刻表不是空的時，標 `emerge` 的剛好一件、標了 `seal` 的都是決戰、`mandate_only` 最多一件而且 `mandate_endings` 的結局都在劇本裡；沒標也不算錯（那個劇本就是不現世、不璽動，跟第一季規則關著的季一樣，3.6）。
- **換劇本時的碎片**：登記是全服、跨季的，持有者照樣帶進新劇本的季，效果照樣有；現世、璽動看新劇本的標記；天命之季蓋了章、新劇本卻沒有 `mandate_only` 的決戰，就照 8.1 的 `mandate_pending` 延到下一個有的季。
- **前提要講清楚**：目前內容只有黃巾之亂，這一份的時機（第 6、9、11、12 週）、量表與機率都是照「每季都重玩黃巾之亂」算的。換劇本之後時刻表的場數與週次不一樣，9.2 的數字要重量。列進 19.1 壬讓企劃者知道。

## 十二、管理者救場與驗收工具【預設】

碎片太稀有：一季 35% 現世、一片一季 13.5% 璽動、真的易手大約 0.3%～2.3%。QA 只能靠管理者工具。設定頁的管理者區多一組「玉璽」，效果跟自然發生一樣（`Game.admin_*`），公告不寫管理者（照計畫一 Task 10）：

| 工具 | 做什麼 | 注意 |
|---|---|---|
| 強制現世（下一場） | 下一場時刻表決戰必定現世，不擲 35%，可以指定哪一片 | 不能指定給誰：照 3.3 從勝方抽 |
| 指定持有者 | 把某一片直接記到某個名號名下（或收回成未現世、改成隱沒） | 只改登記，不必讀他的存檔（`_admin_target(sync=False)`，engine.py:6620）。「這一季上線過」看的是 `seen_real`（5.3），管理者工具碰不到它，所以就算其他管理者工具 sync 了他，也不會害他躲過隱沒或改掉「照新角色」的判斷。抄本與紀錄等他同步時補。一人一片照擋 |
| 強制璽動（下一場） | 下一場決戰必定牽動指定的那一片，略過 7%、新主保護與次數上限 | 天命之季照它的規則 |
| 強制開單挑 | 立刻對指定的那一片開一場奪璽單挑，指定挑戰者，局勢係數可選（預設 1.0，上限 25%） | **正式伺服器只能掛在最近一場剛收場、還沒開過單挑的時刻表決戰上**：公告照那一場寫，看起來就是那一場打完後的單挑，符合「要有大事件發生才可以」【定】。「不必有決戰」的版本只在 `Config.seal.qa_tools` 開著時才列（測試內容與 QA 伺服器用），不然玩家會看到沒有任何大事件就冒出來的奪璽單挑。挑戰者的快照照 5.3 持有者「沒參戰」那一列算；挑戰者也要過一人一片 |
| 定這一場結果 | 正在打的單挑，指定再擲中或不中（QA 用，同時刻表的「定結果」） | 公告照常，看起來跟自然發生一樣 |
| 取消單挑 | 記成未分勝負，碎片留在原主 | |
| 蓋天命之季 | 下一季蓋天命之季的章；或這一季立刻開天命之爭（走 `admin_start_battle`，engine.py:6048） | |
| 立刻隱沒判斷 | 照 7.6 的條件現在判一次，只印結果、不改，用來看下次換季會沉哪幾片 | |

- 週末試玩（人數上限 2、不開假人）幾乎湊不出挑戰者（15.3）。驗收要在有假人的伺服器上做，或用「強制開單挑」。

### 13.2 形狀【預設】

```python
# world_state.py（SharedWorldState 加 seal）
class SealEvent(BaseModel):            # 全服流水號的一筆；補送與江湖史都讀它
    seq: int
    season: int
    kind: Literal["emerge", "stir", "keep", "take", "sink", "recall", "scatter", "unsettled", "mandate"]
    shard: str | None = None
    holder: str | None = None          # 這一筆之後的持有者（take 是挑戰者）
    other: str | None = None           # 對手（take 的失主、keep 的挑戰者）
    record: str | None = None          # 決戰或單挑的流水號
    result: str | None = None          # 單挑結果（挑戰者的角度）
    lines: list[str] = []              # 單挑每回合一句（挑戰者的角度），補戰報用
    text: str = ""                     # 江湖史那一句

class SealShard(BaseModel):
    id: str
    state: Literal["hidden", "held", "sunk"] = "hidden"
    holder: str | None = None          # 名號；比對用 characters.name_key
    since_season: int | None = None    # 到手的季（新主保護）
    stirred_season: int | None = None  # 最近一次璽動的季
    emerged_round: int | None = None   # 這一輪現世過沒（天命的觸發看它）
    former: str | None = None          # 上一個從這一片被奪走的人（追璽）

class SealRegistry(BaseModel):
    shards: dict[str, SealShard] = {}  # 內容的七片；登記沒有的用預設補上
    round: int = 1
    seq: int = 0
    opened_real: float | None = None   # 這一季開季的現實時間（「這一季上線過」、隱沒）；None 一律當上線過
    mandate_season: int | None = None
    mandate_pending: bool = False
    salt: str = ""                     # 亂數的密鹽（5.13）；第一次建登記時產生，不顯示、不進指紋
    history: list[SealEvent] = []
```

```python
# world_state.py（SharedWorldState 加 seal_duels，同 active_battle 是全服的、不在季裡；只列重點）
class SealSide(BaseModel):
    name: str
    faction: str | None
    power: float
    scores: dict[str, float]
    role: str
    hp: float
    hp_cap: float
    last_seen: float | None = None     # 現實秒：最近一次推這場單挑（他自己的請求才記、15 秒最多寫一次；假人不記）
    present: bool = False              # 這一回合開始時判他在場沒（判成不在場，這一回合的鈕灰掉）
    fresh: bool = False                # 照新角色算的（只寫進他自己的戰報）

class SealDuel(BaseModel):
    id: str                            # f"{決戰戰報流水號}:{碎片 id}"；管理者開的另起
    shard: str
    event_id: str | None
    phase: Literal["muster", "active", "ended"]
    starts_real: float
    challenger: SealSide
    holder: SealSide
    edge: float = 50.0                 # 挑戰者的角度
    round: int = 0
    rounds: int = 5
    cap: float                         # 25%×局勢×護璽
    pending: dict[str, str] = {}       # 這一回合誰出了什麼（招或 "text"）
    rates: dict[str, int] = {}
    texts: dict[str, str] = {}
    stories: dict[str, tuple[str, str]] = {}
    proxy_move: dict[str, str] = {}    # 代打預擲的招
    tell: dict[str, str] = {}          # 代打那一邊給對手看的架勢
    opened_real: float | None = None   # 這一回合開始的現實秒
    lines: list[str] = []
    result: str | None = None
    taken: bool | None = None
```

- 引擎不讀電腦時鐘：`last_seen`、`starts_real`、`opened_real`、`seen_real` 都用 `Game.now`（`sync(now)` 傳進來的）。暫停後繼續時 `resume_clock` 把 `starts_real`、`opened_real`、`last_seen` 一起往後挪（5.4）。

## 十四、假人與機器人

### 14.1 伺服器假人（`bot_policy.py`、`bot_runner.py`）

- **假人在奪璽單挑裡一律不算在場**：不記 `last_seen`、不擲要不要來、`bot_policy.take_turn` 不加 `seal` 分支（選單上就算出現 `seal:<招>` 也不按）。所以假人永遠由引擎照他的快照代打（5.6），看起來就是一個不在線的真人：有架勢、從不放手一搏。
  - 為什麼不讓假人親自出招：單挑是一對一、全服看著打的。對手看不到架勢，就知道這一邊有人在場；在場的真人幾乎一定會搏（5.7），在場的假人一次都不搏（假人不寫自由文字）。「沒有架勢、五回合一次都沒搏」幾乎就認得出是假人，碰過幾場就更確定，違反伺服器假人設計。
  - 代價：假人持有者、假人挑戰者都比在線的真人吃虧（被讀架勢）。真人不在線時也一樣吃虧，所以兩者看起來一致。
- **引擎判斷在不在場只看 `last_seen`，絕不看 `is_bot`**。挑人與畫面也一樣（4.6）。`last_seen` 只有真人自己的請求會記（5.5），假人自然永遠不在場，引擎不必知道他是假人。
- **叫醒**：每季另外擲一次持碎片的退隱假人回不回來，不看缺額（7.6）。
- **首創配方取名**那種模型呼叫，這裡沒有：假人不寫放手一搏，所以單挑不叫模型。
- 假人也能拿碎片（現世、奪來），效果一樣、畫面一樣。

### 14.2 整季機器人（`bot.py`）

- 奪璽要兩個角色，整季機器人一個人玩不出來。量表改用 `sim_season_one.py` 的伺服器假人（15.2）。
- `bot.pick()` **不必改**：`seal:<招>` 只在單挑的一方、單挑開著時出現，最多 13 分鐘，不是「永遠按得下去」的選項。
