## 二、定了的原則

1. 【企劃者定】**小功能平常只跑自己那一塊的測試。**
2. 【企劃者定】**整套集中在某個時間點跑。**
3. 【企劃者定】**偶爾晚一點才知道別處壞了，可以接受。**
4. 【企劃者定】**要更好的開發模組與功能模塊化**，讓測試與未來新功能導入都更方便；怎麼切由 Fable 想（第三節），概念企劃者 10/30 看過說 OK。
5. 【企劃者定，照舊】數值全由規則引擎決定、引擎不讀時鐘、名字原創、假人看不出來、畫面改動先出對比圖、新寫的字標「待 joy 潤」。這些不變，這一份不重寫。

## 三、架構：核心、功能包、介面殼

### 3.1 三層【Fable 定】

```
介面殼      server.py 殼（登入、鎖、掛路由）      web/app.js 殼（狀態列、分頁、選項列）
               │                                     │
功能包      tianxia/features/<包>/  一個功能一包：商城、酒肆、懸賞榜、玉璽、擂台、出陣……新功能一律這樣生
               │   （功能包之間沒有箭頭：不互相 import，要用別包的東西經過核心）
核心        狀態與存檔 ｜ 規則與季曆 ｜ 共用服務（記錄、花費、錢包、時刻） ｜ 選項與分派（選單、分派、狀態列）
```

- **核心**不常改。改了跑核心測試＋每個功能包一條煙霧測試。核心包括：`state.py`（`PlayerState`、`WorldState`）、`sqlite_world.py`、`world_state.py`、`characters.py`、`accounts.py`、`database.py`、`rules.py`、`calendar.py`、`models.py`（`Config`、`Content` 骨架）、`content.py`（載入）、`team.py`、`gender.py`、`naming.py`，加上瘦下來的 `Game`（`sync`、`options()` 彙整、`choose()` 分派、`status_data()` 彙整、換季彙整、管理者外殼）與共用服務。
- **功能包**是做事的地方。每個功能把現在散在 `engine.py`、`server.py`、`app.js`、`state.py`、`content/`、`tests/` 六處的那幾段收進一個資料夾。
- **介面殼**只剩登入、行動鎖、路由掛載、狀態列與分頁的框。

### 3.2 一包裡面【Fable 定】

```
tianxia/features/mall/
  __init__.py     登記：name="mall"、order、enabled()、掛鉤（3.3）
  rules.py        純規則，不碰存檔、不碰 Game（現在的 seal.py、bounties.py、mall.py 這一類）
  actions.py      給選項、接按鈕（現在 Game 上的 mall_* 方法＋choose 裡那一段＋_everyday_options 裡那一段）
  state.py        自己的欄位（PlayerState.mall / WorldState.mall 子模型）與 Config.mall（含 enabled）
  content/        自己的 json 與 schema（mall.json）
  routes.py       自己的 API（APIRouter，/api/mall/…）
  web/            mall.js、mall.css
  tests/          只測這一包
  bots.py         假人對這一包的選項怎麼按（取代 bot_policy 叫私有方法）
  README.md       三行：這一包做什麼、導覽在 docs/guide/ 哪一節、設計稿是哪一份幾版
```

不是每一包八樣都要有：沒有 API 的沒有 `routes.py`，沒有畫面的沒有 `web/`。

### 3.3 掛鉤【Fable 定；簽名留給開工的人】

核心照一張 `FEATURES` 清單（有順序）依序問每一包。掛鉤從現在 `Game` 實際在做的事抽出來，就這幾個，不多開：

| 掛鉤 | 現在對應 | 核心怎麼用 |
|---|---|---|
| `enabled(ctx)` | `Config.<x>.enabled`、`rules.season_one`、劇本有沒有陣營 | 關著的包一個掛鉤都不叫 |
| `options(ctx) -> list[Option]` | `_everyday_options` 裡那一段 | 照 `order` 串起來 |
| `choose(ctx, kind, arg) -> Outcome \| None` | `choose` 裡那一段 | 只吃自己前綴的 id（`mall:`）；吃不到回 `None`，核心問下一包 |
| `status(ctx) -> dict` | `status_data` 裡那一段 | 合進狀態列與分頁的資料 |
| `on_sync(ctx, elapsed)`、`on_day(ctx)` | `sync`、`_pill_day` 換日 | 補算時間 |
| `on_season_start(ctx)`、`on_season_end(ctx)` | `_reset_player_for_new_season`、`_save_season` | 換季 |
| `on_drop_stale(ctx)` | `_drop_stale_references` | 清失效參照 |
| `bot_pick(ctx, options)` | `bot_policy` 叫 `game._tavern_price` 之類的私有方法 | 假人；也在這裡宣告哪些選項是「永遠按得下去」的（取代「新增永遠按得下去的選項要改 `bot.py::pick()`」） |
| `admin_tools(ctx)` | `admin_*` 52 個方法裡屬於這一包的 | 設定頁的管理者工具 |
| `routes`、`web`、`content` | `server.py` 路由、`index.html` 的 `<script>`、`content.py` 讀的檔 | 殼照清單掛 |

`ctx` 是核心給功能包的服務：`state`、`world`、`content`、`now`、`rng`，加上現在 `Game` 上被叫最多的那幾個共用方法——`_log`（314 處）、`_write`（104）、`_save_season`（75）、`_side`（63）、`_pill_day`（58）、`_cost_option`（38）、`stamp`、`_guide`、`_quick_client`、`_wallet`。**第一階 `ctx` 就是 `Game` 本身**，不另包一層；功能包只准叫寫在 `tianxia/core/services.py` docstring 那張清單上的方法。要不要之後包成真正的介面，留給做第一階的人看搬完商城的手感決定。

### 3.4 四條規矩【Fable 定】

1. **功能包只能 import 核心，不能 import 別的包。** 要用別包的東西（買東西要扣錢包、懸賞要知道戰果）走核心的服務或核心發的事件。`tests/core/test_feature_boundaries.py` 用 `ast` 掃 import，違反就紅，幾毫秒；第一版只掃 import，之後再加「只准叫服務清單上的方法」。
2. **新功能一律用骨架腳本生成一包**（`scripts/new_feature.py <包名>`）：資料夾、空的掛鉤、`tests/` 骨架與一條煙霧測試、`docs/guide/` 那一節的標題、登記進 `FEATURES`、`README.md`。
3. ~~**舊功能碰到才搬。** 派工單上哪一批要動酒肆，就順手把酒肆搬進包裡；不搬的留在 `engine.py` 不動。沒有大翻修。~~ → 企劃者 2026-10-31 改成照〈全部拆包總表〉主動搬完、不順手搬（第十五節）。搬的那一步是純搬：行為不變、測試不改（只搬位置）、那一包的測試與核心契約綠。
4. **測試跟著包走**（第四節）。

### 3.5 狀態欄位與資料庫【Fable 定】

- 舊功能的欄位留在 `PlayerState`／`WorldState` 原地，由那一包認領（`README.md` 列出自己的欄位名）；**不為了搬包改資料庫結構**。
- 只有新功能的欄位放進自己的子模型（`PlayerState.<包>: <包>Player`），pydantic 預設值讓舊存檔讀得進去；要加表或改結構才升 `SCHEMA_VERSION`（照舊先跟 PM 對版本號；現在第 7 版 → 2026-10-31 Joy 的審查修正 PR #112（`bfb1b1fa`）一筆從第 7 版升到第 9 版）。第 3 階以前新包的欄位實際怎麼放，見第十五節「新包的欄位與 `Config`」。
- 核心的欄位要加，先過 PM。

### 3.6 內容【Fable 定】

- 第 1、2 階：json 照舊放 `content/`，一包的檔以包名開頭（`mall.json`）；`content.py` 照舊全部載入。
- 第 3 階：`content.py` 照 `FEATURES` 載各包的 `content/`；測試可以只載核心內容＋一包的內容（第二級測試會從幾秒變成不到一秒）。`tests/fixtures/content/` 也照包分。

### 3.7 網頁【Fable 定】

- 原生 JS、不引進打包工具（照舊）。`index.html` 的 `<script>` 改由伺服器照 `FEATURES` 的 `web` 清單生成：核心四個檔之後接每一包的 js／css，關著的包不載。
- 殼提供 `registerPage(name, {render, onAction})` 這一類的掛鉤；功能的畫面各自一個檔。第 3 階才做；第 1 階商城的 `mall.js`、`mall.css` 先切出來當示範（`app.js` 裡提到 mall 的 450 行、`style.css` 244 行）。
- 網頁測試照舊「寫到那個檔名的測試檔」挑；`mall.js` 的測試放 `features/mall/tests/`。

### 3.8 假人【Fable 定】

假人與整季機器人照舊不另外設計、不量；但每一包的 `bots.py` 要回答「假人看到我的選項怎麼按」，核心的 `bot_runner` 只問包、不再叫 `Game` 的私有方法。任何畫面不能透露誰是假人（照舊）。

### 3.9 搬的順序【Fable 定】

示範先搬**商城**：10/20 才做、最新；已經有自己的模組（`mall.py` 684 行、`wallet.py` 184、`rename.py` 67）、五條 `/api/mall` 路由、`mall.json`、`tests/mall/` 10 個檔（其他資料夾提到它的只有 5 個）、導覽區塊、分頁；留在 `engine.py` 的只有 13 個方法、98 行。

之後照改動頻率：出陣（25 筆）、走一趟（24）、戰鬥（20）、探索（17）、約戰（17）、酒肆（13）。**正在飛的線碰的功能等線落地再搬**（鐵匠鋪 `feature/smithing-flow`、輿圖 `feature/map-view`），不然撞。（→ 2026-10-31 起順序照〈全部拆包總表〉，第十五節。）

### 3.10 商城這一包的邊界【Fable 定；審稿問到的】

審稿量到商城是跨功能最多的一塊：它賣的「票」被別的功能消耗（走一趟的題壁墨、列傳票、體力丹的 `card_bonus`、自創的重悟帖、深交名額、`library.cap_of`），`content.py`、`create.py`、`outing.py`、`zhuan_end.py`、`howto.py`、`models.py`、`database.py` 都碰 `mall` 或 `wallet`，`mall.py` 自己 import `library`。而且商城的動作全走 `/api/mall/*`，`choose` 裡沒有 `mall:` 前綴、假人從不買。所以：

- **錢包是核心服務**：`wallet.py` 留在核心；「票的庫存查詢與消耗」（現在 `mall.tokens()` 這一類）搬進核心的錢包服務（`ctx.wallet.tokens(kind)`、`ctx.wallet.consume(kind)`），商城包只負責賣與記帳。走一趟、自創、列傳要用票的地方改叫 `ctx.wallet`，不叫商城。這就是「跨包經過核心」的第一個機制；**事件機制第 1 階不做**，等第 2 階真的有「一包要知道另一包發生了什麼」的例子再開。
- `rename.py`（易名帖）搬進商城包。`Config.mall`、`MallItem` 照 3.5 留在 `models.py`，商城包 import 它們（核心可以被包 import，反過來核心只在 `FEATURES` 登記那一處 import 包）。
- `library.cap_of`（深交名額上限）：商城包過渡期可以 import 還沒搬的 `tianxia/library.py`，行尾註 `# 過渡：待搬`；邊界測試第一版只禁「包 import 包」，不禁「包 import 還沒搬的舊模組」。
- **第 1 階多搬一個有按鈕的小包**，驗 `options`、`choose`、`bot_pick`、`on_season_*` 這幾個商城用不到的掛鉤，不然掛鉤簽名等於憑空設計、第 2 階第一個真有按鈕的包要回頭改核心。挑的條件：`Game` 方法 ≤ 10 個、`choose` 裡有自己的 `kind`、假人會按、沒有線在飛。候選：捐獻（`donate_*` 6 個方法、4 個選項 id）、名帖（`mingtie_*` 6 個）、開席（`feast_*` 7 個）；做第 1 階的人量過耦合再挑一個，寫進計畫。
- **`Game.mall_*` 這些公開方法留成一行的委派**（`server.py` 叫 149 個 `Game` 方法、測試直接寫 `g.mall_buy(...)`）：第 1 階「只搬位置」只有這樣做得到。第 2 階那一包的線再碰到時，呼叫端改成直接叫包、委派拿掉。`engine.py` 行數的驗收因此不準，**主要驗收改成「改 `engine.py` 挑到幾條」**，行數只記參考。過渡挑法把委派算成 `mall` 群正好是對的。

### 3.11 過渡期的例外【Fable 定】

- 還沒搬的舊模組（`outing.py`、`create.py`、`zhuan_end.py`……）可以 import `features.<包>`，但能走 `ctx` 的服務就走服務。
- 包可以 import 還沒搬的舊模組（註 `# 過渡：待搬`）。
- 兩條例外都是過渡期的；每搬一包，PM 在交接記還剩幾處。

## 四、測試

### 4.1 分級【Fable 定】

| 級 | 測什麼 | 開不開 Game | 多久 |
|---|---|---|---|
| 一、單元 | `rules.py` 純規則 | 不開 | 毫秒 |
| 二、功能包 | 開 Game（測試內容）只走這一包 | 開 | 幾秒 |

### 4.3 `test_for` 怎麼挑【Fable 定；第 0 階就改】
