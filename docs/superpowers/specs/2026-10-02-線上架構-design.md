## 零、一句話

把現在「Gradio 介面＋每次動作讀寫整個 JSON 檔＋全服一把檔案鎖」的原型，改成一個伺服器只跑一支遊戲程式：全服狀態放在記憶體裡依序處理，每個動作當下寫進 SQLite；網頁前端和伺服器分開；世界時間由伺服器自己的排程推動；LLM 在背景跑，不擋任何人。封測放在企劃者自己的電腦，用 Cloudflare Tunnel 對外。

## 一、範圍與前提 【定】

| 題目 | 決定 |
|---|---|
| 玩家用什麼玩 | 網頁，手機和電腦的瀏覽器都能玩，不用下載 |
| 下一個里程碑 | 封閉測試（CB），撐 100～300 人跑完一季。架構照三千人設計；第一版只部署在一台主機；正式開放前用假人壓測到三千人 |
| 伺服器放哪裡 | 企劃者家裡的電腦，用 Cloudflare Tunnel 對外（自帶 HTTPS、藏住家裡的 IP） |
| 哪一台電腦 | 現在這台開發用的電腦（Windows 11 Home）。線上版和開發版用不同資料夾、不同資料、不同連接埠 |
| 登入 | LINE 登入＋Google 登入；封測期間再加一道邀請碼；管理者權限綁在帳號上，不再用名號認人 |
| 更新 | 改內容與數字：真正的熱更新，不重開。改程式：無縫重啟，玩家最多看到幾秒「連線中…」。大改版：公告後停機 2～4 小時 |
| 架構方案 | 方案一：一個伺服器一支遊戲程式、全服狀態在記憶體、每個動作寫進資料庫。**這是 CB 期間的選擇**，正式開服前依壓測結果再評估 |

- **不在這份文件**：LLM 跑在哪裡、顯卡夠不夠、要不要上雲端（子項目三）；商業模式與金流（還沒定，元寶與招賢已在 `2132028` 拿掉）。

### 沒選的方案

- **方案二：伺服器不存狀態、PostgreSQL 當唯一真實來源、可同時跑好幾支程式。** 現在的引擎是「拿出整季的狀態改完再整份存回去」，改成這種做法等於把每條碰到全服狀態的規則都重寫成資料庫裡的小交易；為了一服三千人不划算。
- **方案三：只換介面和儲存，全服那把鎖留著。** 撐不到三千人，跟「照三千人設計、之後不用重寫」衝突。

## 二、整體結構 【定】

```
玩家的瀏覽器（手機／電腦）
   │  HTTPS（網頁）＋ WebSocket（伺服器主動推送）
Cloudflare Tunnel
   │
遊戲伺服器：一支 Python 程式，從「線上版」資料夾執行
   ├ 網頁與 API：登入、送出動作、取得畫面資料
   ├ 世界主迴圈：所有修改在記憶體裡依序處理
   ├ 排程：世界時間、季末、決戰回合、傳聞摘要、假人
   ├ 假人：在程式裡直接呼叫遊戲動作
   └ LLM 工作佇列：背景呼叫，回應回來後再套用
   │                         │
SQLite 資料庫               Ollama（同一台電腦的顯卡）
   │
每天備份 → 雲端硬碟
```

| 部分 | 做什麼 | 跟現在比 |
|---|---|---|
| `tianxia/` 遊戲引擎 | 規則與數值 | 規則本身不改；只換掉存取全服狀態的那一層（原本是 `WorldStateStore` 讀寫 JSON 檔），以及取得現在時間的方式（改成由外面傳進來） |
| `server/`（新） | 網頁與 API、登入、世界主迴圈、排程、LLM 工作、推送 | 取代 `app.py` 與 `run_bots.py` 的角色 |
| `web/`（新） | 玩家看到的網頁前端，手機和電腦都能用 | 取代 Gradio 介面 |
| `app.py`（Gradio） | 新前端做好之前，留著當開發用的工具，不對外開放 | 之後拿掉 |
| SQLite | 帳號、角色、全服狀態、傳聞、江湖史、戰鬥紀錄 | 取代 `saves/` 的 JSON 檔與檔案鎖 |

**原則**
- 引擎仍是唯一決定數值的地方；伺服器只負責接線（同現在「`app.py` 只負責顯示與接線」的精神）。
- 伺服器裡任何部分都不直接改全服狀態，一律送進世界主迴圈依序處理，因此不需要任何鎖。
- 慢的事（LLM、季末掃排行榜、要大量模擬的計算）都在主迴圈外面做，做完再把結果送回主迴圈。

## 三、資料怎麼存 【定】

### 3.1 記憶體與資料庫

- **全服狀態**（大勢、戰線、決戰、配方、陣營人數、天機……）一直放在記憶體。
- **在線玩家的角色**登入時從資料庫載入，下線一段時間後從記憶體移出。三千人時總共只有幾十 MB。
- **一個動作＝資料庫裡一筆交易**：動作做完，把這次變動的部分一次寫進去。停電或當機最多少掉當下那一個動作。
- **小的整份存，會長大的一筆一筆加**：全服的大勢數值、角色狀態這些小東西整份覆寫；傳聞、江湖史、戰鬥回合、配方這些會一直長的，每次新增一列。一個動作的成本不會隨伺服器開多久、有多少人而變大。
- **角色存檔不再夾帶一份全服賽季**（現在 `GameState.world` 讓每個人的存檔都複製了整個賽季）。

### 3.2 資料表（概念）

| 表 | 內容 |
|---|---|
| 帳號 | 登入方式（LINE／Google）、是否管理者、用了哪個邀請碼、是否停權 |
| 邀請碼 | 碼、可用次數、已用次數 |
| 角色 | 屬於哪個帳號、名號（同服不重複）、陣營、是不是假人、角色狀態 |
| 全服狀態 | 大勢、戰線、時間、天機等小資料，整份覆寫 |
| 傳聞 | 層、陣營、大區、地點、內容、具名或匿名、時間（依傳聞分層設計） |
| 見聞 | 哪個角色聽過哪則傳聞 |
| 江湖史 | **跨季保留**，每筆記著第幾季 |
| 武學與配方 | 每季各自一份，記首創者 |
| 戰鬥 | 全服決戰、參戰者、每一回合 |
| 賽季紀錄 | 每季的結局、世界記憶、排行榜、獎勵 |
| 動作紀錄 | 誰、何時、做了什麼；查問題與抓作弊用，保留 30 天【預設】 |

- **換季不刪資料**，改成賽季編號加一；舊的一季整份留著，江湖史、世界記憶、上一季的首創紀錄都讀得到。這也補上「江湖史目前沒有跨季保存」的缺口（見第一季設計第十四節、無限煉製的配方首創紀錄）。
- **CB 開服從零開始**，不搬現在 `saves/` 的存檔（都是測試資料）。
- 資料庫先用 **SQLite**：一個檔案、備份就是複製、不用另外裝資料庫服務；只有一支程式在寫，正好合用。之後要換 PostgreSQL 只改儲存那一層。

## 四、世界時間與排程 【定】

- 世界時間由伺服器自己往前推，不再等有人點擊；沒人在線時，大勢人物照樣推戰線、決戰照樣逾時結算。

| 多久一次 | 做什麼 |
|---|---|
| 每 10 秒【預設】 | 推進世界時間；決戰的集結與回合逾時 |
| 每個遊戲小時 | 大勢人物日常推動、亂局與豪強割據的自然漲落、大勢門檻 |
| 每 4 小時 | 各大區的地方傳聞摘要（傳聞分層設計） |
| 每天 | 每日上限重算、升第 2 階的晉升彙整、資料庫備份 |
| 每週一 | 陣營軍令、第四階席次上任 |
| 依時刻表 | 史書大事結算、三場全服決戰開打 |
| 每 20 秒 | 假人輪流行動 |
| 季末 | 在背景結算排行榜與獎勵，算完一次套用 |

- **個人的時間不排程**：體力、氣血回復、閉關、福緣等照現在的做法，等你做動作或看畫面時再補算；沒上線的角色不耗計算。
- **停機時的時間**：無縫重啟（幾秒）開回來補算那幾秒；**公告停機 2～4 小時時，賽季時鐘暫停，季末跟著往後延**。
- **快轉**：只有管理者能用，全服一起快轉（同現在）。
- **時間來源**：引擎不再自己讀電腦時鐘（現在 `engine.py`、`world.py` 有幾處直接呼叫 `time.time()`），改由伺服器傳進來；排程統一控制時間，模擬與測試可用假時鐘跑完整季。

## 五、一個動作怎麼跑、LLM 與推送 【定；數字預設】

### 5.1 動作流程

1. 瀏覽器送出動作，附一個流水號。
2. 伺服器確認登入身分，找到角色。
3. **限速**：每個帳號每秒最多幾個動作【預設】，擋連點與腳本。
4. 送進世界主迴圈：補算這個角色的個人時間 → 套用動作 → 收集這次產生的事件（傳聞、大勢變化、戰鬥更新）→ 同一筆交易寫進資料庫。
5. 做動作的人拿到結果與更新後的畫面；其他人只收到跟自己有關的推送：天下大事給全服、陣營軍情給同陣營、地方傳聞給人在那個大區的人、決戰回合給參戰的人。

- **流水號**：重連後，還沒確認的動作自動重送；伺服器看到重複的流水號就不做第二次（不會扣兩次體力）。重連時補送斷線期間錯過的推送。這是「無縫重啟」的基礎。
- **多分頁、多裝置**：資料都在伺服器上，大家看到同一份、動作依序處理；不再有「兩個分頁各一份、最後存的蓋掉前面」。
- **效能底線**：主迴圈裡每個動作控制在幾毫秒內。較重的計算（戰前勝算每次模擬 40 場、季末掃全部角色）移到主迴圈外；戰前勝算依陣容快取（CLAUDE.md 說有快取，其實現在沒有）。

### 5.2 LLM 工作（都在主迴圈外面）

| 用途 | 做法 |
|---|---|
| 大勢人物對話 | 你說完話，畫面先顯示「對方沉吟中…」，背景問模型；回應回來後當成一個動作套用（扣體力、情誼、話題分類）再推給你。模型叫不動時：那一輪不扣體力、對話結束（企劃者 2026-10-02 試玩後決定） |
| 煉製新配方取名 | 背景取名，取好再進主迴圈登記；不再卡住全服 27～83 秒 |
| 戰鬥回合敘述 | 回合先用系統文字立刻結算；模型潤色的文字晚一點補上，太慢就不補 |
| 重複造訪、重複事件的潤色 | 同上，來得及才加 |

- **排隊**：顯卡同時只處理幾件【預設】；每個人同時最多一件在排隊；畫面看得到前面還有幾件。顯卡容量與要不要上雲端是子項目三。

### 5.3 推送

- 每個開著的分頁一條 WebSocket，伺服器只推有變化的部分；取代現在每個分頁每 10 秒重畫 38 個區塊（約 14.5 KB）的做法。

## 六、帳號與登入 【定；數字預設】

- **過渡版**：封測前的朋友試玩先用帳號密碼（`2026-10-03-帳號密碼登入-design.md`，已實作於 `a0bdf1c`）：帳號與名號分開、一個帳號一個角色。封測時在同一個帳號上加 LINE／Google 登入方式，角色不用動；帳號資料在第 1 期搬進 SQLite。
- **登入**：LINE 登入或 Google 登入（伺服器處理授權回傳）。只記「哪個登入服務＋那邊的使用者編號」，不存 email 等個資。
- **邀請碼**：每個帳號第一次登入時輸入一次；管理者產生，可設可用次數，記得被誰用掉。正式上線時拿掉這一步。
- **登入狀態**：存在瀏覽器的安全 cookie（只給伺服器讀、只走 HTTPS），30 天【預設】有效，可以登出。
- **一個帳號在一服只有一個角色**【預設】：名號在建立角色時取，同服不重複，**比對不分大小寫**（從根本堵掉現在「打 rayal 也能拿到 Rayal 的存檔與管理者權限」的問題）。同一個人用 LINE、Google 各登一次就是兩個帳號；CB 期間不做帳號綁定。
- **管理者**：帳號上的標記，只能在伺服器那台電腦用指令設定，畫面上改不了；管理者的每個動作都記進動作紀錄。
- **假人**：沒有帳號的角色，不能被登入。
- **停權**：帳號上的標記。
- **網域**：LINE、Google 登入要登記固定的回傳網址，Cloudflare Tunnel 也要網域，所以**開封測前買一個網域**（一年約 NT$300～500【估】，買在 Cloudflare 最省事）。開發期間用 ngrok 免費版或 Cloudflare 臨時網址（trycloudflare）；兩者的流量、請求數或網址會變，都不適合三百人的封測。

## 七、網頁前端 【定；技術預設】

- **混合做法**：主要畫面做成獨立的網頁應用程式（Vue 3【預設】），伺服器只給資料；大地圖、小地圖與江湖紀錄先沿用伺服器產生的 SVG、HTML。

| 用 Vue 做（伺服器給資料） | 沿用伺服器產生的畫面 |
|---|---|
| 登入、建立角色 | 大地圖、小地圖（SVG，點地點靠 `data-loc`） |
| 場景：文字與選項按鈕（選項不再限 10 個） | 江湖紀錄（`journal.py` 的 HTML） |
| 狀態列：名號、陣營、體力、氣血 | 戰報詳情 |
| 大勢與三方態勢 | |
| 傳聞四層、我的見聞、「你不在的時候」 | |
| 大勢人物對話（「沉吟中…」、排隊還有幾件） | |
| 門下：名冊、人物卡、武學欄、煉製 | |
| 全服決戰面板 | |
| 管理者面板 | |

- **資料格式**：數字、清單、選項等有結構的東西用 JSON；大段敘述文字（場景描寫、事件內文）沿用現在的 Markdown，交給前端顯示，引擎不必把每段文字拆成結構。
- **版面**：以手機為主——主畫面是場景加選項，底部一排分頁切換地圖、門下、傳聞、江湖史、戰報；電腦上地圖和場景並排。
- **連線狀態**：右上角顯示；斷線時動作先排著，重連後自動送出（5.1 的流水號）。

## 八、部署、更新與備份 【定；數字與路徑預設】

### 8.1 兩個資料夾

| | 開發版 | 線上版 |
|---|---|---|
| 位置 | `C:\Ray\專案\ai遊戲` | 另一份獨立的程式，例如 `C:\tianxia-live\app`【預設】 |
| 程式版本 | 隨時在改 | 固定在一個發布的版本 |
| 資料 | 開發用的測試資料 | `C:\tianxia-live\data`（資料庫、紀錄檔） |
| 連接埠 | 另一個 | 線上專用 |
| 對外 | 需要時用 ngrok 免費版或 trycloudflare | Cloudflare Tunnel＋自己的網域 |

- 登入用的密鑰（LINE、Google 的金鑰、cookie 簽章）放在線上版自己的設定檔，**不進 git**。

### 8.2 發布

1. 選一個全部測試與整季模擬都通過的 commit，打版本標籤（例如 `cb-20261015-1`）。
2. 發布腳本：線上版切到那個標籤 → 安裝套件 → 資料庫結構有變就先搬資料 → 無縫重啟。
3. 發布前自動備份一次資料庫。

### 8.3 三種更新

| 改了什麼 | 怎麼上線 | 玩家感覺 |
|---|---|---|
| 只改內容或數字 | 發布後，管理者面板按「重新載入內容」：先跑內容檢查（`content.py::validate`），通過才整批換上，不通過保留舊的 | 沒感覺 |
| 改程式 | 無縫重啟：舊程式做完手上那個動作、存好、關掉；新程式從資料庫載入接手，約幾秒 | 幾秒「連線中…」 |
| 大改版 | 管理者開「維護模式」：全服公告、賽季時鐘暫停、擋住所有動作；做完再關 | 停機 2～4 小時 |

### 8.4 讓它一直開著

- 遊戲伺服器、Cloudflare Tunnel（`cloudflared`）、Ollama 都設成 Windows 服務：開機自動啟動、當掉自動重開、不用登入 Windows 也會跑。
- 電腦關掉睡眠；Windows 更新設定只在離峰時段重開機。

### 8.5 備份

- 每天一次，加上每次發布前：用 SQLite 內建的線上備份做一份，複製到雲端硬碟的同步資料夾（OneDrive 或 Google Drive）。
- 保留最近 14 天每天一份，加上 8 週每週一份【預設】；每個月實際還原一次，確認備份能用。

### 8.6 出事怎麼知道

- 一個健康檢查網址；錯誤寫進紀錄檔；管理者面板看得到最近的錯誤與在線人數。
- 要不要另外推通知（例如 Discord）等封測時再看。

## 九、壓測與驗收 【定；目標預設】

### 9.1 兩層壓測

1. **引擎層，假時鐘跑一整季**：三千個假人角色在伺服器程式裡直接跑完一季；量測每個動作在主迴圈裡花多久、記憶體、資料庫大小、季末結算時間。
2. **網路層，模擬真的瀏覽器**：另寫一支壓測程式，開幾千條連線，從登入、送動作到收推送都走真的網路介面。動作頻率照真人估（每人每 10～30 秒一個）；LLM 用模擬的，延遲 5～20 秒。連續跑 1～2 小時。
   - 登入用一個**只在測試環境才開**的後門；線上版不會有。
   - 三千條連線在本機直接連（不經過 Cloudflare，免得被當成攻擊）；經過 Cloudflare Tunnel 另外用三百條測一次。

### 9.2 目標

| 項目 | 目標 |
|---|---|
| 三千人在線、尖峰每秒 300 個動作 | 九成五的動作 0.2 秒內有回應，主迴圈裡不到 0.05 秒；沒有錯誤 |
| 推送 | 九成五在 1 秒內送到 |
| 記憶體 | 2 GB 以內 |
| 帶著玩家無縫重啟 | 10 秒內恢復，沒有動作遺失、也沒有重複執行 |
| 三千人的季末結算 | 背景 1 分鐘內算完，期間主迴圈沒有卡超過 0.2 秒 |
| LLM 很慢時 | 主迴圈完全不受影響 |

### 9.3 開封測之前要通過的關卡

1. 全部測試與整季模擬通過。
2. 經過 Cloudflare Tunnel 的三百人壓測達標。三千人的本機壓測照跑、結果當參考；**三千人達標是正式開放前的關卡**（第一節）。
3. 實際用備份還原過一次。
4. 帶著連線中的玩家做過一次無縫重啟。
5. 安全檢查：只能用 LINE／Google＋邀請碼登入；管理者只認帳號標記；限速有效；密鑰沒有進 git；測試用的登入後門在線上版是關的。

- 既有的測試全部維持通過。
