# 三國同伴好感度整合 — 設計

- 日期：2026-09-30
- 狀態：企劃階段定案，可以開始實作
- 分支：`feature/sanguo-companions`（base：`tianxia`，獨立於 `feature/conquest-route-redesign`）
- 背景：把 `ai_story`（原本的征服路線引擎）與 `ai_story-tianxia`（天下大勢原型）合併成同一個專案。
  兩邊是同工作室、同一個起點分出去的專案，不是外部依賴，可以自由重組。

---

## 一、範圍

**保留 tianxia 的部分**：體力／行動經濟、地圖（`atlas.py`/`mapview.py`）、事件骨架
（`content/events/*.json`）、大勢線與賽季結構。

**不保留 tianxia 的部分**：`battle.py` 三對三全自動戰鬥系統、多隊派遣系統（`roster.py`/
`team.py` 圍繞 `team_count`/`command_cap` 的邏輯，見四.4）、招賢抽卡系統（企劃者不要做
成抽卡遊戲，見四.4）。

**從 ai_story 移植的部分**：`src/npc_agent.py` 的「LLM 每回合生成對話 + tag 查表決定
好感度變化（不信任 LLM 自報數字）+ 關係現況記憶」核心機制，**不含**
`intimate_mode.py`/`scene_templates.py`/`ending_writer.py`/`rwkv_client.py`（性愛模式與
結局劇情相關的東西全部不搬）。

**世界觀**：改成三國（史書公版，人物/地名/事件可以直接用真實名字，不用擔心版權——這點
跟 tianxia 原本「金庸人名一律原創」的規則不同，是這次明確的方向調整）。

## 二、現況盤點（讀過雙邊程式碼後的結論）

- tianxia 的 `Member`（`tianxia/state.py`）目前只有 `level`/`exp`/`neili`/`innate_level`，
  **沒有好感度欄位**，需要新增。
- tianxia 的同伴目前是純資料（`content/characters.json`：品階/統御/流派/武學/取得管道），
  沒有個性化對話、沒有記憶——這正是要從 ai_story 補進去的部分。
- ai_story 的好感度機制（`src/rules.py`／`src/npc_agent.py`）是圍繞「單一路線走向終局
  （好結局 80 / 黑化 -50）」設計的，多人賽季制沒有這種終局概念，直接照搬會不合邏輯。
- ai_story 的 `NPCAgent` 呼叫 Ollama 是**每回合都要**（游戲核心玩法依賴即時 LLM）；
  tianxia 的既有原則是「規則引擎決定一切數值，AI 選用、逾時直接退回原始文字」——這條
  原則本身是好的工程實踐（多人賽季遊戲不能讓單次 LLM 逾時卡住一個行動），不是「因為
  是 Ray 的規則所以要遵守」，是獨立於歸屬的正確設計，這次移植會延續。

## 三、整合設計

### 3.1 新模組：`tianxia/companion_agent.py`
從 `src/npc_agent.py` 移植並精簡：
- 保留：`_build_messages`/`_record_turn` 對話歷史管理、schema-constrained JSON 輸出、
  tag 查表決定數值變化（不信任 LLM 自報）、`npc_relationship_note` 保底機制、記憶梳理
  （`consolidate_memory`，20 回合一次）、連線失敗/解析失敗時的 fallback（改用 tianxia
  已有的事件骨架當保底，不用另外設計一套 fallback 文案庫）。
- 移除：`intimacy_tags` 裡黑化方向的用語、`bad_ending_flow`、`character_tags` 那一整套
  情慾向標籤。

### 3.2 `Member` 新增欄位（`tianxia/state.py`）
```python
affinity: int = 0            # 0~100，見四.2
relationship_note: str = ""  # 沿用 ai_story 的「一句話關係現況」保底機制
```
舊存檔沒有這兩個欄位時預設 0/空字串，不用遷移腳本。

### 3.3 觸發點：交遊
所有交遊都走 `companion_agent.py` 的即時對話（一段個性化敘事 + 2~3 個帶 tag 的選項），
系統照 tag 查表更新 `affinity`（範圍見四.3，全部 15 位黃巾之亂人物開放，不分主次）。

### 3.4 好感度門檻的效果
不做「終局」，改成解鎖對話話題深度、專屬奇遇事件鏈、情誼滿門檻習得對方本命武學
（詳見七）。

## 四、企劃者決策

### 4.1 拿掉戰鬥後，「歷練」改名「練功」，`battle.py` 整套不用【定】
不沿用「Check 機制簡化處理」，改成**另外設計一套全新武學系統**（見六），玩家有初始
武學，武學帶品質／熟練度／威力／屬性四個欄位。

### 4.2 好感度數值範圍【定】
0~100 單向「情誼」，不做黑化/雙向。

### 4.3 深度 LLM 對話開放範圍與性格漂移架構【定】
**這一季（黃巾之亂）出現的歷史人物全部開放深度 LLM 對話**，不分主次——這款遊戲的核心
賣點就是「跟史實個性鮮明的歷史人物互動」。人物名單見獨立文件
`docs/superpowers/specs/2026-09-30-黃巾之亂人物誌-draft.md`（15 位，含出身/此時處境/
性格基礎模板）。

**性格漂移必須是真的跨玩家共享，不能只是存檔內的單機模擬**。tianxia 現在本來就是
**一個 Gradio process 服務所有連進來的玩家**（跟 conquest-route 用 `*.gradio.live`
分享連結的部署方式相同），所以「真的跨玩家共享」**不需要重新設計一套 client-server
系統**，只要新增一份獨立於各玩家存檔之外的**共用世界狀態儲存**（例如 `saves/world/`
底下一份 JSON 或輕量 SQLite，記錄每位歷史人物目前被集體漂移到什麼性情），所有玩家的
每次交遊都讀寫同一份資料，用檔案鎖或資料庫交易避免同時寫入衝突。資料分兩層：
- **固定史實性格模板**（人物誌文件裡的「性格」欄）：寫死進 `companion_agent.py` 的
  system prompt，是永遠不會消失的錨點。
- **當下性情漂移值**（新的共用世界狀態）：由所有玩家累積的交遊 tag 慢慢推移，同一位
  歷史人物在所有玩家眼中都是同一個、正在被集體形塑的性情狀態。

### 4.4 招募制度：唯一角色、自由競爭、決鬥風險【定】
不沿用 tianxia 既有招賢抽卡模式（每人各自招到自己的一份副本）——企劃者明確表示不要做
成抽卡遊戲，改成：
- **每位歷史人物全服唯一**：不是每個玩家各自擁有一份獨立副本，是全服只有一個「劉備」，
  被誰招走了別人就招不到。人物誌裡可招募的 7 位（曹操/劉備/關羽/張飛/孫堅/袁紹/陶謙）
  是**稀缺、被搶奪的目標**，龍頭人物（張角等 8 位）維持不可招募。
- **招募是高難度、有風險的玩家行動**：玩家之間可以自由互動、搶著招募同一位人物；貿然
  嘗試或手法不對，可能直接惹惱武將，導致他要求與你**決鬥**（不是溫和地拒絕，是有敵意
  後果的失敗）。具體判定規則（難度怎麼算、決鬥輸了有什麼代價）留給實作階段設計，但
  「唯一、可搶、失敗有代價」這三個原則已經定案。
- **每位玩家最多帶 4 個夥伴，只有一支隊伍**，不是 tianxia 原本依幕數開放到 4 隊、統御
  上限逐步放大的多隊派遣設計。`roster.py`/`team.py` 裡圍繞 `team_count`/`command_cap`/
  隊伍依幕數開放/換人在多隊之間搬動的邏輯全部是要砍掉的死程式碼；`content/config.json`
  的 `team_counts`/`command_caps` 等對應設定欄位也一併移除。派遣（派同伴出去辦事，
  一段時間後回報）這個「行動」本身在核心循環仍然保留，但不再是「派一整支獨立隊伍
  出征」，怎麼跟單隊 4 人上限共存（例如派遣時暫時把人從隊伍抽走）留給實作階段設計。

## 五、三國重皮範圍（原型階段，1 大區）

比照 tianxia 原型範圍（1 大區、20~30 地點、30~50 事件），這次重皮只需要在**既有內容量**
上改名字/背景，不用新增內容量：
- `content/characters.json`：換成人物誌文件裡的 15 位歷史人物（7 可招募＋8 龍頭），

- `content/locations.json`/`content/map.json`：地點改真實三國地名（先鎖同一大區規模，

- `content/scenario.json`：大勢線劇本改三國史事骨架，第一季「黃巾之亂」，埋入傳國玉璽

- `content/skills.json`：武學名稱改用三國背景合理的兵法/武藝名稱。

## 六、新武學系統（取代 `battle.py`）

### 6.1 武學的四個欄位
- **品質**：武學本身的檔次（下品／中品／上品／絕學），決定威力上限與取得難度，寫在
  `content/skills.json` 是靜態欄位，不隨遊玩改變。
- **熟練度**：練功練出來的，沿用 tianxia 原本「成」（第一成～第十成）的概念。
- **威力**：由品質＋熟練度算出的衍生數值，判定時真正拿來比較的數字。
- **屬性**：武學的相剋標籤。直接撿回 tianxia 自己設計文件（design.md §六）裡原本就寫
  好、但從沒真的做出來的「內功陰陽剛柔、招式快慢虛實」相剋概念，不重新發明命名。

### 6.2 練功兩種模式【定】
不是單純花資源換熟練度，是兩種明確不同的模式，給玩家真正的取捨：

- **(a) 自創功法**：玩家自己取名一門新武學，**系統依名字用某種演算法決定這門武學的
  屬性／威力／成長性**（名字本身就是「配方」，不是裝飾）——玩家可以透過取名嘗試摸索
  什麼樣的名字傾向長出什麼樣的屬性與強度，等於用取名當一個隱性的鍊金小遊戲。**武學
  名稱全服不能重名**，第一個取到某個名字的人就佔住了這個名字，這代表共用世界狀態
  （四.3）除了性格漂移，還要多存一份「已被佔用的武學名稱」清單，用同一份共用資料庫
  解決。演算法細節（例如取名字的字元/筆畫數/五行偏旁映射到屬性）留給實作階段提案。
- **(b) 鍛鍊**：練現有已學會的武學，熟練度加深、威力提高。

**絕學品質的取得方式**：自創功法**仍然可以抽到絕學，只是機率極小**——不是結構性禁止，
是機率上近乎不可能，維持「取名有機會一夜暴富」的幻想與樂趣。本命武學（情誼滿門檻習得，
見七）則是**穩定給絕學**，不用賭——本命武學是唯一可靠的絕學來源，自創功法的絕學是
意外之喜、不是可規劃的策略，這樣不會出現「練好感度反而不如亂取名」的反直覺結果。
具體機率數字留給實作階段用模擬器調。

**受傷風險**：練得越猛（消耗體力越多／選擇的強度越高）熟練度漲越快，但累積受傷風險，
失手扣氣血、留下內傷——直接沿用 Ray 同日寫的「氣血門戶名冊」設計文件
（`2026-09-30-氣血門戶名冊-design.md`）既有的輕傷/內傷/療傷機制，不另外發明一套。

### 6.3 拿掉戰鬥後，遭遇與劇情戰怎麼判定？【定】
單次判定：我方隊伍武學總威力（含屬性相剋加成）vs 對手難度值，擲一次骰直接出結果等級
（大勝/險勝/僵持/落敗），文字帶過，不是回合制。威力數字因此有實際用武之地（驗證練功
有沒有效），也不用重建 `battle.py` 那套陣型/回合的複雜工程。

### 6.4 學習上限【定】
每人最多學一門內功、一門武學（不管是自創或鍛鍊別人教的），不是 tianxia 原本「本命＋
自選 1＋自選 2」三武學欄的設計——收斂建置空間，逼玩家在「自創獨門絕學」跟「鍛鍊已知
武學」之間做選擇，也讓「威力」數字集中在少數幾個決定性的數字上，跟 6.3 的單次判定
天生合拍。

### 6.5 賽季榜單【定】
賽季會有**天下武學榜**與**內功榜**（依威力排名），是玩家的具體終局目標之一——跟七.3
「效忠陣營／史事推進」是兩條並行的個人成就線，一條是「你在這段史事裡站在哪一邊」，
一條是「你（或你創的武學）在天下武學排名上留下什麼紀錄」，兩者都會寫進賽季結束的
江湖史。

## 七、好感度的用途與玩家方向

### 7.1 好感度只管內容解鎖，不碰數值【定】
好感度**不**混進任何數值/成功率效果（連派遣成功率加成也排除），純粹當內容解鎖的開關：
- 解鎖對話話題深度、專屬奇遇事件鏈（沿用 ai_story 已有的 `npc_stages.json`
  `unlocked_topics` 概念）。
- **情誼夠高才能習得對方的本命武學**——情慾版本裡「好感度夠高她願意為你敞開」的機制
  骨架，改成「情誼夠高她願意傾囊相授本命武學」，同一套門檻判定邏輯換一個適合多人場景
  的收穫；學到的武學進六的練功/威力系統，但**觸發條件是好感度**，威力本身不是好感度
  直接給的數字（且穩定是絕學品質，見 6.2）。

### 7.2 提升方式
主要交遊互動（LLM 對話，tag 決定漲跌）；次要送禮、同隊出戰累積、事件鏈抉擇。

### 7.3 玩家的方向感：用三國知名歷史時期切分賽季【定】
不做「固定魏/蜀/吳陣營」，而是**每季主題劇本＝一段知名三國史事**（第一季「黃巾之亂」），
理由是限縮玩家活動範圍與聚焦目的——這正好對上 tianxia 原本設計文件裡「每季抽一個主題
劇本，劇本內有骨架，走向由玩家推動」（design.md §4.1）的既有機制，只是把「主題劇本」
的內容具體定為三國史事順序（黃巾之亂 → 董卓亂政/群雄割據 → 官渡/赤壁……視原型範圍
再定要做到哪一段）。**由此衍生、待實作階段細化**：每季的陣營/效忠選擇會跟著那一季的
史事換（黃巾之亂季是「黃巾軍／官軍／地方豪強」三選，不是一路到底的魏蜀吳），陣營設計
因此是**逐季內容**，不是一次性的系統。

## 八、LLM 整合架構

### 8.1 規模【定】
工作室內部小規模試玩，十幾人以內。**結論：不需要設計非同步佇列/背景任務系統**——本機
單張 GPU 同步呼叫 Ollama 就夠撐，跟目前 conquest-route 單人版的呼叫方式一樣（沿用既有
Gradio streaming generator 模式即可）。如果之後真的要對外開放到更大規模，這是需要回頭
重新設計的地方（本機單 GPU 會變瓶頸），但**現在不先做這個工程**——沒有實際人數壓力時
先做佇列/非同步是過度工程，YAGNI。

### 8.2 LLM 的用途
1. **交遊深度對話**（核心機制，四.3）。
2. **遭遇/劇情戰結算的敘事潤色**：結果等級由規則引擎決定，「怎麼贏的」那段描述選用
   LLM 潤色，失敗直接退回範本文字，跟一般行動用同一次同步呼叫完成即可。
3. **開發期內容量產**（三國重皮的人物/地點/武學初稿），沿用 tianxia 原本規劃。
4. **重複內容的潤色**（一般地點重複造訪、事件重複觸發、世界事件傳聞）：固定文字後面
   加一小段即時生成的裝飾句，失敗直接省略；重要地點（手寫內容）不加；世界事件傳聞
   全服只潤色一次、所有玩家共用同一份結果，不是每個玩家各自呼叫一次。**優先度低於
   交遊系統**，實作順序排在核心機制之後。
5. **可靠度機制直接繼承 conquest-route 的教訓**：schema 只要求核心欄位、好感度 tag
   查表不信任 LLM 自報數字、里程碑類通知用系統偵測狀態轉換而非問 LLM（例如好感度跨階、
   學會本命武學都是系統判定觸發）、定期記憶梳理避免「劇情沒有累積感」。

## 九、跨季終極目標：傳國玉璽

### 9.1 世界觀設定【定】
接上**真實歷史裡本來就有的傳國玉璽傳說**（和氏璧所刻，孫堅曾在洛陽井中拾得、袁術曾
憑此稱帝的那個真實記載的天命象徵物），不是憑空發明新聖物——放大加料成「仙人賜予、
附有神力、因故裂成七塊」。張角能習得太平要術、引發黃巾之亂，正是因為他取得了其中一塊
（嫁接演義裡「南華老仙傳授太平要術」的既有情節，南華老仙即碎片的持有者/化身，人物誌
裡張角的出身描述不用改，只是多一層因果）。

### 9.2 七塊碎片＝跨季長線，不是單季目標【定】
每塊碎片對應一段知名三國史事的轉折點（黃巾之亂一塊在張角手上；後續季別可以放在董卓
之亂／孫堅真實撿到玉璽那段史實橋段、官渡、赤壁……視之後開的季別而定），呼應七.3
「每季鎖一段史事」的設計。七塊碎片是**繼武學圖鑑、同伴名冊之後第三個跨季收藏類別**
（見 design.md §十 跨季傳承表），一季只揭曉/爭奪一塊，留懸念給下一季。

### 9.3 奪得碎片＝全服「躍進」事件，不是個人結局【定】
不做成單一玩家的個人結局，改用 tianxia 原本設計文件裡本來就有、但還沒真正實作的
「躍進」機制（design.md §4.3：稀有奇遇讓大勢線一次大幅跳升，「一個人改變江湖的
時刻」）：奪得碎片是極低機率、極高難度的奇遇，誰達成都一樣——觸發全服「天機」事件，
把當季大勢線直接推向終局、開啟下一幕。達成的玩家在江湖史留名（跟武學榜一樣是個人
成就線），但不會讓遊戲因為一個人的行動就對其他人提前結束，維持「共享江湖」的設計
精神不被打破。
