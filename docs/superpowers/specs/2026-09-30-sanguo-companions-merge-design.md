# 三國同伴好感度整合 — 設計

- 日期：2026-09-30
- 狀態：企劃階段，待確認三個開放決策後開工
- 分支：`feature/sanguo-companions`（base：`tianxia`，獨立於 `feature/conquest-route-redesign`）
- 背景：把 `ai_story`（原本的征服路線引擎）與 `ai_story-tianxia`（天下大勢原型）合併成同一個專案。
  兩邊是同工作室、同一個起點分出去的專案，不是外部依賴，可以自由重組。

---

## 一、範圍

**保留 tianxia 的部分**：體力／行動經濟、地圖（`atlas.py`/`mapview.py`）、事件骨架
（`content/events/*.json`）、大勢線與賽季結構、門下名冊與隊伍、招賢抽卡。

**不保留 tianxia 的部分**：`battle.py` 三對三全自動戰鬥系統（本次明確排除）。

**從 ai_story 移植的部分**：`src/npc_agent.py` 的「LLM 每回合生成對話 + tag 查表決定
好感度變化（不信任 LLM 自報數字）+ 關係現況記憶」核心機制，**不含**
`intimate_mode.py`/`scene_templates.py`/`ending_writer.py`/`rwkv_client.py`（性愛模式與
結局劇情相關的東西全部不搬）。

**世界觀**：改成三國（史書公版，人物/地名/事件可以直接用真實名字，不用擔心版權——這點
跟 tianxia 原本「金庸人名一律原創」的規則不同，是這次明確的方向調整）。

## 二、現況盤點（讀過雙邊程式碼後的結論）

- tianxia 的 `Member`（`tianxia/state.py`）目前只有 `level`/`exp`/`neili`/`innate_level`，
  **沒有好感度欄位**，需要新增。
- tianxia 的同伴目前是純資料（`content/characters.json`：品階/統御/流派/武學/取得管道），
  沒有個性化對話、沒有記憶——這正是要從 ai_story 補進去的部分。
- ai_story 的好感度機制（`src/rules.py`／`src/npc_agent.py`）是圍繞「單一路線走向終局
  （好結局 80 / 黑化 -50）」設計的，多人賽季制沒有這種終局概念，直接照搬會不合邏輯。
- ai_story 的 `NPCAgent` 呼叫 Ollama 是**每回合都要**（游戲核心玩法依賴即時 LLM）；
  tianxia 的既有原則是「規則引擎決定一切數值，AI 選用、逾時直接退回原始文字」——這條
  原則本身是好的工程實踐（多人賽季遊戲不能讓單次 LLM 逾時卡住一個行動），不是「因為
  是 Ray 的規則所以要遵守」，是獨立於歸屬的正確設計，這次移植會延續。

## 三、整合設計

### 3.1 新模組：`tianxia/companion_agent.py`
從 `src/npc_agent.py` 移植並精簡：
- 保留：`_build_messages`/`_record_turn` 對話歷史管理、schema-constrained JSON 輸出、
  tag 查表決定數值變化（不信任 LLM 自報）、`npc_relationship_note` 保底機制、記憶梳理
  （`consolidate_memory`，20 回合一次）、連線失敗/解析失敗時的 fallback（改用 tianxia
  已有的事件骨架當保底，不用另外設計一套 fallback 文案庫）。
- 移除：`intimacy_tags` 裡黑化方向的用語、`bad_ending_flow`、`character_tags` 那一整套
  情慾向標籤。

### 3.2 `Member` 新增欄位（`tianxia/state.py`）
```python
affinity: int = 0            # 0~100，見四.2 的開放決策
relationship_note: str = ""  # 沿用 ai_story 的「一句話關係現況」保底機制
```
舊存檔沒有這兩個欄位時預設 0/空字串，不用遷移腳本。

### 3.3 觸發點：交遊
`tianxia/roster.py`/事件骨架目前的「交遊」是純事件骨架驅動。這次改成：同伴的
`content/characters.json` 標記 `deep_interaction: true` 的人，交遊時改走
`companion_agent.py` 的即時對話（一段個性化敘事 + 2~3 個帶 tag 的選項），系統照 tag
查表更新 `affinity`；沒標記的同伴維持原本的事件骨架/範本文字，兩條路徑並存，不用把
全部 14 位同伴都換成 LLM 對話（見四.3 的開放決策）。

### 3.4 好感度門檻的效果
不做「終局」，改成解鎖：對話話題深度（比照 ai_story 已經閒置在 `npc_stages.json` 的
`unlocked_topics` 概念）、小額屬性加成、專屬奇遇事件——具體門檻數字與效果留給實作階段
用模擬器（`scripts/simulate.py`）調。

## 四、企劃者決策（2026-09-30 確認）

### 4.1 拿掉戰鬥後，「歷練」改名「練功」，`battle.py` 整套不用
**不採用**原本建議的「沿用 Check 機制簡化處理」，改成**另外設計一套全新武學系統**
（見第六節），玩家有初始武學，武學帶品質／熟練度／威力／屬性四個欄位。

### 4.2 好感度數值範圍【定】
0~100 單向「情誼」，不做黑化/雙向。企劃者確認採用建議方案。

### 4.3 深度 LLM 對話開放範圍【待後續專門討論】
企劃者要另開一輪討論，這份文件先不定案，`companion_agent.py`/`deep_interaction` 欄位的
設計維持第三節寫的「並存、可逐位開關」彈性即可，不用現在決定確切名單與數量。

## 五、三國重皮範圍（原型階段，1 大區）

比照 tianxia 原型範圍（1 大區、20~30 地點、14 位同伴、30~50 事件），這次重皮只需要
在**既有內容量**上改名字/背景，不用新增內容量：
- `content/characters.json`：14 位同伴的姓名/背景改成三國人物或原創武將，統御/品階/武學
  數值不動。
- `content/locations.json`/`content/map.json`：地點改真實三國地名（先鎖同一大區規模，
  例如「中原」或「江東」）。
- `content/sects.json`：門派概念在三國語境下改成「勢力／陣營」（例如曹營、劉備陣營），
  或保留「武學傳承」意義上的門派（例如黃巾餘部、某位名師的兵法傳人）——具體怎麼對應
  留給實作階段，先不在這份文件定案。
- `content/scenario.json`：大勢線劇本改三國史事骨架（例如「黃巾之亂」「群雄割據」），
  走向仍由玩家推動，不是照抄史書結局。
- `content/skills.json`：武學名稱改用三國背景合理的兵法/武藝名稱。

## 六、新武學系統草案（取代 `battle.py`）— 待確認

### 6.1 武學的四個欄位
- **品質**：武學本身的檔次（例如下品／中品／上品／絕學），決定威力上限與取得難度，寫在
  `content/skills.json` 是靜態欄位，不隨遊玩改變。
- **熟練度**：練功練出來的，沿用 tianxia 原本「成」（第一成～第十成）的概念，不用發明
  新名詞。
- **威力**：由品質＋熟練度算出的衍生數值，判定時真正拿來比較的數字。
- **屬性**：武學的相剋標籤。**建議直接撿回 tianxia 自己設計文件（design.md §六）裡原本
  就寫好、但從沒真的做出來的「內功陰陽剛柔、招式快慢虛實」相剋概念**，不用重新發明一套
  命名——這是原本規劃要做、只是先跳去做 3v3 戰鬥系統的東西，現在拿掉戰鬥正好撿回來用。

### 6.2 練功怎麼運作
花體力／時間資源換熟練度成長，不判定成功失敗——練就是練，跟「遭遇/劇情戰打不打得過」
的判定分開。

### 6.3 拿掉戰鬥後，遭遇與劇情戰怎麼判定？【定】
採方案 (a) 單次判定：我方隊伍武學總威力（含屬性相剋加成）vs 對手難度值，擲一次骰直接
出結果等級（大勝/險勝/僵持/落敗），文字帶過，不是回合制。威力數字因此有實際用武之地
（驗證練功有沒有效），也不用重建 `battle.py` 那套陣型/回合的複雜工程。

## 七、好感度的用途與玩家方向（2026-09-30 確認）

### 7.1 好感度只管內容解鎖，不碰數值【定】
**推翻**六.1 之前討論時我提過的「同行戰力加成」構想——企劃者明確要好感度**不要**混進
任何數值/成功率效果，純粹當內容解鎖的開關。套用同一個原則，「派遣成功率加成」這類
好感度直接影響數字的提案也一併排除，不只排除戰力加成。好感度能做的事只剩：
- 解鎖對話話題深度、專屬奇遇事件鏈（沿用 ai_story 已有的 `npc_stages.json`
  `unlocked_topics` 概念）。
- **情誼夠高才能習得對方的本命武學**【定】——情慾版本裡「好感度夠高她願意為你敞開」
  這個機制骨架，改成「情誼夠高她願意傾囊相授本命武學」，同一套門檻判定邏輯換一個
  適合多人場景的收穫；學到的武學進第六節的練功/威力系統，但**觸發條件是好感度**，
  威力本身不是好感度直接給的數字。

### 7.2 提升方式維持原提案
主要交遊互動（LLM 對話或事件骨架，tag 決定漲跌）；次要送禮、同隊出戰累積、事件鏈抉擇
（7.1 的原則只限制好感度的「用途」不碰數值，不影響好感度本身「怎麼漲」的來源）。

### 7.3 玩家的方向感：用三國知名歷史時期切分賽季【定】
企劃者選的不是「固定魏/蜀/吳陣營」，而是**每季主題劇本＝一段知名三國史事**（例如第一季
「黃巾之亂」），理由是限縮玩家活動範圍與聚焦目的，避免滿世界亂跑不知道幹麻——這正好
對上 tianxia 原本設計文件裡「每季抽一個主題劇本，劇本內有骨架，走向由玩家推動」
（design.md §4.1）的既有機制，不用另外發明系統，只是把「主題劇本」的內容具體定為
三國史事順序（黃巾之亂 → 董卓亂政/群雄割據 → 官渡/赤壁……視原型範圍再定要做到哪一段）。
**由此衍生、待實作階段細化**：每季的陣營/效忠選擇會跟著那一季的史事換（黃巾之亂季是
「黃巾軍／官軍／地方豪強」三選，不是一路到底的魏蜀吳），陣營設計因此是**逐季內容**，
不是一次性的系統，跟第五節「三國重皮」的 `content/scenario.json` 規劃銜接。

## 八點五、LLM 整合架構（2026-09-30 確認）

### 8.5.1 規模【定】
工作室內部小規模試玩，十幾人以內。**結論：不需要設計非同步佇列/背景任務系統**——本機
單張 GPU 同步呼叫 Ollama 就夠撐，跟目前 conquest-route 單人版的呼叫方式一樣（沿用既有
Gradio streaming generator 模式即可）。如果之後真的要對外開放到更大規模，這是需要回頭
重新設計的地方（本機單 GPU 會變瓶頸），但**現在不先做這個工程**——沒有實際人數壓力時
先做佇列/非同步是過度工程，YAGNI。

### 8.5.2 LLM 的四個用途（確認）
1. **交遊深度對話**（4.3 的核心機制，範圍見下）。
2. **遭遇/劇情戰結算的敘事潤色**：結果等級（大勝/險勝/僵持/落敗）由規則引擎決定，
   「怎麼贏的」那段描述選用 LLM 潤色，失敗直接退回範本文字——因為規模小、同步呼叫
   可接受，**不需要 8.5.1 提到的背景生成/非同步替換**，跟一般行動用同一次同步呼叫
   完成即可，簡化了原本設想的複雜度。
3. **開發期內容量產**（三國重皮的人物/地點/武學初稿），沿用 tianxia 原本規劃。
4. **可靠度機制直接繼承 conquest-route 的教訓**：schema 只要求核心欄位、好感度 tag
   查表不信任 LLM 自報數字（已定案）、里程碑類通知用系統偵測狀態轉換而非問 LLM
   （例如好感度跨階、學會本命武學都是系統判定觸發，不是 LLM 自己決定要不要提）、
   定期記憶梳理避免「劇情沒有累積感」。

### 4.3（最終定案）深度 LLM 對話開放範圍與性格漂移架構
**推翻**原本「先選 3~5 位看板角色試點」的建議。企劃者決定：**這一季（黃巾之亂）出現的
歷史人物全部開放深度 LLM 對話**，因為這款遊戲的核心賣點就是「跟史實個性鮮明的歷史人物
互動」，人物名單見獨立文件
`docs/superpowers/specs/2026-09-30-黃巾之亂人物誌-draft.md`（15 位，含出身/此時處境/
性格基礎模板）。

**性格漂移必須是真的跨玩家共享，不能只是存檔內的單機模擬**——這是企劃者明確推翻我原本
「先做存檔內版本、以後再升級成共享」的折衷建議後的決定。修正後的架構理解：tianxia 現在
本來就是**一個 Gradio process 服務所有連進來的玩家**（跟 conquest-route 用
`*.gradio.live` 分享連結的部署方式相同），所以「真的跨玩家共享」**不需要重新設計一套
client-server 系統**，只要新增一份獨立於各玩家存檔之外的**共用世界狀態儲存**（例如
`saves/world/` 底下一份 JSON 或輕量 SQLite，記錄每位歷史人物目前被集體漂移到什麼
性情），所有玩家的每次交遊都讀寫同一份資料，用檔案鎖或資料庫交易避免同時寫入衝突。
資料分兩層：
- **固定史實性格模板**（人物誌文件裡的「性格」欄）：寫死進 `companion_agent.py` 的
  system prompt，是永遠不會消失的錨點。
- **當下性情漂移值**（新的共用世界狀態）：由所有玩家累積的交遊 tag 慢慢推移，同一位
  歷史人物在所有玩家眼中都是同一個、正在被集體形塑的性情狀態。
