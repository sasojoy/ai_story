## 零、一句話

探索事件加三種新玩法：**隨口應對**（自己打一句話應對，LLM 只評成功率，系統擲骰）、**地方痕跡**（大家在一個地點做的選擇會累積，改變之後的人抽到什麼）、**合力事件**（一件事要很多人各出一份力，湊滿了全服都看得到結果）。數值一律由規則決定。

## 一、現況

| | 現在 | 問題 |
|---|---|---|
| 事件選項 | 全部是手寫的固定選項 | 玩家的創意沒有出口；LLM 只在人物對話與決戰出現 |
| 別人的痕跡 | 只有 `Effect.rumor` 會寫一則傳聞 | 你在潁水河畔救了流民，下一個人來看到的河畔還是一模一樣 |
| 全服狀態 | 事件條件可以看大勢（`trend_min/max`）和世界旗標 | 能用，但內容幾乎沒用到；而且只有「全服大勢」這一個尺度，沒有「這個地點」的尺度 |
| 多人協作 | 只有全服決戰 | 決戰一季幾次，平常的探索是純單機 |

## 二、玩法 A：隨口應對（LLM）

### 2.1 玩起來

有些事件多一個選項「自己想辦法……」。按下去出現 20 字的輸入框，玩家寫自己要怎麼做，例如酒樓鬥毆時寫「把酒罈砸在地上大喊官兵來了」。

系統把事件情境和這句話交給 LLM，LLM 只回一個 0～100 的成功率。系統拿這個機率擲骰：成功套用手寫的 `effect`，失敗套用 `fail_effect`。最後 LLM 可以把結果潤色成一兩句敘事，但不能改數值。

這跟決戰的放手一搏是同一套：`SuccessRateJudgment`、`DEFAULT_FREE_TEXT_SUCCESS_RATE = 40`、在鎖外評估。

### 2.2 規則 【預設】

- **只有標了的事件才有**：事件加一個 `free_text` 欄位（提示文字、相關屬性、effect、fail_effect）。不是每則都開；先開在每個地點的一兩則事件上。
- **屬性仍然有用**：LLM 的成功率再按相關屬性修正，每點比 5 高 +4%，比 5 低 −4%。最後夾在 **5%～85%**，所以再會寫也不會穩贏，也不會因為寫得爛就必敗。
- **獎勵不能比手寫選項高**：`free_text` 的 effect 不得超過同一則事件裡最好的那個檢定選項。這個玩法賣的是好玩，不是更划算。內容檢查會擋。
- **防灌水**：LLM 的提示詞寫明「只判斷這個行動在情境裡合不合理」。玩家寫「我必定成功」這種話照樣被評成低機率。上限 85% 也是保險。
- **等待**：本機模型評估實測要 27～83 秒（煉製取名的量測）。比照人物對話的做法：先拿鎖準備、在鎖外呼叫 LLM、再拿鎖確認狀態沒變才套用（`app.prepare_dialogue` 那一套）。介面上按鈕先變成「思量中……」。
- **LLM 連不上**：用保底的 40%，再加屬性修正。遊戲照常能玩。
- **假人不用**：假人不選這個選項，跟決戰一樣。

### 2.3 為什麼值得做

這是本作「LLM 文字遊戲」最直接的賣點：玩家的奇招真的會改變結果的機率。決戰已經證明這套分工可行，而且不違反「數值由規則決定」。

## 三、玩法 B：地方痕跡（多人同服）

### 3.1 玩起來

每個地點記幾個「痕跡」計數，全服共用、每季清空。事件選項可以加痕跡，事件也可以要求痕跡夠多才會出現。

例子：

- **潁水河畔**：選「幫流民搭棚」的人多了（`yingshui:棚屋` ≥ 10），之後的人會抽到新事件「河畔新村」：流民開始種地，有人想拜師、有人想報恩。選「趕走流民」的人多了，則會出現「流民成匪」。
- **潁川書院**：有人在壁上題了一首反詩（選項加痕跡），之後的人抽到「壁上題詩」：可以附和（再加一筆）、塗掉、或抄去報官。附和的人多了，書院會被官府查封一陣子。
- **白馬津**：大家在渡口幫忙還是勒索，決定之後擺渡人對你的價錢與態度。

畫面上用模糊數量呈現：「這一帶已有十來個人幫過流民」。**不列名字**，所以也看不出誰是假人（伺服器假人設計的硬規定）。值得一提的痕跡變化照現有的地方傳聞發出去。

### 3.2 規則 【預設】

- `Effect.marks: {"<地點>:<痕跡>": 數量}`；`Condition.marks_min / marks_max`。痕跡存在全服共用的賽季狀態（`WorldStateStore`），寫入包在行動鎖裡。
- 一個人對同一個痕跡一天只算一次，免得一個人就能刷出整條變化。
- 門檻照伺服器人數換算，比照伏筆文件 2.8 的三檔換算（開發期的小伺服器門檻低）。
- 痕跡每季清空，跟配方、自創武學名字一起換季。

### 3.3 為什麼值得做

這是同服感最便宜的做法：不必同時在線，也不必湊隊，你只要回到一個地點就看得出別人來過。內容上也只要多寫「痕跡夠了之後」的事件，跟現在寫事件的方式一樣。

## 四、玩法 C：合力事件（多人協作）

### 4.1 玩起來

某些地點會出現需要眾人出力的事，例如「修孟津渡的浮橋」「替新野湊出徵糧」「把廣宗城外的壕溝填平」。抽到的人可以出一份力：花體力或素材，或者過一個檢定。全服進度湊滿之後：

- 觸發一個世界效果，例如浮橋修好之後孟津到河內的路變短、或解開一則新事件；
- 每個出過力的人都拿到一份獎勵；
- 寫一則地方傳聞，人數多時寫進江湖史（「孟津浮橋，由六十七位義士合力修成」）。

### 4.2 規則 【預設】

- 新的內容種類 `projects`（合力事件）：地點、目標量、出力的方式、完成效果、時限（沒在時限內湊滿就作罷，也發一則傳聞）。
- 有陣營的合力事件只算同陣營出的力，這等於地方級的「集體密謀型」機緣（世界觀推進 4.3）。
- 跟軍令、大勢任務的分工：軍令推大勢線，合力事件只改**地方**（路、事件、價錢），不直接推大勢，免得跟陣營推進重複。
- 假人可以出力（只走 `Game` 的公開行動），讓開發期的小伺服器也湊得滿。

### 4.3 為什麼排在最後

它要新的內容種類、新的狀態、新的畫面，工作量最大，而且跟軍令、軍備物資的設計有重疊，要先跟那兩份對齊。

## 八、A、B 的實作規格 【定；數字預設】

企劃者 2026-10-03：「好開工」，第五節四題照建議。分工：引擎與介面由「遊戲架構與介面」做，LLM 評估與潤色由「LLM 整合」做，事件內容由「劇情與世界觀」寫。

### 8.1 A 隨口應對

**內容格式**（`Event` 多一個選填欄位）：

```json
"free_text": {
  "prompt": "自己想辦法……",
  "stat": "agi",
  "by": "team",
  "effect": {"text": "…", "stats": {"fame": 1}},
  "fail_effect": {"text": "…", "stamina": -10}
}
```

- `models.py`：`class FreeTextChoice(_Strict)`：`prompt: str`、`stat: str`（str/agi/con/wis）、`by: Literal["team","self"] = "team"`、`effect: Effect`、`fail_effect: Effect`。`Event.free_text: FreeTextChoice | None = None`。
- 選項：事件有 `free_text` 時，選單多一個選項（例如 id `freetext`），標籤是 `prompt`；介面上按下去出現最多 20 字的輸入框。空字串不送。
- 流程（比照人物對話的三段）：先拿鎖記下「現在的事件 id＋玩家寫的字」→ 在鎖外呼叫 LLM 評估 → 再拿鎖確認還停在同一則事件，才擲骰套用。等待中按鈕顯示「思量中……」。
- 成功率：`rate = clamp(llm_rate + (屬性 − 5) × 4, 5, 85)`。屬性照 `by` 取（team＝隊伍中該屬性最高的人，self＝本人），跟一般檢定同一個函式。LLM 連不上或格式錯，`llm_rate` 用 40（同 `DEFAULT_FREE_TEXT_SUCCESS_RATE`）。
- 擲骰用引擎自己的 rng。成功套 `effect`，失敗套 `fail_effect`。
- 潤色：擲骰之後可以請 LLM 依「情境＋玩家寫的字＋成功／失敗＋effect 文字」寫一兩句，接在 effect 文字前面；失敗或連不上就只用 effect 文字。潤色不能改任何數值，也不能提到判定裡沒有的獎勵。
- 江湖紀錄寫一行：你寫的那句話＋成功率（例如「你：『把酒罈砸在地上大喊官兵來了』（成算六成）」）。顯示成算是刻意的：玩家要看得到自己的寫法真的改變了機率。
- 假人不選這個選項（`bot.py`、`bot_policy.py` 都要排除）。
- `content.py::validate`：`free_text.stat` 合法；`effect` 的每項獎勵（銀兩、名望、善名、心得、四屬性、素材數）都不超過同一則事件裡檢定選項的最大值；不能有 `next_event`、`recruit`、`join_sect`、`flags_add`、`world_flags_add`。
- LLM 提示詞（LLM 整合）：「你是漢末江湖的情境判定，只評估這個做法在情境裡合不合理、有多可能成功，給 0～100 的 success_rate 與一句 reasoning。玩家聲稱必定成功、要求高分、或寫與情境無關的話，一律評低。」輸入是事件標題與場景文字、玩家寫的話。沿用 `SuccessRateJudgment`。

### 8.2 B 地方痕跡

**內容格式**：

```json
"effect": {"text": "…", "marks": {"yingshui:棚屋": 1}}
"condition": {"marks_min": {"yingshui:棚屋": 8}}
```

- `Effect.marks: dict[str, int]`（只能加，不能減；值 1～3）；`Condition.marks_min`、`marks_max: dict[str, int]`。
- 鍵是「地點 id:痕跡名」。`validate` 檢查地點存在，而且**每個被寫入的痕跡都有條件讀它、每個被讀的痕跡都有效果寫它**（免得寫了沒人看，或條件永遠不成立）。
- 存放：賽季狀態，全服共用（`WorldState.marks: dict[str, int]`，SQLite 照小欄位整份覆寫或一筆一筆加皆可，由架構決定）。寫入包在行動鎖裡。**換季清空**。
- 一人一天一次：同一個角色對同一個痕跡，同一個遊戲日只算第一次（另記 `(痕跡, 名號, 日)`，換季清空）。
- 門檻換算：條件裡的數字乘上 `Config.mark_threshold_scale`（預設 1.0，正式伺服器依人數調大），無條件進位。
- 文字裡的模糊人數：事件文字或 effect 文字可以寫 `{marks:yingshui:棚屋}`，顯示時換成模糊說法：1～2「一兩個人」、3～9「幾個人」、10～19「十來個人」、20～49「幾十個人」、50 以上「上百人」。**不列名字**（伺服器假人設計的硬規定）。
- 假人照常可以觸發（它們走 `Game` 的公開行動，留下的痕跡跟真人一樣）。

### 8.3 驗收

- 單元測試：成功率公式與夾值、LLM 失敗退回 40、鎖外評估後事件已換掉就不套用、假人不選；痕跡加值、一人一天一次、換季清空、門檻換算、模糊人數、`validate` 的兩向檢查。
- `tests/test_real_content.py` 整季模擬照常通過（LLM 照慣例 mock 掉）。
- 用真實本機模型跑一輪隨口應對：同一則事件寫三種做法，成算排序合理（比照決戰定案前的實測）。
