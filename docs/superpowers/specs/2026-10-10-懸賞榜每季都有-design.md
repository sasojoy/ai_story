## 零、一句話

懸賞榜、通緝、遊俠名號、截殺從第一季開關底下搬出來，只看劇本有沒有陣營，每一季都有。第一季規則關著的季，每週初也掛一批單，只掛這一週、不疊單。官軍、黃巾、地方豪強每週各掛一張「求藝」和一張「求兵」：求藝要一門合成出來、指定屬性的武學，求兵要裝備庫裡一把指定種類與屬性的兵器。前三個交的有賞，交了就沒了。換到的銀兩、經驗、心得比一場遊歷好一點，求藝另給素材，偶爾給一把兵器。

### 2.2 改成什麼

1. **懸賞榜**：`bounties.active(state, content)` 改回傳 `content.config.bounties.enabled and bool(content.scenario.factions)`。`Config.bounties`（models.py:1246）加 `enabled: bool = True`。
   - 測試內容（`tests/fixtures/content/scenario.json`）沒有陣營，所以舊測試的城鎮選單不會冒出懸賞榜。這等於「測試內容關掉」，而且**不必改 `tests/fixtures/content/config.json`**：那個檔第 17 行是兵器，之後四欄的 armor、mounts、treasures 也都寫在同一個尾巴，一改就撞。
   - 兵器的開關只看 `enabled`；懸賞榜多看一個「劇本有陣營」，因為沒有陣營就沒有人掛單。
2. **遊俠名號**：`ranger.active` 改成 `state.player.faction is None and bool(content.scenario.factions)`。先例是叛投：`defection.can_defect`（defection.py:32）只問劇本有沒有陣營，第一季規則以外的季也能叛投。劇本沒有陣營就沒有「散人」可言，測試內容也因此照舊不記帳。
3. **截殺**：
   - 刪掉 `raid_shown` 的 5317-5318（`if not season_one(...): return False`），開頭改成 `if not self.content.config.raid.enabled: return False`。
   - 刪掉 `raid_targets` 的 5363-5364，交給 `raid_shown` 判。**只拆其中一處不夠**：只拆 5317 的話，第一季規則以外的季假人永遠不截殺，跟真人不一樣，看得出來。
   - `Config.raid`（models.py:1353）加 `enabled: bool = True`【預設】。這是給主機的緊急開關：上線之後假人截殺真人的情況要是太兇，主機改設定就能關，不必退版。
   - **關掉截殺時通緝一起收**【預設】。通緝只能靠截殺交差，只關 `raid_shown` 的話：`post_problem`（bounties.py:235-253）、`wanted.buttons`（wanted.py:18）、`can_take`／`take_problem` 都只看 `bounties.active`，通緝照樣押得下去、揭得下來，`bot.take_bounties`（bot.py:316-318）與 `bot_policy._takeable`（bot_policy.py:683-686）還會把通緝揭滿 `max_taken` 的 3 格、擋掉討伐與打探，可是永遠交不了差，只能等 `post_weeks` 退押金（PM 10/09 調查就記過這個洞）。所以 `raid.enabled` 關著時：
     - `post_problem` 開頭回「（此刻無法這麼做。）」；`wanted.buttons` 不畫（回空的，不畫灰鈕）。
     - `open_bounties`（bounties.py:90-95）濾掉 `kind == "wanted"`。`mine`、`take`、`hunting`、`status`、`visible`（7.2）、整季機器人與假人都經過它，自然看不到、揭不了、不佔格、不算張數。

  - 只有第一批（每季都有＋FB-121）上線時：討伐 4、打探 2、護送 2，共 8 張。
  - 第二批（求藝、求兵）合進來之後：再加求藝 3、求兵 3，共 14 張；兵器開關（`Config.weapons.enabled`）關著時不掛求兵，共 11 張。
  - 期限錨在 `week_start(本週＋2)`。以前的週不補掛（第三節）。舉例：季已經走到第 8 週（第 210 小時），只掛第 8 週那一批，到期是第 252 小時。
- 遊俠名號的帳從上線那一刻才開始記，以前加過的善名、惡名不追溯。狀態列在散人到第 1 階（5 點俠名）之前照舊寫「散人」。
- 截殺立刻開放。**假人每一輪有 `RAID_CHANCE`（10%）的機會，截殺此地勝算「穩勝」「有把握」的敵對陣營真人。**
  - 新手期照現在的程式從季初算（14 天的季是 3 天，見 6.2）：上線那一刻跑的季早就過了第 3 天，之後每一個新角色一投靠就截得到、也會被截殺，沒有保護。這跟企劃者「新手期照舊」想保護新人的本意相反，**開工前要企劃者確認（14.1 丁）**；PM 建議截殺改看各自的 `joined_at`。
- 通緝立刻開放。
- 這些要寫進給 joy 的部署說明，提醒玩家；主機要知道 `Config.raid.enabled` 能關掉截殺，通緝也會跟著收（2.2 第 3 點）。

**情形二：上線時跑的是第一季規則開著的季**（週末設定）

- 懸賞榜、名號、截殺本來就有。`bounty_week` 從 0 起，但第一季那一條仍照 `hooked_week` 每週跑一次，所以**這一週不會重掛**（3.4）。這一週沒有求藝、求兵，要等下週一（週末設定最多約 5 小時）。
- 截殺的貢獻照記。

## 三、第一季規則關著的季：週初掛單

### 3.1 週次怎麼算

- 季曆不看開關：`calendar.cal_scale`（calendar.py:42-45）、`point`（48-56）、`week_start`（59-61）都照季長算，季長看這一季的章（`WorldState.length_days`）。
- 14 天的季：`cal_scale`＝12×7÷14＝6，一週是現實 28 小時，一季 12 週。`auto_weeks` 2 週＝56 小時，`post_weeks` 1 週＝28 小時。週末設定（2.5 天）一週是 5 小時。
- 不改用「每 7 個遊戲日一批」：`rules.game_day` 一季固定 14 天，照這個算一季只有 2 批。用季曆週的話，兩種季都是一季 12 批、比例一樣。
- 「週」在規則關著的季裡玩家看不到，所以玩家看到的期限一律寫時刻（3.5），不寫「第幾週」。

### 3.2 計數器與兩道擋

- `WorldState` 加 `bounty_week: int = 0`（放在 state.py:543 `bounty_seq` 旁邊），意思是「自動掛單已經掛到第幾週」。
- `bounties.issue`（bounties.py:312）開頭補兩道擋，然後記下週次：

  ```python
  w = state.world
  if not active(state, content) or week != calendar.point(w.time, content, w).week or week <= w.bounty_week:
      return []
  w.bounty_week = week
  ```

  - 第一道「只發這一週」照 `orders.issue` 的 orders.py:282-283 寫。少了這一道，以前的週會被補掛。
  - 第二道「這一週掛過了」讓第一季與規則關著的季兩條路都能直接叫 `issue`，同一週叫幾次都只掛一次。
- **不借用 `hooked_week`**：tests/test_engine.py:6152、6283 與 tests/test_timetable.py:409、426 都斷言規則關著的季 `hooked_week` 是 0。也**不在規則關著的季跑整串 `WEEK_HOOKS`**：`seats.rotate`、`orders.issue` 雖然各自擋了開關，但在那種季跑它們意思不對。

### 3.3 掛在哪

- 新函式 `bounties.tick(state, content)`：用 `calendar.point(w.time, ...).week` 算出這一週，叫 `issue(state, content, 這一週)`。
- `world.advance_world_state`（world.py:528-567）的迴圈裡，接在跑 `sim_tick` 那一段（556-559）後面、`if crossed`（560）前面：

  ```python
  if cal_hour is None and not season.ended:
      msgs += bounties.tick(vehicle, content)  # 第一季規則關著的季：季曆跨進新的一週就掛這一週的懸賞（只掛這一週）
  ```

  - 每一步最多 1 小時，所以最多晚 1 小時掛單；期限錨在週初（3.5），晚掛不會讓單子多掛。
  - `vehicle` 是 `_season_vehicle(content, season)`，裡面的玩家是假的。`issue` 只讀 `state.world` 與 `content`，可以直接用。
  - 管理者快轉幾週時，每跨一週就掛一次；每次掛單會清掉過期的，結果跟時間自然走過去一樣。
- `world.settle_season_start`（506-513）在第 511 行早退之前加一個分支：規則關著的季，開季那一刻也呼叫 `bounties.tick`。

  ```python
  if not calendar.season_one_on(season, content):
      return [] if season.ended else bounties.tick(_season_vehicle(content, season), content)
  if season.hooked_week != 0 or season.ended:
      return []
  ```

  - 這個分支**不碰 `hooked_week`**，所以 test_engine.py:6283 照舊會過（測試內容沒有陣營，`tick` 回空的）。
  - 不加這個分支也行：第一個人同步時就會掛。加它只是讓管理者開季後，第一眼看到的榜不是空的。

### 3.4 跟第一季那一條不打架

- 第一季規則開著的季照舊走 `WEEK_HOOKS`（world.py:29），用 `hooked_week` 當週次。`advance_world_state` 只在 `cal_hour is None`（規則關著）時叫 `tick`，兩條路不會同時跑。
- 第一季平常不會疊單：`advance_world_state` 在每個曆時交界都會停下來跑 `season_hour`（world.py:551-552、560-561），停機之後的補算也是一週一週照時間跑，每次 `issue` 都在那一週的週初、先清掉過期的（實測 main 原樣、週末設定開季後一次補算 22 小時：榜上 16 張，只有第 4、5 週）。`season_events` 的 while 迴圈（345-348）一口氣補好幾週，只會發生在「季的章開著、設定 `season_one` 中途關掉又打開」這一種情形（`calendar.season_one_on` 兩樣都要，關著的那段時間不跑週初掛鉤）。第一道擋在第一季平常不會觸發，只防這種情形補跑舊週；軍令的 orders.py:282-283 也是同一道擋。
- 開關中途打開時，正在跑的那一季照它的章（`season_one=False`）繼續走 `tick`；下一季蓋了「開」的章，才改走 `WEEK_HOOKS`。
- 上線那一刻（2.4 情形二）：`bounty_week` 是 0，可是第一季那條路不會再跑這一週的掛鉤（`hooked_week` 已經是這一週），所以這一週不重掛。

### 3.5 期限怎麼算、怎麼寫

- 期限錨在週初：`expires = calendar.week_start(week + cfg.auto_weeks, content, w)`，取代 bounties.py:325 的 `now + auto_weeks × week_seconds`。
  - 第一季那條路本來就在週初掛，結果不變。
  - 規則關著的季晚掛最多 1 小時，期限不會跟著延後。
  - 上線那一刻掛的單（例：第 210 小時掛第 8 週）期限是第 252 小時，不是 210＋56＝266。
  - 通緝照舊是 `now + post_weeks × week_seconds`（玩家隨時掛，沒有週初可錨）。
- **給玩家看的期限一律走新函式 `bounties.due_text(b, content, w)`**，裡面是 `calendar.stamp_text(b.expires, content, w)`（calendar.py:97-103）。`bounties.py` 不能 import engine，所以用不到 `Game.stamp`；它們是同一個寫法。
  - 第一季開著時寫「第 5 週・週一 00:00」。
  - 規則關著時寫「第11天 12:00」。
  - **期限到季末或過了季末，一律寫「到季末」**：`b.expires >= season_length_days(w, content) * calendar.DAY - calendar.EPS_SECONDS`（`world_state.season_length_days`，照這一季的章）時不交給 `stamp_text`。季曆一季 12 週＝季長天數，兩種季的季末都是這個數。理由：規則關著時 `stamp_text` 走 `calendar.day_clock_text`，不會夾。14 天的季第 11 週掛的單到期是 `week_start(13)`＝第 336 小時，會寫成「第15天 00:00」；第 12 週是 `week_start(14)`＝第 364 小時，會寫成「第16天 04:00」，這種季只到第 14 天。光是 `min(expires, 季末)` 也不夠，季末那一刻本身就寫成「第15天 00:00」。第一季的 `point_text` 雖然會夾成「第 12 週・週日 23:59」，兩種季寫成同一句比較清楚。
  - 真正的 `expires` 不必夾：季末收季時懸賞榜跟著 `WorldState` 整個重來。
  - 不要在別處自己拼「第 N 週」。
- 名額寫 `_left(b)`（bounties.py:86-87）。

### 3.6 為什麼不能照抄 `season_events` 的 while 迴圈

讀者 2026-10-10 用 14 天的季實測：季走到第 8 週（第 210 小時）、榜上一張都沒有時，照 `while w.hooked_week < week` 的寫法補，一次掛出 64 張（週次 1～8、全部同一刻到期、同一個地點最多 6 張討伐）。只掛這一週是 8 張。PM 10/09 也量過一次，給 joy 的說明寫的是 48 張。

再加上週初掛單的實測（同 2.2 末段那一次，`ranger.active` 照 2.2 第 2 點）：每一步都 `tick`、只掛這一週，非 slow 6692 個過、9 個紅（就是 2.2 末段列的那 9 支），`-m slow` 60 個全過。正式內容、預設設定讓整季機器人玩一季，種子 1、2 都是每週剛好 8 張、12 週共 96 張，`hooked_week` 一直是 0。種子 1 交差 5 張；種子 2 交差 1 張、記了俠名 2 點（正式內容有陣營，`ranger.active` 兩種定義在這裡結果一樣）。

### 3.7 數字在規則關著的季的意思

懸賞的銀兩是照「週末設定一天大約收 100 兩」定的（`Bounties` 的註解，models.py:1247 起）。14 天的季一週是現實 28 小時，一批單攤到的時間是週末的 5.6 倍，每小時能拿到的懸賞少很多。這份不另調數字，由量表（11.1）照實報兩種季各拿到多少。

截殺的損失上限也是照週末定的：`Raid` 的註解（models.py:1366-1367）寫「一季（週末 60 小時）一個人最多被截殺約 60 次」，靠的是保護時間 `shield_seconds` 1 小時。截殺每季都有之後，14 天的季有 336 小時，保護時間照舊 1 小時，一個人一季最多可能被截約 300 次。
- 每小時的損失上限跟週末一樣（每次最多 5%、15 兩，氣血上限的 8%、不變成內傷），體力也照現實時間回，所以每小時賺的與被截的比例不變；變的是一季加起來的量。銀兩照比例扣，永遠扣不光，這一條在 14 天的季仍然成立。
- 這份不另調數字。11.2 的 `sim_server_bots.py`（規則關著的季）多印被截殺最多的那個人一季丟了多少銀兩、多少氣血，列進 14.2 第 12 條，等量完再決定 14 天的季要不要另一組數字（例如保護時間照季長放大）。
- `Raid` 的註解要補一句 14 天的季的上限（2.3 第 6 點那一批註解一起改）。

## 四、求藝與求兵

### 4.1 掛單

- `bounties.issue` 在原本的官軍、黃巾迴圈（326-354）之後，另跑一圈 `content.scenario.factions`，三方都跑，順序照劇本。每個陣營各掛 `Config.bounties.give_kinds`（預設 `["art", "arms"]`）裡的每一種：
  - 求藝 `art`：`attribute` 從 `give_attributes`（剛、柔、快、慢）挑。
  - 求兵 `arms`：`attribute` 同上，`weapon_kind` 從 `WEAPON_KINDS`（models.py:18：劍、刀、槍、棍、弓弩、拳腳）挑。
  - 同一期裡，各方的求藝屬性互不重複：`n = len(factions)`，先 `picks = rng.sample(give_attributes, min(n, len(give_attributes)))`，陣營比屬性多時再補 `n - len(picks)` 次 `rng.choice(give_attributes)`（可以重複）。**不寫死 3**：`validate` 只要求 `give_attributes` 至少一個，`rng.sample(attrs, 3)` 在少於 3 個時會丟 `ValueError`。求兵另抽一次，做法相同。求兵的種類不要求不重複。
- **亂數另開一份**：`random.Random(f"bounty-give|{week}|{sorted(w.trends.items())}")`。不從 bounties.py:320 那一份抽：那一份同時挑討伐、打探、護送的地點，插進去抽的話，後面每一張的地點都會位移。
  - 已知的代價：這份種子沒有天機（WorldState 沒存天機，`issue` 也拿不到 store），每一季第 1 週的屬性會一樣。列進 14.2 第 7 條。
- `Config.weapons.enabled` 關著時不掛求兵。
- 名額 `give_quota`（3）。不走 `bounties.quota()`：它在 30 人的正式設定與週末設定都算出 1。
- 期限同其他陣營懸賞：`week_start(week + auto_weeks)`。
- id 照舊用 `b{bounty_seq}`。每期多 6 張會讓下一週 bounty.py:320 的種子跟著變，第 2 週起的討伐、打探、護送地點跟現在不同。7.2 的「同一地點不重複」本來也會改到地點，所以接受，量表的基準重量。
- 每批的張數（兵器開著）：討伐 4＋打探 2＋護送 2＋求藝 3＋求兵 3＝14 張；一季 12 批共 168 張。
- `content.py::validate` 補幾條檢查：`kinds` 只能是 strike、scout、escort；`give_kinds` 只能是 art、arms；`give_attributes` 只能是 `martial_arts.ATTRIBUTES` 裡的、而且至少一個；`arms_silver` 的鍵**剛好是**下品、中品、上品三個（少一個的話交那個品質的兵器會 `KeyError`）；`arms_tier` 的鍵剛好是 "1"、"2"、"3"。理由：現在 bounties.py:348-349 遇到不認得的種類會默默 `continue` 掉。兵器第二批也在 `validate` 加檢查（`craft_names.weapon`，約 content.py:1457），見 12.1。

### 4.3 懸賞榜上怎麼列

`Game._bounty_options`（engine.py:2471-2488）改成照下面的順序列：

1. **交得出的求藝、求兵，每張一顆「挑一件」**：`bounty:pick:<bid>`。標籤例（散人）：「交出… 官軍・求藝・剛（賞銀 20・經驗 30・心得 20・俠名 +2・素材；你有 2 門合用；期限 第11天 12:00・名額還剩 3）」。賞的那一段一律走 `reward_text`（4.7）：陣營的人不記俠名，標籤裡就沒有「俠名 +2」。排在最前面，因為按了當場就能交。
2. **原本的揭下、放棄**（討伐、打探、護送、通緝），每行後面多寫期限與名額（7.1）。
3. **交不出的求藝、求兵**：收成一行灰掉的 `bounty:none`。例：「這幾張你現在交不出：黃巾・求藝・柔、地方豪強・求兵・屬快的槍（求藝要合成出來、沒帶在身上的功夫；求兵要裝備庫裡種類與屬性都對得上的兵器）」。陣營的人只列自己陣營的。
4. 「返回」`bounty:back`（照舊）。

說明：

- 這樣做是因為選單會太長。散人同時看得到三方 × 兩種 × 兩批，最多 12 張求藝、求兵，每張再列幾件合用的就爆了（FB-128 記過，手機第一屏只放得下約 5 顆）。所以交不出的收成一行，交得出的每張只佔一行，挑哪一件到第三層。
- 「交得出」＝`bounties.fitting(...)` 不是空的：至少有一件過得了 `fit_problem`（4.5）。這裡人一定在城鎮、榜也開著，所以跟「第三層至少有一件按得下去」是同一件事；卡片（4.9）用同一個 `fitting`，不看地點。灰掉的那一行不是永遠按得下去的選項，所以 `bot.pick()` 不必改。
- 求藝、求兵**不給「揭下」**：`take_problem`（bounties.py:117）對這兩種回「這一張不用揭，在懸賞榜上直接交。」。不擋的話，`bot.take_bounties`（bot.py:306-321）會把它們也揭下來，揭滿 `max_taken` 的 3 格，擋掉討伐與打探；`bot_policy._takeable` 也會一直是真的，假人會在城裡反覆打開、關上懸賞榜。

### 4.4 交出的選單（第三層）

- `PlayerState` 加 `bounty_pick: str | None = None`（放在 state.py:300 `picking_bounty` 旁邊）：正在替哪一張挑東西。
  - 按 `bounty:pick:<bid>` 時記下；按 `bounty:unpick`、`bounty:back`、交出成功、打開懸賞榜（`_act` 的 engine.py:1916-1918）時清掉。
  - `_bounty_options` 看到 `bounty_pick` 指的那一張已經不在 `open_bounties`、或已經交不出時，當它不存在、照第二層畫。所以**不必改** `_drop_stale_references`（506-507）與 `_depart`（4346）。這兩處緊貼兵器第二批改的行，也是不改的理由之一。
- 第三層的選項：
  - **求藝**：功法庫裡合用的，每一門一顆 `bounty:give:<bid>:<功法 id>`。
    - 標籤：「交出【烈焰掌】（武學・上品・第七成；熔掉能換 48 心得）」。
    - `confirm`：「把【烈焰掌】（上品・第七成）交給官軍？交了就沒了；熔掉的話能換 48 心得。」
    - `confirm_yes`：「交出」。
    - **標籤與確認句的心得數一律取 `library.melt_value`**（library.py:179-193），不要自己算。例子的 48 照現在的公式：第七成練成花了 2×(1+…+6)＝42 心得（`practice_xinde_per_level` 2），八成是 33（`melt_refund_ratio`），加上自己修到上品的加給 15（`melt_quality_bonus`；合成時就擲到上品的不算，見 `art_rolled`）。舊設計 5.2 的「16」是練成每成 1 心得時的數，不能照抄。
    - 第幾成用 `library.level_of`（23-33），品質用 `team.player_art`。
  - **求兵**：裝備庫（`p.rack`）裡合用的，每一把一顆 `bounty:give:<bid>:<兵器 id>`。
    - 標籤：「交出【軟鋼劍】（一階中品・鋒利度 80）→ 賞銀 35」。
    - `confirm`：「把【軟鋼劍】（一階中品）交給黃巾？交了就沒了。」淬煉過的多一句「淬煉過 2 次，賞銀不會多給。」
    - `confirm_yes`：「交出」。
    - 階品寫法用兵器第二批的 `weapons.grade`。
  - **按不下去的列在最後**（灰掉、寫原因）：身上正在練的那門（「【坐山拳】身上正在練，先改練別的才能交」）、等著定名的那門（「先替它定名」）、手上那把兵器（「手上這把要先換下來」）。
  - 合用的照「最不值錢的先」排：求藝照熔煉值、再照名字；求兵照品質、階、鋒利度、id。最多列 `give_list`（8）件，多的收成一行灰掉的 `bounty:more`。
    - **只讓交最不值錢的這幾件是有意的**【預設】：交出去就沒了，該交的是最捨得的；而且求藝、求兵沒有別的地方可以交（拆解還能去修練頁的裝備庫拆，交出沒有這條路）。
    - 灰掉那一行寫成指引，不只是報數（待 joy 潤）：求藝「還有 N 門合用的沒列出來（列的是熔掉最不值錢的；要交別的，先把前面這幾門熔掉、改練或交掉）」；求兵「還有 N 把合用的沒列出來（列的是最不值錢的；要交別的，先把前面這幾把拆掉或交掉）」。
    - 修練頁的功法卡、裝備庫要不要加一顆「交出」的入口，這次不做，列進 14.2 第 13 條。
  - 最後一顆「回到懸賞榜」`bounty:unpick`。
- **id 的格式與解析**：`_bounty`（engine.py:2490-2501）照舊先 `verb, _, rest = arg.partition(":")`；give 再 `bid, _, item = rest.partition(":")`。
  - 兵器的 id 是「兵:3」，裡面有冒號，**只能 partition 一次、不能 split**。
  - 懸賞 id（`b17`）沒有冒號；合成武學的 id 是中文名字（`naming.name_problem` 只准中文），也沒有冒號。
- **確認只在網頁那一層**：`Option.confirm` 在 main 上已經有（engine.py:97）。`confirm_yes` 是兵器第二批 Task 1 加的（weapons-2 `5802c742`，網頁 `choose()` 會照它換掉「照打」）。所以這一批一定要等兵器第二批合進來，不另加狀態，也不改 app.js 確認層那一行。引擎、假人、腳本都不會先問，所以交出的動作在引擎裡要整個重驗（4.5）。

### 4.5 擋什麼

拆成兩個純函式，拒絕的話都待 joy 潤：

- `bounties.fit_problem(state, content, world, b, item_id) -> str | None`：**只看這件東西合不合這一張**，不看人在哪裡、榜開沒開，是下面的第 3～7 條。江湖頁的懸賞卡（4.9 的 `status` 與 `have`）用它，4.3 第 1 點的「你有 2 門合用」也是；另包一個 `bounties.fitting(state, content, world, b) -> list[str]`，回傳合用的那幾件 id（照 4.4 的「最不值錢的先」排）。
- `bounties.give_problem(state, content, world, b, item_id) -> str | None`：第 1、2 條，再接 `fit_problem`。第三層的鈕亮不亮、`give` 真的交之前，都走這一個。
- 不拆的話，卡片要列「現在交得出的」就得走 `give_problem`，而它第 1 條要人在城鎮：人一出城，卡上這幾列就不見了，跟 4.9 要的效果相反。

1. 懸賞榜看不到（`board_here` 不成立）→「（此刻無法這麼做。）」
2. 這一張不在 `open_bounties` 裡（過期了，或名額滿了）→「這張懸賞已經下榜了。」
3. `kind` 不是求藝、求兵 →「（此刻無法這麼做。）」
4. `can_take` 不成立（陣營的人看別的陣營的單）→「這一張不是給你的。」
5. 自己已經在 `done_by` 裡 →「這一張你已經交過了。」（一張一人只交一次）
6. 求藝：
   - 不在功法庫也不在身上 →「你的功法庫裡沒有這一門。」
   - 身上正在練的（`p.member.neigong_id`、`wugong_id`）→「身上正在練的不能交，先改練別的。」
   - 等著定名（`art_id == p.naming`）→「先替它定名，再談交出去。」
   - 查不到資料（`team.resolve_art(art_id, content, world)` 回 None：存檔裡記著、內容與全服登記裡都沒有的失效引用）→「找不到它的資料。」，同 `fusion.fuse_problem`（fusion.py:485-486）。排在下面兩條之前，後面才能放心讀 `.origin`、`.attribute`。
   - 不是合成出來的 →「這一張只收合成出來的功夫。」判斷式是：`art_id in content.skills`、或 `team.resolve_art(...).origin != "fused"`、或 `.preset` 為真，三者有一就不收。
   - 屬性不對（`resolve_art(...).attribute != b.attribute`）→「這一張要屬剛的。」
   - 判斷可以跟 `library.melt_problem`（library.py:160-176）共用，但那裡的字寫的是「熔」（「先改練別的」「再談熔掉」），交出要另寫自己的字。
7. 求兵：
   - 兵器開關關著 →「（此刻無法這麼做。）」
   - 手上那把（`p.weapon is not None and p.weapon.id == item_id`；空手時 `p.weapon` 是 None，這一條跳過）→「手上這把要先換下來。」
   - 不在 `p.rack` 裡 →「裝備庫裡沒有這一件。」寫法同 `weapons.dismantle`（weapons.py:276-288），只在 `p.rack` 裡找，所以身上那把天然排除。
   - 種類或屬性對不上 →「這一張要屬柔的劍。」
8. 序章不必另外擋：序章裡閒著的選單經過 `prologue_rules.allowed` 過濾，打不開懸賞榜。

不必另外擋的：

- 開爐三段式、論武做到一半時那一門被交掉：`fusion.fuse_problem`（fusion.py:472-480）的 C 段重驗會回「你沒有這門武學。」；論武答應時也會重驗（engine.py:5237-5240）。
- 決戰的屬性是加入時快照的，交掉不影響正在打的那一場。
- 兩個人同時搶最後一個名額：交出是 `choose` 的一個動作，包在行動鎖裡。後到的那個人選項已經不在選單上，回「（此刻無法這麼做。）」。`choose` 最後會 `_save_season()`（engine.py:1403），不會重演 FB-119 那種「交了差沒存回共用賽季」。

### 4.6 交出時清掉什麼

- **求藝**：把 `library.melt_art` 的 library.py:223-225 抽成 `library.remove_art(state, art_id)`，熔煉與交出共用。它做的事是：`p.arts.remove`，再清掉 `art_levels`、`art_quality`、`art_mastery`、`art_rolled`。這四份是 PlayerState 以功法 id 為鍵的全部私有紀錄。
  - `p.naming` 本來就擋掉了；`renames_told` 不必清。
  - 不退心得。
  - **全服登記的那一門不受影響**：名字、首創者、絕學的正式名字、別人手上那一份、拿它當底的配方都照舊，你是首創者也一樣。這一條照舊設計 5.2。
  - 交掉之後，照同一個配方可以再合一次（5 心得＋5 體力；配方已經登記，查表、不叫模型）。這不是漏洞，見 4.10。
- **求兵**：`p.rack.remove(那一把)`，就這樣。`edge_warned` 只管手上那把，不用動。

### 4.7 獎勵

`bounties._complete`（bounties.py:177-193）加一個參數 `silver: int | None = None`，讓求兵照那一把的品質與階傳銀兩進來。`_share`（139-143）對 `wanted`、`art`、`arms` 都回 1.0，陣營的人拿全額。`give()` 先叫 `_complete`（銀兩、經驗、俠名、`bounties_done += 1`、`done_by`），再接下面各自的獎勵。新的幾行接在後面，原本三種懸賞的訊息順序不變。

- **`silver` 傳的是底數**：`arms_silver[品質] × arms_tier[階]`，還沒乘第 4 階散人的 1.25、也還沒乘 `_share`。`_complete` 把它交給 `_silver`（146-150；改成 `_silver(state, content, b, base=None)`，`base` 是 None 時照舊用 `b.silver`），由 `_silver` 照原本那一條路乘 `ranger.bounty_factor` 與 `_share`。不要在呼叫端先乘，不然會乘兩次。
- 選單上的標籤、懸賞卡、`take` 回話的賞，一律走 `reward_text`（132-136）。它本來就只在 `ranger.active` 時寫俠名，所以陣營的人看不到「俠名 +2」；求兵的那一把實拿多少，也用同一個 `_silver(..., base=)` 算。

**求藝**（散人與陣營的人一樣）：

| 獎勵 | 數字 | 寫法 |
|---|---|---|
| 銀兩 | 20 ×（第 4 階散人 1.25，`ranger.bounty_factor`） | 照 `_silver` |
| 經驗 | 30 | `team.add_team_exp`（同伴也拿，同其他懸賞） |
| 心得 | 20 | `p.stats["xinde"] += 20` |
| 俠名 | 散人 +2 | `ranger.add_deeds` |
| 素材 | 這張屬性的一階 ×2；30% 再給同屬性二階 ×1 | `materials.by_tier(content, 1, 屬性)[0]` 加 `materials.grant`，回「獲得 精鐵砂 ×2」 |
| 兵器 | 20%：種類照 `weapons.art_weapon(p.member.wugong_id, ...)`；推不出來（身上沒武學、內功、舊的自創武學）就照同一份亂數從 `WEAPON_KINDS` 挑。屬性同這張、一階、品質上品 30%／中品 70% | `weapons.new_weapon(..., name=weapons.shop_name(種類, 屬性), tier=1, quality=…)` 加 `weapons.store` |
| 裝備庫滿了 | `weapons.rack_full` 成立時不給兵器，改給同品質的 `arms_silver`（中品 35、上品 50；是那把兵器照價折，不乘第 4 階的 1.25） | 「裝備庫滿了，那把厚背刀折成銀兩 35。」 |

- **擲骰用自己的亂數**：`random.Random(f"bounty-gift|{world.get_season_number()}|{p.name}|{b.id}")`，不碰 `Game.rng`。照固定順序抽：二階素材、兵器、品質、退路的種類。不管有沒有用到，每一次都照抽，同一個人交同一張永遠是同一個結果。一張一人只能交一次，所以也重擲不了。
  - **種子一定要有季數**：`b.id` 是 `b{bounty_seq}`，`WorldState` 每季重來，每一季都從 b1 算起。少了季數，同一個名號每一季交同一號都擲出一樣的東西；選項 id（`bounty:pick:b17`）在網頁上看得到，有心人記下哪幾號送兵器，下一季就專挑那幾張。`give` 本來就拿得到 `world`（`WorldStateStore.get_season_number`，world_state.py:285）。
- 兵器開關關著時（測試內容就是）不給兵器，也不折銀兩。
- 名字用 `shop_name`，會跟鐵匠鋪架上的下品同名（例「厚背刀」），要靠 `weapons.grade` 寫出的階品分辨。joy 要另取一套名字再說。
- **跟四欄設計 6.5 的做法不一樣**：四欄設計的懸賞重賞在裝備庫滿了時寄放在 `held_gear`，之後補發；這裡是折成銀兩。理由：寶物、良駒買不到也打不出來，折錢等於拿走稀有的東西；求藝送的是架上 40 兩就買得到的一階貨，折成銀兩就是等價。
- 等裝備一把 `Weapon` 泛化成 `Equipment` 之後，`rack_full` 要照欄位判斷（四欄設計 3.3），這裡跟著改成看武器那一欄。

**求兵**（散人與陣營的人一樣）：

| 獎勵 | 數字 |
|---|---|
| 銀兩 | `arms_silver[品質]` × `arms_tier[階]`：下品 20、中品 35、上品 50；二階 ×2、三階 ×4。這是底數，再由 `_silver` 乘第 4 階散人的 1.25 |
| 經驗 | 30（`team.add_team_exp`） |
| 心得 | 10 |
| 俠名 | 散人 +2 |

- 淬煉、首創配方都不加錢。確認句已經寫明（4.4）。
- 依據之一：鐵匠鋪架上一階下品 40 兩。拿買來的下品去交，淨虧 20 兩，換 30 經驗＋10 心得。
- 依據之二：**這份等兵器第二批合進來才開工，所以照它的打造工錢算**（plans/2026-10-10-兵器-2-自己打造.md 第 38 行；`WeaponRules.forge_silver` 一階 20、二階 60、三階 150，素材另算，不花體力、心得；階照主料；品質從下品 50／中品 30／上品 20 起算，輔料的階、悟性、熟手、天時地利會往上下推）。下表照起算的機率，也就是一爐普通搭配的平均：

  | 階 | 工錢 | 素材 | 交出的銀兩（下／中／上） | 交出的期望銀兩 | 對工錢的淨得 |
  |---|---|---|---|---|---|
  | 一階 | 20 | 主料、輔料各一個一階（可以同一種） | 20／35／50 | 0.5×20＋0.3×35＋0.2×50＝30.5 | ＋10.5，另扣兩個一階素材 |
  | 二階 | 60 | 主料二階、輔料一個 | 40／70／100 | 61 | ＋1，另扣素材（約打平） |
  | 三階（×4） | 150 | 主料三階、輔料一個 | 80／140／200 | 122 | −28；上品 ＋50、中品 −10、下品 −70 |
  | 三階（原本的 ×3） | 150 | 同上 | 60／105／150 | 91.5 | −58.5；連上品都只打平工錢、素材白丟 |

  每一階另有經驗 30、心得 10，散人另記俠名 2。
  - **一階「打了就交」淨賺是有意的**：柔、快的求兵在鐵匠鋪買不到（下面那一條），自己打是主要的交法，打一把要是虧錢就沒人交。擋住它的是名額 3、一張一人一次、同一期屬性輪換（4.10），散人一季最多交 36 張，照上表約淨賺 380 兩（另扣 72 個一階素材）＋1080 經驗＋360 心得。
  - **二階約打平**：手上多出來的二階交掉不虧，專門打來交不划算。
  - **三階不打算讓人專門打來交**：三階是打來用的（一階加成 +5%、三階 +15%）。三階改成 ×4，是讓手上多出來、配不上身上武學的三階上品交了至少不虧工錢（＋50 夠補一點素材）；原本的 ×3 連上品都只打平工錢、三階素材白丟，等於沒人會交。
  - 這張表交企劃者看，見 14.2 第 4 條。
- 剛、慢在鐵匠鋪買得到：正式內容 10 個鐵匠鋪，9 處賣剛、下曲陽賣慢。柔、快沒有地方賣，要撿（遊歷、野怪 3% 掉落，屬性照當地）或靠兵器第二批自己打造。兵器第二批打得出陰陽虛實，這四種不符合任何一張求兵。
- 二階、三階要等兵器第二批（打造的階照主料）與第三批才有。

`reward_text`（bounties.py:132-136）的寫法：

- 求藝：「賞銀 20・經驗 30・心得 20・俠名 +2・素材，偶有兵器」。
- 求兵：「賞銀 20～50（照品質，高階另加）・經驗 30・心得 10・俠名 +2」，每顆交出鈕上另寫那一把實拿多少（`_silver(..., base=)`）。

### 4.10 量與防刷

- 一張的總名額 3 人；一張一人只交一次（`done_by`）；同一期三方的屬性不重複。所以同一門武學一期只對得上一個陣營的求藝。
- 散人三方的單都能交，加上 `auto_weeks` 2 讓兩批重疊，一週最多新交 3 張求藝、3 張求兵；一季最多交 36＋36 次。陣營的人只能交自己陣營的，一季最多 12＋12 次。
- **36 次不必是 36 門不同的武學**：交掉之後照同一個配方可以再合（4.6）。人人開局就有的基礎吐納（內功・柔）融風、火、水、山，就合得出快、剛、柔、慢四門合成內功（`origin` 是 fused、不是師門配方），四個配方就對得上每一張求藝。
- 全服上限：每種每季 3 方 × 12 週 × 3 名額＝108 次。
- **「交了再合」一圈拿多少**：再合一門花 5 心得＋5 體力，交出去換銀兩 20、經驗 30、心得 20、同屬性一階素材 2 個，30% 再一個二階素材、20% 一把一階中品或上品兵器（第 4 階散人銀兩再 ×1.25）。每圈淨得約心得 15、經驗 30、銀兩 20、素材 2.3 個、兵器 0.2 把。
- **散人一季的上限**（36 圈全部交成）：銀兩 720（第 4 階 900）、經驗 1080、心得淨 540（720 減掉再合的 180）、一階素材 72 個、二階約 11 個、兵器約 7 把，花 180 體力。對照 CLAUDE.md 記的週末 20 個種子散人季末銀兩 1233，這個量不小；週末一季 60 小時、一週 5 小時就要交 3 門，實際交得到幾張要看量表。
- **串接：求藝的素材 → 打造 → 求兵**。求藝給的是這張屬性的一階素材 2 個，剛好是一爐同屬性的一階兵器（柔＋柔＝柔，兵器第二批的 `insights.merged_attribute`），工錢 20 兩。同一期三張求兵的屬性互不重複、從四個裡挑三個，所以這把有 3/4 的機會對得上某一方的求兵，交出去期望 30.5 兩＋30 經驗＋10 心得（4.7 的表）。等於一門 5 心得合出來的功夫，一圈換兩張懸賞。
- 能擋住它的是名額 3、一張一人一次、同一期屬性輪換；要不要另加門檻（成數、品質）見 14.1 甲。11.1 的量表要照實報散人一季從求藝、求兵各拿到多少。
- 求兵拿架上的下品去交是淨虧 20 兩（4.7），只拿經驗與心得；自己打一階的淨得見 4.7 的表。
