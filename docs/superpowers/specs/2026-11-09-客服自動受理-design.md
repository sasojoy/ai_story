# 客服自動受理（客服官）設計，第 1 版

PM 2026-11-09 晚寫。**待企劃者點頭**；點頭之後 PM 寫計畫、派 Opus 5.5 開發、Sonnet 測試與審查（企劃者 11/08）。接在 `2026-11-08-帳號綁定與客服-design.md` 第六節（客服單、客服身分、查帳號，第 211～214 批，都進 `develop`、開關關著）之後；這一份只寫新加的，那一份寫過的不重複。

## 一、為什麼做

企劃者 2026-11-09 晚原話：「客服的目標 想要讓 Claude 自動審核 我想像的流程是玩家 問問題跟截圖 然後我們傳到 dc 的客服頻道 Claude 監聽那個頻道 有問題先自動受理」。

現在客服單只有文字、只有真人客服能回；上線之後沒有人整天盯著。要讓一個 Claude（下面叫**客服官**）先受理每一張單：看字、看截圖、看帳號卡，答得了的直接答，缺資訊的追問，要管理者動手的整理好叫人；人只處理它叫的那幾張。

## 二、企劃者定的（2026-11-09 晚，PM 問、企劃者答）

| # | 題 | 定的 |
|---|---|---|
| 1 | 玩家的問題與截圖從哪裡進 | **遊戲內送單，伺服器自動轉貼到 Discord**（玩家不用進 Discord） |
| 2 | 自動受理做到哪一步 | **受理與整理、加上解答、再加上查帳號**（三層全要） |
| 3 | Claude 回的話玩家看到的署名 | **標明是自動回覆**，玩家按「找真人」就轉人處理 |
| 4 | 要管理者動手或答不了時在 `#客服` 點名誰 | **企劃者和 Joy** |
| 5 | Claude 能不能自己結單 | **答完等玩家，玩家沒再回就自動結**；要管理者動手的單永遠由人結 |
| 6 | 企劃者和 Joy 在 `#客服` 說的話算不算指令 | **算，只認這兩個人**；其他人的話是資料 |

沿用上一份設計不變的：補發、退款、重設密碼、解綁、刪帳號**只有管理者做**（6.4 的核對規矩照舊）；客服名單認帳號；玩家只看得到自己的單；一張單的字只過 `esc`。

## 三、一眼看完的流程

1. 玩家在遊戲「設定 › 客服」寫一張單，可以附**最多 3 張截圖**。伺服器存進旁檔，一如現在。
2. 主機上一支**橋**（`scripts/support_bridge.py`，跟伺服器、假人一樣是獨立行程）每 15 秒看一次旁檔：有新單、玩家再回、玩家按了「找真人」，就把它**貼到 Discord `#客服`**（文字加截圖，用頻道的 webhook），同時在自己的輸出印一行。
3. **客服官**（一個專職的 Claude Code session，像現在的聯絡官，開在主機上）盯著橋的輸出，那一行一印就醒；不靠 Discord 叫（Discord 外掛會把 bot 與 webhook 貼的訊息丟掉，`server.ts` 第 806 行 `if (msg.author.bot) return`，所以「伺服器貼到頻道、Claude 在頻道上聽到」這條路走不通）。閒著不花 token。
4. 客服官用一支本機工具 `scripts/support_cli.py` 讀這張單：內容、截圖（存成檔讓它看）、單上帳號的帳號卡（名號、綁了哪幾種、元寶帳本），然後三選一：
   - **答得了**（規則、公告、常見問題）：寫回單上，狀態「已回覆、等玩家」；玩家看到的署名是「客服（自動回覆）」。
   - **缺資訊**：追問，一樣標自動回覆。
   - **要管理者動手或拿不準**：在單上寫內部註記「請管理者處理」（玩家看不到）、把核對要用的資料列好，在 `#客服` 貼一行 **@企劃者 @Joy**。
   每做完一張在 `#客服` 貼一行摘要（`#單號・做了什麼`），人在手機上就看得到全貌。
5. 玩家再回一句 → 橋印一行 → 客服官再看；玩家按「找真人」→ 這張單客服官不再自動回、`#客服` 點名兩位。
6. 企劃者或 Joy 在 `#客服` 說「#13 補發好了，回他」→ 客服官照做（回單、結單、註記三種動作而已）。
7. 「已回覆」的單玩家 3 天沒再回就自動結；標了「請管理者處理」或「找真人」的不自動結。

## 四、不做

- 客服官**不做任何管理者動作**：不補發、不退款、不重設、不解綁、不刪帳號、不碰 `/api/admin`。它只有回單、結單、註記三個寫的動作。
- 客服官**只看單上那個帳號**的帳號卡；「查別的帳號」（完整 Email、手機比對）不開給它，留給真人客服（6.3 的紀錄與每小時上限照舊）。
- 伺服器裡不呼叫 Claude、不接任何模型 API：判斷都在客服官那個 session 裡，伺服器只存、只貼。
- Discord 不是玩家的入口：玩家不進 Discord，`#客服` 只有企劃者、Joy、客服官（與日後的真人客服）看得到。`#beta-回報` 照舊歸聯絡官與 QA，這一版不併。
- 不收影片、語音、PDF；截圖只收 PNG、JPEG、WebP。
- 客服信箱照舊人工收，不進單。
- 不透露任何人是假人：帳號卡、單、CLI 輸出都不帶 `PlayerState.bot`；玩家問「某某是不是機器人」客服官不答。

## 五、遊戲那一側（`tianxia/features/support/`，第 215、216 批）

### 5.1 截圖（第 215 批）

- 一張單最多 `Config.support.files_max`（3）張，每張 `file_bytes_max`（3,000,000 位元組）以內；只收 PNG、JPEG、WebP，**照檔頭位元組認**，不看副檔名、不看 `Content-Type`。不重新編碼（不加 Pillow）。
- 存在旁檔旁邊的資料夾 `<db stem>-support-files/<單號>/<序號>.<png|jpg|webp>`；旁檔多一張表 `files`（單號、序號、種類、位元組數、sha256、上傳時間）。`scripts/backup_db.py`、`restore_db.py` 連這個資料夾一起備份、還原（照旁檔的時間戳規則）。
- 上傳走 `POST /api/support/file`（gate 第一行、登入、單是自己的、單沒結、還沒滿 3 張；一次一張，內文就是圖的位元組，單號在查詢字串；超過大小、不是那三種格式、滿了各一句拒絕，待 joy 潤）。畫面上寫單時先送文字再逐張傳圖；傳一半失敗的，單還在、圖少一張。圖掛在**單**上、不掛在哪一則回覆上：單沒結就能補圖（客服官追問「請附截圖」時玩家補得上），回覆表單不另外附圖；一張單從頭到尾最多 3 張。
- 看圖走 `GET /api/support/file/<單號>/<序號>`：單的主人、客服名單上的人、客服官都看得到，其他人 404 同一句。回應 `Content-Type` 照檔頭認的種類、`Content-Disposition: inline`，第 209 批的 `X-Content-Type-Options: nosniff` 已經全站都有。
- 不處理 EXIF（沒有圖片函式庫）：手機截圖本來沒有定位，但玩家若傳的是拍螢幕的照片可能帶 GPS。看得到圖的只有單的主人與客服，PM 認了這個風險，寫進第十三節。

### 5.2 客服官的身分（第 216 批）

- `Config.support.bot_account`（`tianxia/core/tuning/support.py`；帳號 id 或登入名，同 `staff` 的寫法）：客服官用的帳號，企劃者用 `scripts/set_password.py` 建、名號照保留字的規矩取（含「客服」兩字的名號只有名單上的帳號能取，上一份 6.1 已定）。
- 金鑰檔 `.local/support.json`（路徑常數放 `tianxia/core/identity_base.py`，跟 `SUPPORT_FILE` 並排；不進版控、不貼給任何 Claude）：`{"bot_token": "<至少 32 字>", "discord_webhook": "<頻道的 webhook 網址>", "server_url": "http://127.0.0.1:7861", "mention": ["<企劃者的 Discord ID>", "<Joy 的 Discord ID>"]}`。
- `/api/support/*` 的 `_staff` 多認一種：請求標頭 `Authorization: Bearer <bot_token>`（`hmac.compare_digest` 比對）→ 當成 `bot_account` 那個帳號，**不看** 6 小時密碼登入那一條（它沒有 session）。token 沒設、`bot_account` 沒設、帳號不在，一律跟不是客服同一句 404。
- token **只在 `/api/support/*` 有效**：`/api/admin*`、`/api/do`、`/api/main`、`/api/me` 收到它一律當沒登入（契約測試把 `FEATURE_ADMIN_ACTIONS` 全部工具與所有 `/api/admin*` 用 token 打一遍，全部要被拒）。
- token 進不了 `POST /api/support/lookup`（第四節第 2 條）：回 404 同一句。看單帶出的帳號卡照舊算一次 `log_card` 紀錄。
- 用 token 回的每一則 `replies.by_account_id` 就是 `bot_account`；玩家那一側照它標「自動回覆」。

### 5.3 自動回覆的標示與「找真人」（第 216 批）

- 玩家看單：客服官回的那幾則署名**「客服（自動回覆）」**，真人客服回的照舊「客服」（`_player_ticket` 多回 `auto: true/false`；`web/support.js` 的 `supportTicketHtml` 照它畫）。字待 joy 潤。
- 單上有自動回覆、還沒結的單，玩家那一側多一顆**「找真人」**（`POST /api/support/human {id}`，主人才按得動）：旁檔多一張表 `flags`（單號、種類 `human`、時間；之後要加別的旗標也放這裡，不 `ALTER` 舊表——第 212 批的前例）。按了之後：單的狀態回到「處理中」、畫面寫「已請真人處理」、橋貼到 `#客服` 點名兩位。旗標**留到結單為止**：客服官讀到 `human: true` 的單從此**不再自動回**；這張單由真人客服在客服頁回（照第 211 批的做法），或企劃者、Joy 在 `#客服` 說要回什麼、客服官**轉達**（6.2 的 `answer --human`：玩家看到的署名是「客服」，內部註記寫轉達自誰）。真人回過之後客服官也不接回去——玩家要的就是真人。
- 客服頁（真人與客服官看的）每一則回覆標誰回的：真人客服寫「客服・回覆」、客服官寫「客服官・自動回覆」（`_staff_ticket` 多回 `auto`）。

### 5.4 自動結單（第 216 批）

- 只看狀態：**「已回覆」（等玩家）的單，最後一則回覆距今超過 `Config.support.auto_close_days`（3）天就結單**，不看是誰回的、不看旗標——「請管理者處理」的單與「找真人」的單在等人的時候狀態是「處理中」，本來就掃不到；人回了、玩家又 3 天沒回，一樣結。單上多一則系統的字「3 天沒再回，單自動結了。」（待 joy 潤；`staff=1`、`auto=1`、不推播）。
- `admin_flag` 在客服（真人或客服官）回覆或結單那一下清掉（現在 `staff_reply` 只會設、不會清）。
- **不另開排程、也不讓「讀」有副作用**：掃的那一下是一條路由 `POST /api/support/sweep`（客服名單或 token；旁檔不在就什麼都不做），客服頁「重新整理」與客服官的 `queue` 叫 `queue` 之前先叫它一次。時間照 `shell.time.time()`（路由是殼）。掃到的單若客服官正好在回（3 天沒動的單只會是人叫它轉達），`staff_reply` 回「這張單已經結了」，CLI 原樣印、客服官在 `#客服` 說一聲。

### 5.5 旁檔與備份

- 旁檔 `<db>-support.sqlite` 多 `files`、`flags` 兩張表（`CREATE TABLE IF NOT EXISTS`，舊表不 `ALTER`）；多一個資料夾 `<db stem>-support-files/`。
- 資料庫第 9 版不動、沒有新的存檔欄位。
- 換回第 214 批的程式：單與回覆照讀，`auto` 看不出來（都寫「客服」）、「找真人」的旗標沒人讀、圖的檔留著沒人看；季中能換、不必休季。

### 5.6 畫面（企劃者 10/15 的規矩：先出對比圖再做）

這一份動到三處畫面，開工前由開發出 2～3 張真實畫面給企劃者挑，挑完才做：①寫新單的表單多截圖那一格（怎麼挑圖、縮圖怎麼排、3 張的上限怎麼寫）；②玩家看單時「客服（自動回覆）」的署名與「找真人」那顆的位置；③客服頁一張單的截圖怎麼擺（寬版右欄、窄版清單頁）。

## 六、主機那一側（第 217、218 批）

### 6.1 橋 `scripts/support_bridge.py`（第 217 批）

- 跟 `scripts/monitor.py` 同一種東西：獨立行程、只用標準庫加 `requests`、旁檔**唯讀**（`mode=ro`）、不 import `tianxia`（照 `store.py` 的檔名規則自己找旁檔與圖的資料夾；`TIANXIA_DB` 換了檔它跟著換）。它掛了遊戲不受影響；伺服器不知道它存在。
- 每 15 秒看一次：新單、玩家的新回覆、新的 `human` 旗標。自己的進度（看過的最大單號、回覆 id、旗標 id）記在 `.local/support_bridge.json`，重開不會重貼。
- 看到就做兩件事：①貼到 `#客服`（`.local/support.json` 的 `discord_webhook`；multipart、圖一起上傳；一張單一則：`#單號・類別・名號・版本・送單時間`、全文、截圖；玩家再回一句也一則；`human` 旗標一則、帶 `mention` 裡兩個 ID 的 @；**不貼帳號名、Email、手機**）；②在自己的 log 檔 `C:\Ray\tianxia-support\bridge.log` 追加一行機器可讀的字（`NEW 12`、`REPLY 12`、`HUMAN 12`、`FILE 12`〔補到的圖〕，每 5 分鐘一行 `ALIVE`），客服官的 Monitor 盯這個檔醒。**這一行只是鬧鐘**：客服官醒了不照它做事，先 `queue`（6.2）再照 queue 的結果做，所以漏印、重印、重開都不影響。
- 新單等 60 秒或已經有一張圖才貼（讓截圖傳完）；之後才到的圖當補貼、多印一行 `FILE`，客服官若還沒回就會連圖一起看，回過了就自己決定要不要補一句。
- 唯讀開 WAL 的旁檔：照 `scripts/monitor.py` 開主資料庫的做法（`mode=ro` 的 URI；主檔 `database.py` 也是 WAL，監控頁在這台這樣跑了一個月）；伺服器開著 `-shm`、`-wal` 都在。旁檔還不存在（沒人送過單）就睡著等。
- 橋直接讀旁檔、不走 API，是刻意的：伺服器掛了、token 沒設，它照樣把單貼出來；代價是它要認得 `tickets`、`replies`、`flags`、`files` 四張表的欄位——它的測試用 `support_kit` 造真的旁檔，表改了測試會紅。Discord 貼失敗（逾時、5xx）下一輪再試，進度不前進；連續失敗印一行警告，不停。
- `--once`（看一輪就結束）、`--dry-run`（只印不貼）給測試與排練用。測試用 `support_kit` 造一個旁檔、假的貼送函式，驗：第一次貼、不重貼、60 秒的等法、失敗重試、@ 兩個 ID、不含帳號名。

### 6.2 客服官的手 `scripts/support_cli.py`（第 217 批）

客服官**只透過這一支**動遊戲，它自己讀 `.local/support.json` 的 token（Claude 從頭到尾看不到 token）、打 `server_url` 的 `/api/support/*`、輸出 UTF-8 的純文字或 JSON：

| 子命令 | 做什麼 |
|---|---|
| `queue` | 先叫 `sweep`（5.4）再列沒結的單，每張標一種：**待客服官**（處理中、最後一則看得到的回覆不是客服官回的或還沒有回覆、沒有 `human` 旗標）、等玩家、等真人（`human`）、請管理者（`admin_flag`）。**這是客服官唯一的狀態來源**，橋的鬧鐘不算；同一張單重看一次結果一樣，所以重複醒來不會重複回 |
| `ticket <單號>` | 整張單：內容、每一則、帳號卡（名號、綁了、餘額、帳本）、截圖存到 `C:\Ray\tianxia-support\inbox\<單號>\` 並印路徑（在客服官的工作夾裡，Read 不用另外放行） |
| `answer <單號> --file <回覆.txt> [--close]` | 回一則、等玩家（或回完結單）；署名自動回覆 |
| `answer <單號> --file <回覆.txt> --human [--close]` | 轉達企劃者或 Joy 在 `#客服` 說的話：玩家看到的署名是「客服」，內部註記寫轉達自哪個 ID；只在那兩個人明說要回什麼時用 |
| `note <單號> --file <註記.txt>` | 內部註記「請管理者處理」（玩家看不到；設 `admin_flag`） |
| `close <單號>` | 結單 |

- 客服官的工作夾放一支 `cli.cmd`（用那份 clone 的 venv 叫 `scripts/support_cli.py`、把 `server_url` 等預設帶好），權限白名單只放行它。
- 回覆與註記的字從檔讀（不走命令列，免得引號與長度出事）；超過 1,000 字由伺服器拒絕，CLI 原樣印。
- 永遠不印 `bot`、不印 Email 與手機的明碼（API 本來就只給遮好的字）。
- 測試用 `tests/kit/webharness.py` 那一套起一台伺服器，驗每個子命令與 token 失效時的訊息。

### 6.3 客服官 session（第 218 批；照聯絡官的做法，`docs/superpowers/discord/中間bot-設定.md`）

- 資料夾 `C:\Ray\tianxia-support\`：`CLAUDE.md`（它的工作說明與規矩）、`cli.cmd`、`inbox\`（截圖）、`bridge.log`、`.claude/settings.local.json`、`start.cmd`（設 `DISCORD_STATE_DIR=%USERPROFILE%\.claude\channels\discord-support`，用 `Start-Process` 分離啟動橋、輸出導到 `bridge.log`，再開 `claude --channels plugin:discord@claude-plugins-official`）。
- **權限白名單寫死、不用 `--dangerously-skip-permissions`**：放行 Discord 外掛的 `reply`（聯絡官現在就是這樣）、`cli.cmd` 的任何參數、Monitor 盯 `bridge.log`、Read 自己工作夾底下的檔（截圖、FAQ、公開版玩法說明）；專案資料夾**不放行**。白名單外的任何動作都會跳許可、沒人按就停住——**那是設計**：客服官不該做白名單外的事，跳出來就是它想越線。第 218 批的排練要驗整條線走完一次許可都沒跳。

## 七、安全與隱私

- token 與 webhook 只在 `.local/support.json`，不進版控、不貼給 Claude；客服官透過 CLI 用它、看不到它。

## 十三、PM 的判斷（企劃者看這幾條就好）

1. **叫醒客服官的是橋、不是 Discord**：外掛丟掉 bot 與 webhook 的訊息，這是查過外掛程式碼確定的；Discord 留給人看與人下令。

5. **截圖不重新編碼、不處理 EXIF**：不加圖片函式庫；風險寫在 5.1。
6. **自動結單放在開客服頁那一下掃**，不另開排程。
7. **「找真人」是一顆鈕**，不是靠客服官讀字判斷。
8. 這一份不改聯絡官、不改 `#beta-回報` 的做法。
9. **審查員（Sonnet，2026-11-09）問了 12 題**，都在這一版答了：權限白名單寫死、白名單外跳許可就停（6.3）；鬧鐘是 `bridge.log`、唯一的狀態來源是 `queue`、重複醒來不重複回（6.1、6.2）；`human` 旗標留到結單、真人回或客服官轉達（5.3）；自動結單只看「已回覆」超過 3 天、不看旗標、`admin_flag` 回覆時清、掃改成明確的 `sweep` 路由（5.4）；圖掛單不掛回覆、單沒結就能補、補到的圖印 `FILE`（5.1、6.1）；WAL 唯讀照 `monitor.py` 的前例、橋讀旁檔的耦合刻意接受（6.1）；知識只給工作夾裡的公開版三樣、不放行 `docs/guide/`（6.3、6.4）；Joy 的 ID 確認不了先只認企劃者（十.2）。
