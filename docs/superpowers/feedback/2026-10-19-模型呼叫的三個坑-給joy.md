# 模型呼叫的三個坑（2026-10-19 線上抓到）

這一晚第 4 季廣宗決戰前後，`server_err.log`／`bots_err.log` 連續冒出「首次 LLM JSON 解析/請求失敗…觸發 re-prompt 重試」。查下來是三件不同的事，記在這裡免得之後又照著警告文字猜。

### 一、警告文字會騙人：「疑似被截斷」不一定是截斷

`ollama_client` 缺必填欄位時一律寫「疑似被截斷」。實際量過（`eval_count` 與回傳內容）：

- `fight_llm` 的 `losing`：**真的是截斷**。兩版過程各 200 字，`losing` 排在 schema 最後，預設 1024 不夠 → 已給 `PREDICT`（1320）。
- `letters` 的 `letter`：**不是截斷**。成功的信只有 75～85 字，240 的額度綽綽有餘。真因見下一節。

警告沒寫是哪一個呼叫，所以只能靠「缺的欄位名」反推；要是像 Ollama 回 500 那種就完全無法歸屬。**把 `response_model.__name__` 加進那一行**是一行的改動，還沒做。

### 二、schema 沒有 `required`，模型就合法地回 `{}`（每封信白跑一趟）

pydantic 欄位有預設值（`LetterText.letter: str = ""`）時，`model_json_schema()` 不會把它寫進 `required`；送出去當結構化輸出的語法，於是**允許模型回一個空物件**。接著 client 自己的 `_ensure_required_present` 判定缺欄位 → 重問一趟 → 第二趟才拿到信。

實測三次複現三次中：**每一封信都固定花兩次模型呼叫**。對照組是 `NameReply`（沒有預設值、schema 本來就有 `required`），取名一直都第一趟成功。

修法：`chat_structured` 多一個 `require_in_schema`，把呼叫端已經宣告的 `required_fields` 寫進送出去的 schema。**預設是不動**（opt-in），因為隨口應對的評分那一次被 FB-223 的守門測試釘到連 kwargs 都要一字不差（「評分那一次的提示與呼叫不能動」，丁批 QA 量到動它會讓分數整體移動）。開著的三條：`letters`（實測從兩趟變一趟）、`battle_instance.write_tales`（`TaleBatch.lines` 同樣有預設值）、`companion_agent` 的對話（`options`）。

### 三、省電模式下的冷啟動會吃掉假人取名的預算

省電模式（`.local/power_save`）沒人玩時會卸掉模型，再載回來實測 **11.4 秒**。假人取名的總預算 `bot_naming_budget_seconds` 原本 30 秒、`naming.propose` 切成兩趟 → 一趟只有 15 秒，光載入就吃掉大半，當晚逾時四次（同時在跑整套測試、CPU 滿載，加重了）。取名取不到的後果照欄位註解：**首創那一爐不開**（不用字表名字搶首創），絕學定名改用字表另組。正式內容改成 60 秒。

### 另外記一筆：num_predict 只加不減

第一版我把八個呼叫點全設了額度，其中五個是**調低**（取名 300、備註 800…）。調低沒有好處，而且會製造這一節要修的那個截斷；預設 1024 沒出過事的呼叫就別碰。原則寫在 `fight_llm.py` 的註解裡。

### 每回合的秒數也在同一晚改了

`round_seconds` 300 → 180（企劃者 2026-10-19）。量到的代價寫在 `tests/test_real_content.py::test_the_showdown_gives_scattered_players_time_to_gather` 的 docstring：廣宗那九回合實際 117／151／106／199／105／138／117／265／55 秒（平均 139），3 分鐘會截斷其中兩回合。
