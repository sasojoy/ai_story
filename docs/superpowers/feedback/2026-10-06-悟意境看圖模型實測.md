# 悟意境 §0.2a 實測：看得懂圖的模型能不能替畫圖取名

- 日期：2026-10-06
- 對象草案：`docs/superpowers/specs/2026-10-06-悟意境-draft.md`（PR #18，分支 `claude/insight-draft`）§0.2a
- 範圍：只量模型做不做得到。沒有寫遊戲程式、沒有改 main、沒有碰 `saves/` 與 `.local/`，沒有動 `server.py`／`run_bots.py`。
- 腳本與圖：session scratchpad 的 `glyph_probe.py`、`glyphs/*.png`、`vision_results.json`（獨立小腳本直接打 Ollama，不 import `tianxia/`）

## 結論（一句）

**值得做，但它是加分項不是地基**——看圖又快又準（熱機後約 4 秒、純辨識 8/8 全對），可是**只給文字特徵描述的對照組在八個形狀上全中（8/8），比看圖的預設提示詞還好**。看圖真正多出來的價值只在「規則沒編碼進特徵的東西」；而且**提示詞一定要明寫「說明要講出線條形狀」**，否則模型會改寫地點景色。

## 一、模型：不用多裝

**`gemma4:26b` 本身就看得懂圖**，`ollama show` 的 capabilities 列了 `vision`，並帶一個 572.79M 參數的 clip projector。所以草案 §0.2a 寫的「要另外拉 qwen2.5vl 或 gemma3（7B～12B）」沒有必要，一個模型兼兩用，省 6～9 GB 磁碟與一套額外的退路邏輯。

草案 §0.2a 最後那句「截至 2026-10-03 連 gemma4:26b 都載不起來」**已經過期**：Ollama 升到 0.35.1 後正常載入；而真正讓所有 LLM 功能走保底的原因是另一個與模型無關的程式缺陷（`success_rate: 0` 被 `_ensure_required_present` 當成截斷丟掉），已於 2026-10-05 修掉並推上 main（commit `e732370`）。

### 速度

| 情形 | 秒數 |
|---|---|
| 看圖，**閒置後第一次**（載 clip projector） | **19～28 秒** |
| 看圖，熱機 | **3.4～7.2 秒**（中位 3.8） |
| 只給文字特徵 | 3.7～4.5 秒（中位 4.4） |
| 純辨識（只問「這是什麼形狀」） | 約 5 秒 |

硬體：RTX 5070 12 GB，gemma4:26b 以 24% CPU／76% GPU 分攤跑，`keep_alive: 12h`。

**對設計的影響**：熱機後 4 秒跟現在的合併命名同級，不需要特別處理。但**閒置後第一次要 19～28 秒**，而玩家畫完圖正在等結果——需要比照煉製的「爐火正旺」做等待提示，或在進入感悟狀態（畫布出現）的那一刻就先送一個暖機請求，玩家畫圖那幾秒剛好用來載 projector。

**簡體字那一列有個量測陷阱，記下來**：我第一版用 OpenCC `s2twp` 比對原文與轉換結果來抓簡體，結果報了 10 筆——全是誤判。OpenCC（`s2t` 也一樣）會做**異體字偏好轉換**：岳→嶽、群→羣、峰→峯、岩→巖。那四個都是合法的正體字，不是簡體。實際把輸出餵進專案自己的 `tianxia.zh.to_traditional()`，`剛岩定心`、`峻嶺連峰`、`剛嶽觀山` 三個**一字未改**（它用詞組規則，不會單字硬換）。所以結論是零簡體，而且專案現有的轉換不會把模型的用字改壞。**以後要量「有沒有簡體字」，不能直接拿 OpenCC 的轉換差異當判準。**

## 三、最重要的發現：不是看不見，是看見了不寫

交叉與亂畫一團在上表是 0/3——但那不是辨識失敗。單獨問「這張圖畫的是什麼形狀」，**八張全對**：

| 圖 | 模型自己說的 |
|---|---|
| 圓圈 | 一個黑色的圓圈。 |
| 螺旋 | 一條黑色的螺旋線。 |
| 一道直劈 | 一條斜向的黑線。 |
| 交叉 | **兩條交叉的黑線。** |
| 鋸齒 | 連續的鋸齒狀波浪線。 |
| 波浪 | 波浪線。 |
| 一個點 | 一個黑色的圓點。 |
| 亂畫一團 | **雜亂交錯的黑色線條。** |

所以失手的原因是**提示詞裡的地點與屬性把圖壓過去了**：模型拿到「嵩山深處・靜坐觀山・剛」，就寫了一段山岳景色。圓／螺旋／波浪之所以成功，是因為那些形狀本來就能自然接到山勢的比喻；交叉與亂畫接不上，就整個被丟掉。

**一句話就能修。** 在提示詞加「說明裡必須明確寫出你在圖上看到的線條形狀（例如圓轉、交叉、折角、雜亂），不要只寫地點的景色」，重測那三個弱項，九次全部講到形狀：

| 圖 | 結果 |
|---|---|
| 交叉 | **剛毅交鋒**／以兩道堅硬的交叉線條，象徵意志如鐵般的正面碰撞 ・ **剛毅交錯** ・ **剛直交錯** |
| 亂畫一團 | **斷嶽折脊**／由圖中大量尖銳的折角與交錯線條組成 ・ **折脊剛意**／充滿尖銳折角與雜亂交錯 ・ 折獄剛勁 |
| 一道直劈 | **孤鋒直入**／如圖中那道筆直且凌厲的斜線 ・ **孤影斜劃** ・ **孤鋒意** |

（`折獄剛勁` 的「折獄」是審理案件的意思，用在這裡不通——偶發的用詞雜訊，約十分之一。）

## 四、對照組告訴我們的事（這才是該拿去做決策的那一條）

**只給文字特徵描述的對照組，八個形狀全中，而且略快。** 這很合理：那段描述是規則寫的，已經把答案講明了（「一筆圓轉、緩慢畫成的閉合圈」），模型只要接著發揮。

所以**看圖並沒有在「讓說明貼合筆畫」這件事上贏過文字路線**。它真正多出來的是**規則特徵沒有編碼的資訊**：
- 畫了幾個分離的符號、符號之間的相對位置
- 圖案像不像某個具體的東西（畫了一座山、一條魚、一個字）
- 整體的氣質（工整 vs 潦草），而不只是折角數量

草案 §0.2a 的分工（屬性由規則讀筆畫、名字由看圖模型寫）**本身是對的**，而且實測支持它：模型辨識穩定但不該用來定屬性（同一張圖三次可能給不同形容，見鋸齒那三次「震盪／連波／連峰」）。

## 五、建議（照實測結果調整草案 §0.2a）

1. **模型就用 `gemma4:26b`**，不要另外裝看圖模型。
2. **提示詞必須明寫「說明要講出看到的線條形狀」**，否則會變成地點景色的作文。這是整份實測最具體的一條。
3. **處理冷啟動**：閒置後第一次看圖 19～28 秒。建議在玩家進入感悟狀態（畫布出現）的那一刻就先送一個暖機請求，讓玩家畫圖的幾秒把 projector 載完；加上比照煉製的等待提示。
4. **退路順序照草案不變**：看圖 → 只給文字特徵 → 退路字表。但要注意**文字特徵那一層其實不弱**（實測 8/8），所以它是體面的降級，不是殘障模式。
5. **先確認看圖值不值得這條管道**：如果畫布只收一到三筆、而規則已經把直彎／開合／筆數／快慢都讀出來了，那看圖多出來的資訊有限。**真正能讓看圖發揮的前提是允許玩家畫得複雜一點**（多個符號、具象圖形）。這是設計要先決定的，不是模型能力問題。
6. 名字品質可用但有雜訊（約十分之一出現用詞不通，如「折獄」）。撞名過濾（`banned_names.json`）實測零命中，現有機制夠用。

## 六、追加：企劃者 2026-10-06 定「只能一筆畫到底」

這個限制對實測的影響：原本八張圖裡**有七張本來就是一筆畫成**（圓圈、螺旋、直劈、鋸齒、波浪、點，連「亂畫一團」都是一條連續亂走的線）。唯一違規的是**交叉（兩筆）**，而它正是失手的兩個之一。拿掉它重算，看圖的形狀命中率由 18/24 升為 **18/21（86%）**。草案裡拿交叉當例子的地方要改掉。

### 一筆到底之後，看圖還剩什麼價值：造「規則分不出、但長得不一樣」的單筆圖來測

一筆畫的特徵（直彎、開合、折角數、快慢、走向）規則本來就讀得到，所以關鍵問題是：**同一個屬性底下，不同的畫法模型分不分得出來**。造了兩組各三張，每張三次：

**柔組（規則一律讀成「柔」）——分得乾淨，三種各有其名：**

| 圖 | 三次的名字 | 說明抓到的形 |
|---|---|---|
| 圓圈（一筆閉合） | 圓融心境／圓融靜觀／圓融無礙 | 「一圈圓潤無缺的線條」 |
| 螺旋（一筆向內收） | 旋柔勁／旋柔意境／旋流柔意 | 「不斷盤旋縮小的螺旋線條」 |
| 彎鉤（一筆長弧帶鉤） | 垂首柔弦／垂弧柔意／垂首柔弦 | 「一條垂直下落後轉為圓弧的線條」 |

**剛組——部分成功，銳角類彼此會混：**

| 圖 | 三次的名字 | 判讀 |
|---|---|---|
| 山形（一筆三峰） | 剛毅鋸齒／剛嶽折線／剛折峻嶺 | 一次抓到（「如山脊般陡峭的三次折線」），兩次叫它鋸齒 |
| 閃電（一筆急折下行） | 折鋒意／折線驚雷／折線勁雷 | 三次有兩次抓到「雷」 |
| 鋸齒（一筆等距折返） | 連峰疊嶂／鋸齒驚雷／連峰疊浪 | 反被叫成山峰 |

**結論**：看圖確實提供了規則編碼不了的資訊（三種「柔」各有其名；閃電認出雷），所以一筆到底之後**看圖仍然值得**。但銳角類的單筆彼此會混淆，不要指望細分。

### 可是配方鍵會把這個價值丟掉

草案的配方鍵是**地點＋做法屬性＋畫的屬性**，全服共享、第一個悟到的人替全服命名。一筆到底之下，**山形、閃電、鋸齒三種畫法會落進同一個配方鍵**（嵩山深處＋靜坐觀山＋剛）。第一個人畫鋸齒、定名「連峰疊嶂」之後，**後面畫閃電、畫山形的人全部拿到「連峰疊嶂」，他們畫的圖根本不會被送給模型**（快取命中、零 LLM 呼叫、0.008 秒）。

那樣看圖模型一輩子只在每個配方的第一次被叫到，§0.3 寫的「同一個地方畫不同的形會悟到不同的東西」不成立。要救，配方鍵得再多帶一兩個規則讀到的筆畫特徵（折角數分段、開合、走向上下），或者走下一節的私有化。

## 七、企劃者問「意境不全服共用會有什麼問題，自己領悟的自己用」

查了現在的程式，這個方向在設計上站得住，但**它不是把一個開關關掉**，有四件事會斷：

1. **玩家手上沒有意境本體，只有 id。** `PlayerState.insights` 存字串 id，真正的 `Insight`（名字、屬性、正邪、說明）只存在 `content/insights.json`（寫死的六個）或**全服的 `insights` 表**——見 `insights.resolve()`：找不到寫死的就 `return world.get_insight(insight_id)`。改成私有要先把本體搬進角色存檔，是結構改動。
2. **功法會指向別人看不到的意境（最硬的衝突）。** `cultivation.py` 第 59～63 行，修練一門功法要求 `art.insight in state.player.insights`；而**功法是全服共享的**。私有意境的 id 一旦被寫進共享功法的 `insight` 欄位，別人拿到那門功法時 `resolve()` 回 `None`，功法等於廢的。**意境私有、功法共享，兩者目前耦合在一起**——這一條不管最後選哪個方案都要處理。
3. **江湖史的「首悟意境」整欄消失。** `_season_firsts_lines()` 跨季保留三種首創（合成首創、**首悟意境**、練成絕學），直接查 `insight_recipes.creator`。沒有「第一個悟到的人」就沒有那一行，而它是三根榮譽柱子之一。
4. **名字唯一性失效，重名變常態。** 現在 `claim_insight_recipe` 遇到名字被占用會回 `(None, False)` 讓退路改名。私有化之後十個人在同一處畫圓圈，可能生出十個都叫「圓融心境」的意境（本次實測三次就出現兩次「垂首柔弦」）。玩家之間沒辦法指稱同一個東西，傳聞與江湖史也寫不清楚。

**設計上會失去的**：§0.3 自己寫的「跟合成、合併同一種樂趣」那個首創者榮譽；以及 **LLM 呼叫量從「每個配方一次」變成「每個玩家每次」**（快取命中現在是 0 次呼叫，私有化之後熱機 4 秒、冷啟動 19～28 秒，十個人在線就是十倍）。

**但它正好解掉上一節那個矛盾**：自己悟的自己用，代表每個人畫的圖都真的會被模型看一次，看圖的辨識力不再被配方鍵丟掉。所以這兩件事是連動的：**共享配方＋看圖＝看圖幾乎沒用；私有意境＋看圖＝看圖才有意義。**

### 建議：切成兩半，不要全有全無

- **意境本體私有**：存進角色存檔，名字不要求全服唯一（重名就重名，那是你自己的感悟）。
- **首創紀錄仍然全服**：第一個在某地悟出某名字的人照樣登記進江湖史。登記的是**紀錄**，不是**定義**；後面的人自己悟自己的。
- **功法的 `insight` 欄位改成存屬性，或讓 `resolve()` 失敗時退回屬性比對**。這是第 2 點的必要修補。
